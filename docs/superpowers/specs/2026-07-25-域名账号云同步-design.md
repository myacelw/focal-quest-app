# 域名 + 账号体系 + 云同步（迭代 3）· 设计文档

日期：2026-07-25
状态：已获用户批准（4 个关键决策经确认；基于 6 方向联网调研，调研结论见 §2）。同日修订：域名决策改 .top；新增管理后台（§8）与防滥用（§9）设计；D1 免费版时点恢复期限修正为 7 天。

## 1. 背景与目标

App 现为纯前端 PWA（GitHub Pages，`myacelw.github.io/focal-quest-app/`），数据只在设备本地 IndexedDB（可选双写本机 Node+SQLite）。目标升级为"完整服务"：

- **买域名**，摆脱 github.io 的可达性波动与子路径。
- **注册/登录**：换设备、iPad+手机多端能拿到自己的数据。
- **后端数据存储**：只做**同步**（本地仍是可靠源），不做每操作调 API。
- **数据分析**：家长视角统计维持前端本地计算，多设备数据合并后再算；全体用户级运营分析延后到商业化。
- 约束：**零/近零成本**、适配中国网络监管、iPad+手机浏览器通吃。

## 2. 调研结论摘要（2026-07，决定方案的硬事实）

1. **微信登录 Web 端对个人是死路**：网站扫码登录需开发者资质认证（仅企业/个体工商户，300 元）；个人公众号不能微信认证故无网页授权。个人主体小程序禁用 web-view（无法套壳 PWA，须重写）、拿不到手机号、游戏须走小游戏（软著/版号）。→ 出局；将来办个体工商户可低成本补上，架构留第三方登录扩展位。
2. **短信并非完全死路但不首发**：常规短信通道 2025 年起对个人关闭（腾讯云已停新增个人资质）；阿里云「号码认证服务→短信认证」个人可开通（约 0.05 元/次、平台预置签名、仅 +86）。→ 二期可选增强。
3. **备案与海外托管互斥**：备案需国内接入商产品且域名必须持续解析到国内 IP（指回 GitHub Pages = 空壳网站 → 注销备案）；个人备案碰不了医疗/教育/游戏前置审批，"儿童视力训练"内容定性有风险。海外托管不备案完全合法。→ 现阶段不备案；域名在国内注册商注册+本人实名，保留将来备案资格。
4. **零成本后端唯一赢家 Cloudflare Workers/Pages Functions + D1**：免费层 10 万请求/天、D1 共 5GB，本场景富余百倍。`workers.dev`/`pages.dev` 子域在国内被污染，**必须绑自定义域名**。LeanCloud 免费版强制已备案域名；CloudBase 免费环境需半年手动续期；阿里云 FC 无永久免费层。
5. **域名**：阿里云/腾讯云 .com 首年 ~83-85 元、续费 ~90-95 元；国内实名 + 解析到海外托管是官方认可做法。.app 不在工信部批复列表、永远不能备案；.cn 监管强于 .com。
6. **合规红线是话术不是牌照**：宣称疗效 → 二类医疗器械（视功能训练软件已有注册证先例）；定位"游戏化训练记录工具"、不用"治疗/康复/恢复视力/降低度数"等词（六部门通知禁用语）即停留在非医疗器械范畴。儿童数据 = 法定敏感个人信息：需隐私政策（含儿童条款）+ 监护人同意 + 数据最小化。儿童数据同步到海外服务器字面触发数据出境义务（家用规模无执法先例）→ **商业化前须把后端迁回国内**（届时应有企业主体）。

## 3. 关键决策（用户已确认）

1. **托管路线**：海外免备案——域名解析 Cloudflare，前端 Cloudflare Pages，后端 Workers 生态，零月租；商业化时再迁国内。
2. **登录方式**：**邮箱 + 密码**（零成本零外部依赖）；邮箱验证/找回密码二期再接邮件服务；短信/微信留扩展位。
3. **域名**：**国内注册商（阿里云/腾讯云）注册 .top**（首年 ~14 元、续费 ~32-39 元/年，比 .com 每年省约 60 元；在工信部批复列表内、可备案），本人身份实名，NS 指向 Cloudflare 免费 zone。已知取舍：.top 声誉弱于 .com（个别安全软件/微信对其误拦概率略高）；IndexedDB 数据绑定域名，将来换域有真实迁移成本——按长期使用规划，商业化若换 .com 靠云同步迁数据。
4. **前端托管**：**Cloudflare Pages**（与后端同生态同域名；原生 `_headers` 发 COOP/COEP，vosk 跨域隔离不再依赖 SW 补头技巧）。

## 4. 总体架构

```
浏览器（iPad / 手机 / 电脑）
  ├─ React PWA（本地 IndexedDB = 唯一可靠源，离线全功能）
  │    └─ 同步引擎（outbox 推送 + 游标拉取，尽力而为）
  └─ HTTPS 同域
       Cloudflare Pages（静态 + _headers: COOP/COEP/CORP/CSP）
       └─ Pages Functions /api/*（同域，无 CORS）
            └─ D1（SQLite：users / records 追加日志（含 profile 事件）/ tokens / counters）
```

- **同域 API**：Pages Functions 挂在同一域名 `/api/*` 下，零 CORS、零预检，且 crossOriginIsolated 页面对同源 fetch 无 CORP 负担。
- **本地优先铁律延续**：后端不可用 → 训练/打卡/统计/勋章全部照常，同步静默重试。每用户每天 API 调用个位数。
- 现有本机 Node+SQLite 后端（server/）：同步语义被 Worker+D1 取代，保留作 dev 调试或退役（实现阶段定）。

## 5. 账号与认证

### 5.1 模型
- **家长账号**（email 唯一）→ 下挂多个**孩子档案 profile**（昵称即可，不收真名/生日——数据最小化 + 二孩支持）。
- 孩子操作无登录概念：选档案即练。设备记住 activeProfileId（本地设置，不同步）。
- 一期注册需**邀请码**，且**邀请码归属于账号**：每个账号注册时自动获得专属邀请码（设置页可见可复制），新用户落库 `invited_by`=码主账号——注册来源可追溯（防滥用主线，见 §9.2）。

### 5.2 密码方案（适配 Workers 免费层 10ms CPU 限制）
- 客户端：`authKey = PBKDF2-SHA256(password, salt=normalize(email), ~310k 次)`（WebCrypto，浏览器无 CPU 限制，重计算发生在客户端）。
- 服务端：存 `SHA-256(serverSalt ‖ authKey)`（单次哈希，微秒级 CPU）。防 DB 泄露有客户端拉伸兜底，服务端 CPU 不超限。
- 登录失败限速：D1 计数（按 email+IP，10 次/小时）。

### 5.3 会话
- 不透明随机 token（32B）+ 客户端 localStorage，`Authorization: Bearer`；**D1 只存 token 的 SHA-256**（泄库不泄会话），常数时间比较。滚动有效期 365 天（家庭设备，免频繁重登）。

### 5.4 一期已知取舍（明示）
- 无邮箱验证：邮箱仅作登录标识——邀请码制下"抢注他人邮箱"的风险仅限持码者，家庭规模可接受；开放注册前必须接邮件验证（Resend）。
- 无自动找回密码：**local-first 使此事不紧急**——数据在设备本地全量存在，丢账号≠丢数据，新账号重传即可恢复云端。一期文档说明+人工处理。

## 6. 数据模型与同步协议

### 6.1 服务端 D1 表
```sql
users   (id, email UNIQUE, auth_hash, server_salt, is_admin DEFAULT 0,
         invite_code UNIQUE, invited_by /*邀请人 user_id，站长为 NULL*/,
         invite_quota DEFAULT 5, created_at)
tokens  (token_hash PK, user_id, created_at, last_seen_at)
records (user_id, uuid, profile_id, kind, payload JSON /*含 _deleted 墓碑*/,
         updated_at /*客户端逻辑时间，LWW 判据*/, received_at, seq INTEGER,
         PRIMARY KEY(user_id, uuid))
CREATE INDEX idx_records_pull ON records(user_id, seq);
counters(date, metric, value, PRIMARY KEY(date, metric))
```
> **⚠️ 2026-07-25 勘察修订**：原设计假设"全是追加式不可变数据"**与现实不符**。实际数据层为 Dexie v5、**7 张表**（sessions/checkins/badges/monsters/rewards/redemptions/exams），其中 `rewards`（软删 `active=false`）、`redemptions`（status: pending→fulfilled/cancelled）、`checkins`（补签改 streak）走 `update`/`put` **可变**，`exams` 还有**真删除**（`db.exams.delete`）。故协议为下述 **LWW upsert + 墓碑**，而非纯追加日志。

- **单表 KV 化**：一行 = 一条业务记录的最新快照，`kind ∈ {session, checkin, badge, monster, reward, redemption, exam}`，服务端**不解析 payload**（分析在前端）。
- **同步身份 uuid**（与本地自增 id 解耦），分两类生成：
  - **自然键表派生确定性 uuid**：`checkin:<date>` / `badge:<badgeId>` / `monster:<monsterId>`——两设备同日打卡或解同一勋章算出**同一 uuid**，LWW 自动收敛为一行，天然去重。
  - **自增键表用随机 uuid**（`crypto.randomUUID()`）：sessions / rewards / redemptions / exams。
- **LWW 判据 `updated_at`**（客户端写入时的本地毫秒）。家庭场景同一时刻只有一台设备在用，LWW 足够，不引入向量时钟。
- **按 kind 分派合并策略**（客户端 `mergeRecord()` 纯函数，服务端一律 LWW 不区分）：
  | kind | 策略 | 理由 |
  |---|---|---|
  | session / reward / redemption / exam | LWW（`updatedAt` 大者胜） | 后写即最新意图 |
  | **badge / monster** | **取最早**（`unlockedAt` / `capturedAt` 小者胜） | ⚠️ 两设备各自解锁同一勋章时 LWW 会留下**较晚**的时间戳，而"首次达成时刻"才是正确语义 |
  | **checkin** | LWW 落库后**整体重算**（§6.5） | `streak`/`totalPoints` 是链式累积，LWW 修不了错乱的链条 |
- **删除用墓碑**：`exams` 删除推 `payload={_deleted:true}`，其他设备拉到后按 uuid 删本地行；本地表不加 `deletedAt`，删除仍是真删。
  ⚠️ 这是对既有策略的**有意变更**：`deleteExam()` 现在刻意不推送（注释"删除仅本地（后端是防丢副本非镜像）"）。单向备份下那样合理，但真同步下若不传播删除，A 设备删掉的记录会被 B 设备的数据**复活**。故 3b 起 `exams` 删除必须推墓碑。
- **`seq` 必须在 UPDATE 时也递增**（SQLite AUTOINCREMENT 在 UPDATE 时不变）→ 用 §6.3 的 per-user 预留区间法分配。
- `counters` 为按日计数表（滥用与统计通用，`INSERT..ON CONFLICT` 自增）；`received_at` 为服务端落库时间，供管理统计与排障。
- 档案（3c）走 `kind='profile'` 的 LWW 行，改名 = 覆盖同 uuid。

### 6.2 客户端改造（Dexie v6 迁移）
- 7 张表各行增加 **uuid**（建索引；存量迁移按上述规则补齐）、**updatedAt**、**profileId**（存量归入自动创建的默认档案）。
- 新增 `outbox`（`++id, uuid, kind, payload, updatedAt, op`）与 `syncMeta`（`key` 主键：lastPulledSeq / token / email / userId）。
- **改造点集中在 `src/data/api.ts`（架构红利）**：现有 `pushSession/pushCheckin/pushBadges/pushMonsters/pushRewards/pushRedemptions/pushExams` 已在所有写入点被调用（checkin.ts、rewards-service.ts、badge-service.ts、dex-service.ts、exams-service.ts）。**保持这些函数签名不变**，仅把实现从"POST 本机后端"换成"写 outbox + 触发同步"，则业务代码零改动。
- 需补的两个缺口：`exams` 删除**当前无 push 调用**（新增 `pushExamDeleted(uuid)`）；`restoreBackup()` 导入后**当前不推送**（导入结束触发全量重推）。
- 设置/标定/皮肤选择**不同步**（设备相关；皮肤解锁由累计积分派生，积分由 checkins 派生，跨设备天然一致）。

### 6.3 协议（2 个端点）
- `POST /api/sync/push` `{records:[{uuid, profileId, kind, payload, updatedAt}]}`：
  1. 先 `UPDATE users SET sync_seq = sync_seq + N WHERE id=? RETURNING sync_seq` **预留 N 个连续 seq**（并发安全；若第 2 步失败只留 seq 空洞，无害）；
  2. 再 batch `INSERT ... ON CONFLICT(user_id,uuid) DO UPDATE SET payload=excluded.payload, updated_at=excluded.updated_at, seq=excluded.seq WHERE excluded.updated_at > records.updated_at`（**旧数据不覆盖新数据**，且按 uuid 幂等）。
- `GET /api/sync/pull?since=<seq>&limit=500` → `{records, nextSince, hasMore}`（`WHERE user_id=? AND seq>? ORDER BY seq`）。
- 触发时机：应用启动、单节训练完成后、网络恢复；失败指数退避，永不打扰训练。
- **拉取后必须重算 checkins**（关键，见 §6.5）。
- 新设备引导：**先登录再使用**则零歧义；若先离线练了再登录，本地数据并入该账号（不做跨账号历史合并，MVP 明示此限制）。

### 6.4 注册即绑定
注册/登录成功 → 现有本地 7 表全量入 outbox 推送（存量上云），换设备登录 → 全量 pull 重建。可复用 `backup-service.ts` 的 `readTables()` 模式读全量。

### 6.5 checkins 重算（多设备正确性的关键）
`CheckinRow.streak` 与 `totalPoints` 是**链式累积**写死在行里的（`doCheckIn()`：`totalPoints = 上一条.totalPoints + dailyPoints`）。两台设备各自打卡不同日期后合并，链条必然错乱——**LWW 不足以修复，必须重算**。

- 新增纯函数 `reconcileCheckins(checkins, sessionsByDate, repairDates) → CheckinRow[]`：按 date 升序，用现有 `nextStreak()` / `dailyPoints()` 重算 streak/dailyPoints/totalPoints；补签补插的行（date ∈ repairDates）保持 `dailyPoints=0`。
- 时机：每次 pull 落库后运行一次，把变化的行写回本地（并入 outbox 推送，使各设备收敛到同一结果）。
- 可测性：纯函数，输入输出皆为普通对象，遵循 `weekly-report.ts` 既有范式。

## 7. 合规组件（一期必做）

1. **隐私政策静态页**（含"儿童个人信息处理"专节：收集范围、目的、存储地点与期限、监护人权利、拒绝选项）。
2. 注册流程勾选：**「我已阅读隐私政策，我是孩子的监护人并同意」**（不勾不能注册；不注册不影响本地使用——满足"不同意不得拒绝基本功能"）。
3. **数据最小化**：档案仅昵称；不收孩子真名、生日、照片。
4. **文案红线**：全站（含 i18n 字典、README、商店描述）禁用"治疗/康复/恢复视力/降低度数/近视治愈"类词——现有「关于训练·家长必读」的"记录+引导、非诊断"定位保持。
5. 留存一份简版个人信息保护影响评估记录（docs/ 内一页纸）。

## 8. 管理后台（仅自用）

- **入口**：同一 PWA 内 `/admin` 懒加载路由（不进主包），仅 `is_admin=1` 的账号可见；`/api/admin/*` 端点同样校验。管理员标记由部署者在 Cloudflare D1 Console 手动执行一次 SQL 设置（不做提权 UI）。
- **指标（全部由现有表 SQL 派生，无需解析 payload）**：
  - 总注册数 / 总档案数 / 各 kind 记录量与增速；
  - **日活/周活/月活**：主口径 = 当日有 `kind='session'` 记录的去重用户（按 client_created_at，即"练了的人"）；辅口径 = `tokens.last_seen_at`（"打开过的人"）；
  - 每日训练节数曲线（复用前端手绘 SVG 图表组件与糖果主题）；
  - 最近注册列表（含邀请人）；**注册来源统计**：按邀请人聚合的邀请树/排行（`invited_by` 一列 SQL 即得）；
  - 滥用计数（counters：注册被拒 / 登录限速命中 / 推送被拒 / 配额超限）。
- **统计口径明示**：只覆盖注册且同步的用户；未注册的纯本地用户不上报——**不加匿名遥测**（隐私与儿童合规成本不值，家庭规模下装机量≈注册量）。
- **即席查询不做 UI**：复杂/一次性查询直接用 Cloudflare 控制台的 D1 Console 跑 SQL——自家服务没必要开放"任意 SQL"的 API 攻击面。

## 9. 防滥用（纵深四层）

1. **边缘层（全免费）**：自定义域名走 Cloudflare 代理，默认含不限量 DDoS 缓解 + Bot Fight Mode；免费版含 **1 条 WAF 限速规则**，用在刀刃上——限 `/api/auth/*`（如同 IP 10 次/10 秒即限流）。
2. **注册主防线 = 归属制邀请码（一期）**：注册必须携带有效邀请码；每个账号注册时自动生成专属码（8 位、去易混字符），新用户落库 `invited_by`=码主——**注册来源天然可追溯，且传播链有主**。防扩散控制：每账号邀请配额 `invite_quota`（默认 5，用量按 `COUNT(invited_by)` 派生不另存计数；管理员把某账号配额改 0 即封其码，泄码最大伤害=配额余量）。
**IP 限速分两道**（实现时修正，勿合并）：**成功建号 20 次/日** + **失败尝试 10 次/小时**。原设计写的是"每 IP 每日注册上限"单一额度，实现中发现那会让**手抄或口述邀请码错几次的家长被锁一整天**——家长抄错是常态，代价远大于防住的滥用。拆开后失败额度用短窗口、一小时自愈；邮箱/authKey 形状错误与重复邮箱不吃失败额度（前者该由客户端本地校验，后者是"已注册"这类用户侧信息）。`functions/lib/ratelimit.test.ts` 有 3 个测试锚定此意图。**引导启动**：首个账号（站长本人）用一次性引导码（`INVITE_CODE` 环境变量）注册、`invited_by=NULL`，之后删除该变量关闭系统码，全站只剩归属码通道。**不用 Turnstile**：其验证域 challenges.cloudflare.com 在大陆存在 DNS 污染、不可靠（2026-07 核实）；将来开放注册时改用"邮箱验证 + 限速"组合，人机验证届时再评估。
3. **应用层配额（Functions 内校验，命中即记 counters）**：
   - 登录失败限速：同 email+IP 10 次/小时（§5.2）；
   - push：每请求 ≤500 条 / 总体 ≤1MB / 单条 payload ≤16KB / kind 白名单 / 字段 schema 校验；
   - 每用户每日写入 ≤2000 条、累计 ≤10 万条（护住 D1 免费 5GB；正常使用一天只有十几条）。
4. **令牌与密码**：token 只存哈希（§5.3）、密码客户端拉伸（§5.2）、登录失败限速——暴破三重不划算。

**兜底性质**：local-first 决定了最坏情况——API 被打挂或 10 万请求/天免费额度被耗尽——训练、打卡、统计、勋章全部照常，攻击的最大伤害只是"当天同步延迟"。

## 10. 部署与迁移

- **域名**：阿里云/腾讯云注册 .top（用户操作：注册+实名，首年 ~14 元）→ NS 改指 Cloudflare 免费 zone → Pages 绑 apex + www。
- **Cloudflare Pages**：GitHub Actions 构建后 wrangler 部署（需 CF API Token secret）；`_headers` 发 COOP/COEP/CORP + CSP；`functions/api/*` + D1 binding。
- **Vite base 归位 `/`**（现为 `/focal-quest-app/`，已有 env 化基础）；SW 保留（离线预缓存职责不变），补头逻辑退化为无害兜底。
- **vosk 模型三分片保留**（当年 EdgeOne 的切片方案再次救场）。⚠️ 勘察修正：单片实为 **20 MiB 整**（20971520 B），Pages 单文件上限 25 MiB，**余量仅 5 MiB**；且仓库内**无切片脚本**（分片是手工产物），将来换模型需先补脚本。
- **SW 必须放行 `/api/`**：`src/sw.ts` 的 fetch handler 对所有同源 GET 做 cache-first，会让 `GET /api/sync/pull` 读到过期缓存。此改动**排在 3a**（而非 3b）上线，好让已装机 iPad 在账号功能到来前就换上带放行的 SW。
- **过渡期**：GitHub Pages 部署链保留为热备，CF Pages 真机验证稳定后再决定去留。
- **D1 备份**：免费版 Time Travel 仅 **7 天**时点恢复——按月 `wrangler d1 export` 快照（可做成 GitHub Action 定时导出存私有位置）。

## 11. 测试策略

- 同步引擎单测：outbox 入队/幂等推送/游标拉取/去重合并/断网重试（模拟 fetch）。
- Dexie v3 迁移单测：存量数据补 uuid/profileId 的正确性。
- Functions 单测：auth（注册/登录/限速）、push/pull 幂等，跑在 vitest + wrangler 本地环境。
- 防滥用单测：邀请码校验、push 配额与 schema 拒绝、登录限速、counters 记数；admin 端点鉴权（非管理员 403）。
- 端到端手测清单：双设备（iPad+手机）注册→训练→交叉同步→换新设备重建；断网训练→恢复补传。

## 12. 迭代拆分（各自走 spec→plan→实现）

- **3a 基建搬家**：买域名、CF Pages + `_headers` + 自定义域名 + CI、base 归位、真机验证 crossOriginIsolated/离线。**不含任何账号代码**。
- **3b 账号与同步**：D1 schema、auth、同步引擎、设置页「☁️ 云同步」卡、隐私政策+监护人同意。**防滥用（归属制邀请码/限速/配额/令牌哈希）随注册同批上线，不拆开。**（schema 自始含 profileId，UI 先单默认档案）
- **3c 多档案 UI**：档案切换、按档案统计/勋章、迁移打磨。
- **3d 手机竖屏适配**：与账号无依赖，可与 3b/3c 并行。
- **3e 管理后台**：`/admin` 路由 + `/api/admin/*` 统计端点 + 滥用计数展示（依赖 3b 的数据积累，排 3c 前后皆可）。

## 13. 风险与止损

| 风险 | 应对 |
|---|---|
| CF 海外边缘国内访问波动 | 同步尽力而为+离线全功能；必要时 DNSPod 分线路解析（延后） |
| 免费层政策变化 | 数据可全量导出；后端为 ~200 行同步逻辑，可平移自建/国内 |
| 儿童数据出境纸面义务 | 家用规模接受；商业化触发迁国内+企业主体（§2.6） |
| 邮箱无验证被抢注 | 邀请码把风险限定在持码者内；开放注册前接 Resend 验证 |
| .top 后缀声誉（安全软件/微信误拦概率略高于 .com） | 家用+亲友场景接受；将来若换域，云同步负责迁数据 |
| D1 免费版时点恢复仅 7 天 | 按月 `wrangler d1 export` 快照（可定时化） |
| 恶意注册/API 滥用 | §9 四层纵深；最坏情况仅同步延迟，训练不受影响 |
