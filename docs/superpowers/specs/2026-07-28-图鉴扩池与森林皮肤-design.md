# 图鉴扩池 + 魔法森林皮肤 · 设计文档

日期：2026-07-28
状态：已获用户批准（5 个关键决策经确认：扩池规模 / 新皮肤主题 / 美术风格 / 解锁定价 / 同时做闪光变体；四节设计逐节通过）
来源：闺女实测反馈——「图鉴没几天就收集差不多了」。用户同时提出「再做一套新皮肤」，并在看过风险清单后决定把原本列为「下一张牌」的闪光变体也并进本轮。

## 1. 问题与定位

**图鉴的内容供给跟不上获取速率。**

- 现有 **34 只**（太空 17 + 神庙 17，各 6 普通 + 8 稀有 + 3 史诗）
- 获取速率 **每天最多 3 只**：打卡保底 1 只（`shouldDailyCapture`）+ 彩蛋最多 2 只（`DAILY_EGG_CAPTURE_MAX = 2`）
- 理论最快 12 天集齐，按平均 2.5 只/天约 14 天——与「没几天就差不多」吻合

图鉴在整个激励体系里的定位是**每天的小确幸**（免费、打卡必得一只；与之相对，卡册是攒几天的大奖）。集齐之后这份小确幸就消失了，所以问题必须靠**加内容**解决，而不是靠降低获取速率——后者只是让孩子等，不会把乐趣还回来。

**顺带解决第二个诉求**：新皮肤天然带来一个新世界的怪兽池，两件事在内容上是同一件事。

### 1.1 为什么出图成本没想象中高

怪兽是 **4×4 网格一张出 16 只**。所以 +48 只只要 **3 张网格图**。对比参照：卡册那一轮一次出了 16 张。

### 1.2 一个已有的正反馈值得保留

捕获的储备怪会**加进训练轮换池**（`buildEnemyPool` / `buildGuardianPool` 按 `capturedReserveIds` 过滤）。所以扩储备池 = 同时扩训练画面的变化度，收集本身会让训练更耐看。

## 2. 关键决策（用户已确认）

| 决策 | 选择 | 理由 |
|---|---|---|
| 扩池规模 | **+48 只（34 → 82）** | 3 张网格图即可；按 2.5 只/天约再撑 19 天，史诗档因权重低尾巴更长 |
| 新皮肤主题 | **魔法森林 / 精灵** | 与冷色太空、暗色神庙形成对比 |
| 美术风格 | **柔和插画风（同卡册）** | 闺女刚选了深海精灵卡套、已认可这个风格；与 app 的「糖果能量」主题最融；透明背景的柔和插画也是 Gemini 最稳的一类 |
| 解锁门槛 | **4000 累计分** | 延续 0 / 1000 / 2500 的递增节奏。**用累计分（只增不减、不扣分）**，她本人早已过线、上线即可玩，门槛只对将来的新用户起作用 |
| 闪光变体 | **本轮一起做**（原列为「下一张牌」） | 光扩池到 82 只按 2.5/天也只撑约 19 天；闪光零美术成本把收集量翻到 164、约 68 天，才真正对上卡册那个两个月的节奏。作为独立的阶段四，可随时喊停（§10） |

## 3. 内容与数据模型

### 3.1 48 只的分配（受一条约束支配）

`reserveMonstersOfWorld` 的筛选条件是 `rarity !== 'common'`，而每个世界的 6 只 BASE 是**写死在 Stage 里**的（`BASE_ENEMIES` / `BASE_GUARDIANS`）。

**推论：给太空/神庙新增 `common` 会造出"只存在于图鉴、永远不出现在训练画面里"的怪。** 所以：

| 世界 | 新增 | 稀有度 | 说明 |
|---|---|---|---|
| 🌲 forest（新） | 16 | **6 普通 + 7 稀有 + 3 史诗** | 6 只普通进 `BASE_SPIRITS` 轮换，与现有世界的 6/8/3 结构对齐 |
| 🚀 space | 16 | **10 稀有 + 6 史诗** | 全部非普通 → 自动进储备池 → 捕获后进训练轮换 |
| ⛩️ shrine | 16 | **10 稀有 + 6 史诗** | 同上 |

扩池后总计 **82 只**：普通 18 / 稀有 43 / 史诗 21。

抽取权重不变（保底 70/25/5、彩蛋 30/45/25）。权重是**按档**而不是按只，所以档里怪变多不会让该档掉率变高，只会让该档更难集完——这正是想要的。

### 3.2 `World` 扩成三个，并去掉世界硬编码

`World` 类型加 `'forest'`。同时在 `monster-defs.ts` 导出

```ts
export const WORLDS: readonly World[] = ['space', 'shrine', 'forest']
```

并让下列 6 处**从它派生**，不再写死世界字面量：

| 位置 | 现状 | 改为 |
|---|---|---|
| `dex-service.ts:43` | `const byWorld: Record<World, number> = { space: 0, shrine: 0 }` | 由 `WORLDS` 构造 |
| `dex-service.ts:44` | `byWorldTotal` 同上 | 同上 |
| `dex-service.ts:56` | `Record<World, string[]> = { space: [], shrine: [] }` | 同上 |
| `DexWall.tsx:21` | `const WORLDS = [{ key: 'space' }, { key: 'shrine' }]` | 用导出的 `WORLDS` |
| `TrainingPage.tsx:63` | `useState<Record<World, string[]>>({ space: [], shrine: [] })` | 由 `WORLDS` 构造 |
| `TrainingPage.tsx:561` | `effectiveSkinId === 'space' ? … : effectiveSkinId === 'shrine' ? … : []` | `capturedByWorld[effectiveSkinId] ?? []` |

⚠️ **最后一处是本次重构的真正理由**。前 5 处漏改会被 TS 的 `Record<World, …>` 完整性检查挡下来，而那条三元链有 `: []` 兜底——**漏改不会报错，只会让森林皮肤永远吃不到储备怪，静默失效**。改成按 id 索引之后，这条路根本不存在。

它成立的前提是「皮肤 id 与世界 id 同名」，这条由 §8 的一条新测试锚住。

### 3.3 素材路径

```
public/skins/forest/<slug>.webp            ← 6 只基础精灵
public/skins/forest/reserve/<slug>.webp    ← 10 只储备
public/skins/forest/bg.webp                ← 森林背景
public/skins/space/reserve/<slug>.webp     ← 新增 16 只（与既有 11 只同目录）
public/skins/shrine/reserve/<slug>.webp    ← 新增 16 只
```

### 3.4 `MonsterImage` 加缺图回落

现在是 `<img src={def.img}>` 直连，**没有任何兜底**，缺图就是破图图标。加一个与 `CardImage` 同款的回落（渐变 + 首字母），两个理由：

1. 让代码可以先于美术落地、独立验收（否则 48 条 defs 一进去，图鉴里就是 48 个破图）；
2. 线上万一某张图没进 SW 预缓存，也不该给孩子看破图。

## 4. 魔法森林皮肤

### 4.1 沿用「怪兽承载视标」结构

与神庙同构：精灵每题轮换，视标 E 印在精灵身上的深色圆底上。这套已被验证过，不另起炉灶。

导出的三个符号照 `ShrineStage` 逐一对位，便于测试与将来扩池：

| 神庙 | 森林 |
|---|---|
| `BASE_GUARDIANS`（6 只） | `BASE_SPIRITS`（6 只） |
| `buildGuardianPool(capturedReserveIds)` | `buildSpiritPool(capturedReserveIds)` |
| `guardianForSeq(seq, capturedReserveIds?)` | `spiritForSeq(seq, capturedReserveIds?)` |

储备池同样由 `reserveMonstersOfWorld('forest')` 派生，不手写第二份清单。

### 4.2 两条从神庙抄来的医学铁律（不可动）

1. **视标祖先链上不许有 `transform: scale`。** 3d 迭代时神庙正是因为祖先挂了 `scale(0.8)`，让 E 只有标定值的 80%——等于换个皮肤就偷偷把训练强度降一档，而家长完全无感。缩放要折进容器的 `width/height`（见 `ShrineStage.tsx:102` 那段注释）。
2. **E 的深色圆底 padding 走 `heightPx * 0.4`，不许换成 `cqmin`。** 圆底必须与**视标**同比例，而不是与画布同比例。

### 4.3 演出

| | |
|---|---|
| 背景 | 古树林光束插画（`bg.webp`） + 一层柔和绿色氛围光 |
| 主体 | 森林精灵每题轮换 + 名牌 + 视标 E |
| 答对 | 光点爆散 + 花瓣飞舞 + 萤火虫上升 |
| 答错 | 画面轻微暗闪 + 精灵抖动（复用 `fzpShakeG`） |
| 翻拍过渡 | 「藤蔓重织」+ 柔光（对位神庙的「符文重组」） |
| 彩蛋 | 金色光晕（复用现有 `drop-shadow` 写法） |
| 计数 | 🍃 叶片 N/10 → 点亮一棵古树（对位神庙的精灵/神庙计数） |

### 4.4 刻意不做下方的动画角色

神庙的勇者用了两条 CC0 精灵图（idle 4 帧 / attack 6 帧）。**逐帧动画 AI 生成不了**，得去找 CC0 素材，是整套里最难的一块，而它对训练体验的贡献很小。省掉之后森林只需要 **1 张背景 + 16 只怪**。

### 4.5 注册

`registry.ts` 的 `SKINS` 加一条 `{ id: 'forest', name: '魔法森林', Stage: ForestStage }`，`SKIN_UNLOCK_COST.forest = 4000`。

既有 `registry.test.ts` 只有**一条**断言会红：`SKINS.map(s => s.id)` 的等值断言。其余不受影响——`pickRandomSkin(3000, 0.99)` 在 3000 分时池子仍是 `[space, shrine]`、结果仍是 `shrine`；`newlyUnlockedSkins(0, 3000)` 也仍是 `['space','shrine']`。

## 5. 闪光变体

每只怪都有一个极稀有的「闪光」版本：**同一张图 + 统一的金色微光处理**，零新美术就把收集量从 82 翻到 **164**。

### 5.1 为什么是独立行，而不是在行内加 `shinyAt` 字段

直觉写法是给 `MonsterRow` 加一个可选的 `shinyAt`，一行代表一个物种。**这个写法会被同步语义静默吃掉数据。**

`merge.ts` 对 monster 的规则是**整行取最早 `capturedAt`**（`EARLIEST_FIELD`）。于是：

| | 设备 A（本地） | 设备 B（远端） |
|---|---|---|
| 行 | `{ capturedAt: 100 }` | `{ capturedAt: 100, shinyAt: 200 }` |

合并时 `remoteT === localT === 100`，`remoteT < localT` 为假 → 判 **skip** → **B 的闪光被丢掉，且全程无声**。

要修就得把 merge 从「整行 put / skip / delete」改成「按字段合并」——那是动同步核心，风险远大于收益。

**改成独立行则完全绕开**：

```
id = 'space-ufo'           → uuid = monster:default:space-ufo
id = 'space-ufo~shiny'     → uuid = monster:default:space-ufo~shiny
```

每个收集品一行一 uuid，`capturedAt` 取最早照常成立，**同步层零改动**。后缀用 `~shiny` 而不是 `-shiny`：slug 里本来就有连字符（`comet_rider` 那批用下划线，但不保证以后不用连字符），`~` 不会歧义，也**不含冒号**（`naturalKeyFromUuid` 靠这条反解）。

在 `monster-defs.ts` 导出配套的纯函数：`SHINY_SUFFIX`、`shinyIdOf(id)`、`isShinyId(id)`、`baseIdOf(id)`。

### 5.2 获取：两步掷骰

```
1. 以 SHINY_CHANCE 掷「这次是不是闪光」
2. 从对应的桶里抽一只未拥有的：
     闪光桶 = 所有物种的闪光条目 − 已拥有的闪光
     普通桶 = 所有物种 − 已拥有的普通
   桶空则回落到另一个桶；两个都空返回 null（全图鉴集齐）
3. 桶内仍用现成的 pickWeighted 按稀有度权重抽
```

`SHINY_CHANCE = 1 / 16`。

**「不出重复」的铁律照旧成立**——两个桶都只装未拥有的条目。

这套的节奏是自洽的，值得写清楚：前期普通桶还有货时，闪光按 1/16 稀疏地撒进来（82 只普通抽完约需 87 次捕获、约 35 天，期间约出 5 只闪光，够惊喜）；普通桶抽空之后所有掷骰都回落到闪光桶，**后 33 天变成纯闪光收集期**。合计约 **68 天**，正好对上卡册那个两个月的节奏。

⚠️ 由此可知 `SHINY_CHANCE` **只控制前期的惊喜密度，不控制总时长**——总时长由 164 这个总量和获取速率决定。想让闪光更稀有就调小它，不会因此拖长整体周期。

### 5.3 视觉：统一金色微光，不用 per-monster 色相旋转

`MonsterImage` 加一个 `shiny?: boolean` prop，命中时叠加统一的金色微光 + ✨ 粒子。

**刻意不用 `hue-rotate`**：82 只怪配色各异，同一个色相旋转角度会在其中一部分身上产出难看甚至看不清的结果，而且没法逐只调。统一的加亮 + 描边发光可预期得多，对像素风（神庙）和插画风（太空/森林）都成立。

### 5.4 图鉴呈现：数据两行，界面一格

图鉴**仍是 82 格**。拥有闪光的格子右上角挂 ✨ 角标，点开的放大弹窗里能看两态（普通/闪光切换）。

进度改成两个数：`82/82 图鉴 · ✨ 17/82`。`getDexProgress` 因此要多返回一个 `shinyOwned`。

**不把闪光铺成 164 格**——同一张图并排出现两次，观感是重复而不是丰富。

### 5.5 闪光不进训练轮换（YAGNI）

要进的话得给 `StageProps` 再加一个字段，还要回答「同时拥有普通与闪光时训练里显示哪个」。本轮只在图鉴呈现；她真喜欢再说。

由此得一条必须守住的性质：**`pickCapture` 返回的闪光条目不能污染既有的轮换池逻辑**。现有 `getOwnedReserveIdsByWorld` 与 `buildEnemyPool` 都按 `MONSTER_DEFS` 的 id 匹配，而闪光 id 不在 `MONSTER_DEFS` 里，所以天然被忽略——**这一点由测试锚住，不靠巧合**。

## 6. 出图规格

**共 4 张**：3 张 4×4 怪兽网格 + 1 张森林背景。闪光变体**不需要任何新图**。

### 6.1 ⚠️ 怪兽必须透明背景（与卡片正好相反）

怪兽要抠出来叠在皮肤的动态场景上，任何烘焙进去的背景都会带一块难看的方块。卡片则相反（满幅插画）。`docs/怪兽出图提示词.md` 开头已有这条互斥提示。

### 6.2 怪兽仍用 4×4，不跟卡片走 2×2

理由是**显示尺寸不同**：

| | 最大显示 | 视网膜物理像素 | 4×4 单格 256px 需拉伸 |
|---|---|---|---|
| 卡片 | 240 CSS px | 480 | 1.9×（太软，所以卡片改了 2×2） |
| 怪兽 | 160 CSS px（图鉴弹窗） | 320 | **1.25×（够用）** |

用 2×2 出 48 只要 12 张图，不划算。

### 6.3 三张网格各自匹配所在世界的既有画风

- forest：柔和插画（同卡册）
- space：半写实科幻游戏美术
- shrine：**16-bit 像素风**——这张风格漂移风险最高。**已明示接受**：真漂了就只当低频储备怪出现，影响可控，不为它返工。

## 8. 测试

- `monster-defs.test`：总数 82；分世界 33/33/16；稀有度分布；id 全局唯一；**id 不含冒号**（同步 uuid 反解依赖，monster 是 KEYED_KIND）；`WORLDS` 与实际出现的世界集合一致
- `dex-service.test`：`byWorld` / `byWorldTotal` / `getOwnedReserveIdsByWorld` 三个 Record 的键恰为 `WORLDS`（锚住"从 WORLDS 派生"而不是硬编码）
- `registry.test`：4 套皮肤；`skinUnlockCost('forest') === 4000`；解锁边界
- **新不变量**：`SKINS` 里每个非 `plain` 的皮肤 id 都必须在 `WORLDS` 里。这是 `capturedByWorld[effectiveSkinId]` 能成立的前提，也是替换掉那条静默失效的三元链之后该锚住的东西
- `ForestStage.test`：池轮换（`spiritForSeq`）、储备门控（未捕获不进池）——照 `ShrineStage.test` 写
- `i18n.test`：森林与新怪名的键在 zh / en 都齐全

闪光变体（§5）：

- `monster-defs.test`：`shinyIdOf` / `isShinyId` / `baseIdOf` 三者互逆；**闪光 id 不含冒号**；`baseIdOf(shinyIdOf(x)) === x` 对全部 82 只成立
- `capture.test`：两个桶各自只出未拥有的；一个桶空时回落到另一个；**两个都空返回 null**；`SHINY_CHANCE` 固定 rand 下的分流正确
- **关键隔离断言**：闪光 id **不在** `MONSTER_DEFS` 里，因此 `getOwnedReserveIdsByWorld` 与 `buildEnemyPool` / `buildGuardianPool` / `buildSpiritPool` 拿到一堆闪光 id 时**结果与不传它们完全相同**。这条锚住 §5.5 那个"天然被忽略"的性质——它现在是对的，但它是**巧合式正确**（靠 id 匹配不上），没有测试的话，将来谁把匹配改成前缀或模糊匹配就会让闪光怪混进训练轮换
- `dex-service.test`：`getDexProgress` 的 `shinyOwned` 只数闪光行、`owned` 只数普通行，两者互不串

## 9. 明确不做

- **降低获取速率**（彩蛋每日上限调小、允许重复捕获）——问题是"没内容了"，让孩子等不会把乐趣还回来；重复捕获的挫败感在卡册那一轮已经明确拒绝过
- **在 `MonsterRow` 上加 `shinyAt` 字段**（见 §5.1，会被同步的整行取最早语义静默吃掉）
- **把闪光铺成 164 格图鉴**（见 §5.4，同一张图并排两次是重复不是丰富）
- **闪光进训练轮换**（见 §5.5）
- **per-monster 色相旋转**（见 §5.3，82 只配色各异，统一角度必然翻车一批）
- **森林皮肤的动画角色**（见 §4.4）
- **给太空/神庙加新的普通怪**（见 §3.1，会造出训练里永不出现的怪）
- 为像素风漂移返工（见 §6.3）

## 10. 实施顺序

**阶段一 · 世界派生化重构（不依赖美术，可独立验收）**

`World` 加 `'forest'`、导出 `WORLDS`（**三个世界一次加齐**）、6 处硬编码改派生、`MonsterImage` 加缺图回落、相应测试。

一次把 `'forest'` 加进类型与 `WORLDS`、而不是等阶段三再加，是为了**只触碰这批文件一次**。此时 forest 还没有任何 monster def，于是：`byWorld.forest === 0`、`monstersOfWorld('forest') === []`、图鉴里多一个空分组。空分组在有数据之前是难看的，所以 `DexWall` 渲染时**跳过 `monstersOfWorld(w).length === 0` 的世界**——这条顺带让将来加世界时"先加类型、后补数据"永远安全。

**阶段二 · 出图（用户交付物）**
4 张图。

**阶段三 · 接入**
48 条 monster defs + `ForestStage` + registry + i18n + 测试。

**阶段四 · 闪光变体（§5，可独立上线、也可随时喊停）**

`SHINY_SUFFIX` 与三个 id 纯函数 → `pickCapture` 改两步掷骰 → `captureMonster` 按结果拼 id → `MonsterImage` 的 `shiny` prop → `DexWall` 的 ✨ 角标与放大态切换 → `getDexProgress.shinyOwned` → 测试。

**不依赖前三个阶段**（前三阶段只是让它作用在 82 只而不是 34 只上），所以如果实测发现扩池已经够用、或闪光观感不佳，这一阶段可以整个不做，前面三阶段的价值不受影响。

⚠️ `pickCapture` 的返回类型会从 `MonsterDef | null` 变成 `{ def, shiny } | null`，调用方 `captureMonster` 与既有 `capture.test` 的断言要跟着改——这是阶段四唯一一处会波及既有代码的地方。
