# 视标自适应 设计文档

**日期**：2026-07-29
**状态**：已与用户逐节确认

## 1. 背景

闺女的训练记录同步到云端后，第一次拿真实数据看，发现**「建议调小视标」这个功能其实已经存在，而且一直在触发，但从没被执行**。

`src/stats/weekly-report.ts` 在本周正确率 ≥90% 时给出 `suggest.highAccuracy`（"正确率很棒 👍 可以把视标调小一点"）。她 2026-07-11 至 07-28 的 30 节训练里，**28 节正确率 ≥95%、全期 98.5%**，所以这条建议每周都在显示。而视标大小在这 18 天里只被手动调过一次（07-26，0.90 → 0.80mm）。

建议没被执行的原因是可以指认的：

- 它埋在统计页周报卡的一行文案里，家长未必常看；
- 文案先夸奖后行动（"正确率很棒 👍 可以…"），读起来像表扬不像待办；
- 照做需要三步——进设置页 → 展开刻意折叠的「📐 视标与时长（家长设置）」→ 拖滑块；
- 它**没说该调到多少**，家长得自己判断。

所以本迭代要做的不是"增加建议"，是**把建议变成会发生的事**。

### 1.1 一个必须先纠正的医学口径

「正确率 98.5% = 视标太容易」这个推论是不严谨的，本设计不建立在它之上。

调节灵敏度训练的刺激来自**拍子的 ±2.00D**，与视标大小无关。正确率高恰恰说明她成功清晰化了——那正是训练目的。真正的疗效指标是**清晰化所需时间**（反应时间）。

视标大小的作用是另一回事：它决定"看清"这个判据严不严。视标偏大时，孩子可能在**还没完全调节到位**就已经能认出方向，于是"清晰"被提前判定，训练强度打折。理想大小是"必须完全调节才认得出，但完全调节后就认得出"——落在正确率略低于满分的位置，**不是越小越好**。太小就变成受她本身视力上限限制，即 `settings.optotypeHint` 里写的"太小易放弃"。

因此判据必须同时看正确率与反应时间，见 §2。

### 1.2 缺失的医学锚点

`src/exams`（线下验光记录）**一条记录都没有**。她的实测矫正视力才是选视标大小的正确锚点。本设计因此只能用通用值定下限（§3），并在文档里明示这一点：**下次验光后应按实测视力复核 `AUTO_FLOOR_MM`**。

## 2. 触发判据

只用正确率不够，她的数据直接给出了反例：07-11 正确率 95%、07-18 正确率 96%，两天都能过现有的"≥90%"门槛，但那两天的中位反应是 **4024ms 和 4341ms**——答得对但清晰化很吃力，那时候调小视标是帮倒忙。

两个信号必须同时成立：

| 条件 | 阈值 | 常量 | 作用 |
|---|---|---|---|
| 窗口 | 最近 3 个**训练日** | `AUTO_WINDOW_DAYS = 3` | 避免单日状态波动误触发 |
| A · 正确率 | 窗口内**每天**都 ≥95% | `AUTO_MIN_ACCURACY = 0.95` | 十次错不到一次 = 确实不吃力 |
| B · 反应时间 | 三天**日中位数的中位数** ≤2000ms | `AUTO_MAX_REACTION_MS = 2000` | 清晰化够快 = 视标偏大、判据太松 |
| C · 冷却 | 距上次调整 ≥3 个训练日 | `AUTO_COOLDOWN_DAYS = 3` | 一步一观察，不连着往下压 |

三条全满足 → 视标**调小 `AUTO_STEP_MM = 0.1`**（滑块本身的步进），到下限停。

### 2.1 为什么用绝对反应阈值而不是相对值

相对阈值（"比自己上周快 X%"）会追着自己跑：她越快，门槛越严，最终要么永不触发、要么一直触发。而调节灵敏度有生理下限（临床上儿童双眼调节灵敏度约 11 cpm，即每半周期约 2.7 秒），绝对值更稳定、更可解释。2000ms 是可调常量。

### 2.2 判据会自我收敛

这是本设计最好的性质：视标一变小，正确率会掉、反应会变慢，**两道门自己就把调整停在合适的位置**。不需要再定义一个"最优正确率"——那个数没有可靠的医学依据可定。

## 3. 安全边界

### 3.1 只调难，永不自动调简单

自动调整**只朝增加强度的方向走**。这与上一轮「训练完成门槛」把视标大小折叠进家长区的决定对齐——那个折叠是为了防孩子把训练调水，而自动收紧不给孩子任何把训练变容易的通道。要调大只能家长手动。

### 3.2 下限 `AUTO_FLOOR_MM = 0.6`

40cm 距离下的等效视力换算（`acuityFromHeightMm`）：

| 视标 | 等效视力 |
|---|---|
| 0.9mm | 0.65 |
| 0.8mm | 0.73（她当前值） |
| 0.7mm | 0.83 |
| **0.6mm** | **0.97** ← 下限 |
| 0.5mm | 1.16 |
| 0.3mm | 1.94（滑块最小值） |

停在 0.6mm 即正常视力上限。再往下，她就是**受自己视力限制而不是受调节能力限制**，训练退化成猜。手动滑块仍可到 0.3mm，下限只约束自动逻辑。

⚠️ 见 §1.2：有实测矫正视力后应复核此值。

### 3.3 自愈回退

自动调小后观察**接下来 2 个训练日**。某天满足以下任一指标即算**该天破线**：

- 该天正确率 < `REVERT_MIN_ACCURACY = 0.85`（开始蒙了）
- 该天中位反应 > 调整前窗口中位数 × `REVERT_REACTION_FACTOR = 1.5`（清晰化明显变吃力）

**两个观察日都破线才回退**那一步，并进入 `REVERT_COOLDOWN_DAYS = 10` 个训练日的长冷却，防止"调下去→退回来→再调下去"来回震荡。

**为什么是"两天都"而不是"任一天"**——这条由她的真实数据定：07-18 那两节在 22:43 开始，是全期最慢的一天（4341ms），但它是孤立的深夜疲劳日，下一个训练日 07-21 就回到 2547ms。按"任一天即回退"回放，07-17 刚调到 0.7mm 就会被 07-18 单独触发回退，并把之后 4 个训练日全锁在长冷却里；按"两天都"回放则不回退，进度得以继续。为一个疲劳日锁死 10 个训练日是错的。

代价：真正调过头时需要 2 个训练日才被撤销。这个代价明示接受——两个不顺的日子在几周疗程里不构成伤害，而误回退的代价（进度停滞 10 个训练日 + 家长以为功能坏了）更大。

### 3.4 手动优先

家长手动改过大小之后，冷却重新计时（`AUTO_COOLDOWN_DAYS`）。否则家长刚把它调大（比如孩子那天状态不好），自动逻辑第二天又压回去，等于跟家长对着干。

### 3.5 数据可比性

`SessionRow.acuity` 本来就逐节记录当时的视标大小，审计线索是现成的，**不新增字段**。

但统计页的反应时间趋势图会**横跨视标变化**——视标变小后反应变慢是正常的，图上看起来像退步。这与神庙皮肤那次"历史数据与新数据不可比"是同一类问题。本迭代**不做图表标注**（属另一件事），但周报建议文案要说明这一点。

### 3.6 对限时挑战的影响

`ChallengePage` 同样读 `fzp.optotypeSizeMm`，所以视标变小后挑战也变难——这是对的，视标恒为 `毫米 × 标定`。

她的挑战最高分（localStorage `fzp.challengeBest`）会因此不可比，但**刻意不清零**：清零会白白抹掉她的成绩记录，而那个分数本来就是给她自己看的。

### 3.7 明示接受的限制：设备间不同步（2026-07-29 合并前复核订正）

`currentMm`（`fzp.optotypeSizeMm`）与 `last`（`fzp.optotypeLastAdjust`）都存在 localStorage，是**设备本地状态**，不进云同步；判定输入的另一半——sessions——才走云同步。

⚠️ **这比"两台设备看到的证据一样、结论也一样，实际不会分叉"更复杂，原表述与实现不符**：判据**不看 `SessionRow.acuity`**（即那节训练时视标实际有多大），只看 sessions 里的正确率与反应时间。于是手机第一次训练时 `last = null`，冷却直接放行；如果 iPad 那边已经攒了几个训练日"当前尺寸下又快又准"的证据，手机会直接按这份证据收紧一步（哪怕手机本地视标还停在更大的尺寸上），此后两台设备各自独立进入冷却/观察周期。反过来，手机上练出来的"轻松"日子也会原封不动地被 iPad 的判定窗口读到——§2.2 那条"两道门自我收敛"的性质在跨设备场景下是断的。两台设备的 `currentMm` 可以差好几档，且要经过多个训练日才可能重新收敛（如果家长没手动介入的话），不是"真分叉也只差一步 0.1mm"。

**接受这个限制的理由**：今天家里训练主力是 iPad，手机只是偶发场景，风险面小；真出现分叉，家长在设置页能直接看到两边的滑块值、手动对齐。**不为此引入同步。**

## 4. 交互设计

### 4.1 判定时机

一轮训练结束、sessions 落库之后，与怪兽捕获判定同一位置。

**不达标页也要判**——按门槛那一轮定下的口径，"门槛只决定今天算不算完成，不决定训练事实是否被记录"，数据就是数据。结算页的两个分支（达标 / 不达标）都要渲染这张卡。

### 4.2 一个判定，两种呈现

判定逻辑是纯函数，开关只决定它的结果是"直接执行"还是"摆出来等家长按"。

**开关打开（默认）** —— 结算页告知既成事实：

> 👁️ **视标已调小**　0.8 → 0.7mm
> 最近三天又快又准，给你加点难度 💪

**开关关闭** —— 结算页变成一张待办：

> 👁️ **建议调小视标**　0.8 → 0.7mm
> 最近三天又快又准，可以加点难度了
> 　[应用]

关闭态正是对 §1 那个"建议没被执行"问题的正面解决：把建议从周报的一行文案，变成结算页一个**写明目标值、一步完成**的按钮。

回退发生时的文案同理：「👁️ 视标已退回　0.6 → 0.7mm ／ 这两天有点跟不上，先退回一档」。

### 4.3 撤回按钮不放在结算页

结算页主要是**孩子**在看。撤回按钮摆在那里等于给她一条每天一按、把训练调回容易的通道——正是折叠视标大小要防的那件事，而且比展开折叠更好按。

撤回放在**设置页已折叠的家长区**，在「👁️ 视标大小」滑块下方：

> 最近一次自动调整：7-29 从 0.8 调到 0.7mm　　[↩️ 撤回这一步]

孩子看得到"变难了"这个事实（不隐瞒医学参数变更），但改不回去。

**「应用」按钮暴露给孩子则是安全的**，方向不对称：它只会让训练**变难**，孩子不会去按；且她只能应用算法已经认可的那一步，冷却与判据照常约束。

### 4.4 开关

「自动跟随难度」开关放在设置页折叠的家长区，与"最近一次调整 / 撤回"同一张卡。**默认开**。

加这个开关的理由不是灵活性，是安全：**这是一个会自己改变训练强度的医学参数，必须有一个不用重新部署就能停下的闸门**。功能表现不对、或孩子反应不好时，家长应当场能关，而不是等改常量、跑 CI、等设备联网更新。

### 4.5 状态

只存一条"最近一次调整"（从多少、到多少、何时、是收紧还是回退、调整前窗口的基线反应），localStorage 一个键。

**不做完整历史**——`SessionRow.acuity` 里每节都记着当时的大小，要追溯有现成数据，再存一份是重复。

## 5. 实现

### 5.1 一并修复的既有缺陷

`fzp.optotypeSizeMm` 有三个读取点，**全都没有校验**：

```
ChallengePage.tsx:192   Number(lsGet('fzp.optotypeSizeMm') ?? '1')
SettingsPage.tsx:29     v ? Number(v) : 1
TrainingPage.tsx:459    Number(lsGet('fzp.optotypeSizeMm') ?? '1')
```

`Number('abc')` 是 `NaN`，训练页 `heightPx = NaN × pxPerMm` 会让视标直接渲染不出来。这与当初 `readDurationSec` 那个"`'abc'` 让门槛静默全放行"是同一类，`goal.ts` 的 `sanitizeDurationSec` 已给出处理范式。

本迭代要**程序化写入**这个键，脏值后果更严重，故一并收口：新增 `sanitizeSizeMm` 作为唯一出口，三个读取点全部改走它。

### 5.2 新文件 `src/training/optotype-auto.ts`

纯函数，不碰 DOM、不碰 db。

```ts
export const AUTO_WINDOW_DAYS       = 3      // 判定窗口（训练日）
export const AUTO_MIN_ACCURACY      = 0.95
export const AUTO_MAX_REACTION_MS   = 2000
export const AUTO_COOLDOWN_DAYS     = 3
export const AUTO_STEP_MM           = 0.1
export const AUTO_FLOOR_MM          = 0.6    // §3.2 的医学下限
export const REVERT_MIN_ACCURACY    = 0.85
export const REVERT_REACTION_FACTOR = 1.5
export const REVERT_COOLDOWN_DAYS   = 10

export interface OptotypeAdjust {
  from: number
  to: number
  atDate: string                // 训练日，YYYY-MM-DD
  kind: 'tighten' | 'revert' | 'manual'
  baselineReactionMs: number    // 调整前窗口的中位反应；回退判据用
}

export type AdjustDecision =
  | { action: 'none' }
  | { action: 'tighten'; from: number; to: number; baselineReactionMs: number }
  | { action: 'revert';  from: number; to: number }

export function decideOptotypeAdjust(
  sessions: readonly SessionRow[],
  currentMm: number,
  last: OptotypeAdjust | null,
  todayStr: string,
): AdjustDecision

/** 三个读取点的唯一出口：NaN/0/越界一律钳回 [0.3, 2.0]，脏值回默认 1.0 */
export function sanitizeSizeMm(mm: number): number
```

调用点只有一处：`TrainingPage` 一轮结束、sessions 落库之后。

### 5.3 六个必须写进注释、也要被测试锚住的口径

1. **窗口与冷却按训练日算，不按自然日。** 她出去玩 4 天，按自然日算冷却会白白流逝，窗口还会跨过断档去比两周前的数据。
2. **回退判据优先于收紧判据。** 顺序写死，否则刚回退完可能立刻又满足收紧条件。
3. **门槛达标与否不影响判定。** 不达标的日子照样计入——与 `goal.ts` 那条"门槛只决定今天算不算完成，不决定训练事实是否被记录"一致。她 07-13 那天没打卡但有 5 节有效数据。
4. **缺 `avgReactionMs` 的节次不计入**；窗口内有效天数不足 `AUTO_WINDOW_DAYS` → `none`。宁可不调，不瞎调。
5. **先按天取中位、再对天取中位**，不是把所有节次混在一起。单节异常（如 07-26 那节 4916ms）不该带偏整天。
6. **`sanitizeSizeMm` 是唯一出口**，三个读取点全部改走它。

### 5.3.1 精确定义（消除实现分歧）

以下每条都可能被两种方式实现，各自给出不同结果，故写死：

- **训练日** = 有至少 1 条 `SessionRow` 的日期（按 `SessionRow.date`）。不要求当天打卡，不要求达标。
- **训练日序号** = 把全部训练日按日期升序排列后的下标。窗口、冷却、观察期一律按这个序号算差值，**不碰自然日**。
- **冷却判定** = `今日序号 − last.atDate 的序号 ≥ 冷却天数`。上一次调整当天序号差为 0，故 `AUTO_COOLDOWN_DAYS = 3` 意味着"再练满 3 个训练日"才可能再调。
- **`currentMm` 是唯一真相**，`last` 只用于冷却与观察期判定。localStorage 被手工改过、或从备份恢复导致 `currentMm !== last.to` 时，一律以 `currentMm` 为准往下算，不做纠正、不报错。
- **手动改动**写 `kind: 'manual'`，其 `baselineReactionMs` 不参与任何判定（置 0）。它只起"重置冷却"的作用（§3.4）。
- **回退后**，冷却按 `REVERT_COOLDOWN_DAYS` 从回退当日序号起算；且回退记录本身不再触发新的观察期（不会出现"回退也要观察 2 天再回退"）。
- **观察期不足 2 个训练日时**（收紧后只练了 1 天）→ `none`，继续观察。观察期与冷却期可以重叠，但回退优先（口径 2）。

### 5.4 真实数据回放（最强的一条测试）

把她 12 个训练日的 `(日期, 正确率, 日中位反应)` 做成 fixture，断言判定链的完整轨迹：

| 训练日 | 正确率 | 中位反应 | 判定 | 视标 |
|---|---|---|---|---|
| 07-11 | 95% | 4024ms | 数据不足 | 0.9 |
| 07-12 | 97% | 1954ms | 数据不足 | 0.9 |
| 07-13 | 98% | 2176ms | 窗口中位 2176 > 2000 | 0.9 |
| **07-14** | 100% | 1667ms | 窗口中位 1954 ✓ → **收紧** | **0.8** |
| 07-15 | 100% | 1812ms | 观察中（未破线） | 0.8 |
| 07-16 | 100% | 1719ms | 观察中（未破线） | 0.8 |
| **07-17** | 100% | 1727ms | 冷却满 3 天、窗口中位 1727 ✓ → **收紧** | **0.7** |
| 07-18 | 96% | 4341ms | 破线（>1727×1.5≈2591），观察 1/2 | 0.7 |
| 07-21 | 100% | 2547ms | **未**破线（<2591）→ 不回退 | 0.7 |
| 07-26 | 98% | 1664ms | 窗口中位 2547 > 2000 | 0.7 |
| **07-27** | 98% | 1175ms | 窗口中位 1664 ✓ → **收紧** | **0.6** |
| 07-28 | 97% | 1554ms | 到下限，且观察未破线 | 0.6 |

**终值 0.6mm，三次收紧、零回退。** 这条测试把整个判定链一次性钉死，将来任何人动阈值都会立刻看到后果。

注意 07-21 那行：2547ms 与回退阈值 2591ms 只差 44ms。这个"擦边不回退"正是 §3.3 那条"两天都破线才回退"的实证依据，测试里要单独注释说明，别让人以为是巧合而随手改掉。

### 5.5 其余测试

- 边界：到 0.6mm 不再触发 / 冷却期内不触发 / 缺反应数据不触发 / 回退触发且进 10 天长冷却 / 手动改过之后冷却重算
- `sanitizeSizeMm`：`'abc'` → 1.0、`'0'` → 1.0、`'99'` → 2.0、`null` → 1.0
- 源文本契约：`optotype-auto.ts` 里不出现比 `AUTO_FLOOR_MM` 更小的毫米字面量，防止绕过下限

## 6. 明确不做

- **图表标注视标变化点** —— 属另一件事，本迭代只在周报文案里提示。
- **视标大小纳入云同步** —— §3.7 已说明不需要。
- **按左右眼分别调** —— 弱眼天生慢，分别调等于对最该练的那只眼施加最严标准；与 `goalPerRound` 不做单眼各判是同一个理由。
- **完整调整历史 UI** —— §4.5，`SessionRow.acuity` 已是现成的审计线索。
- **自动调大（放松难度）** —— §3.1，那会给孩子一条把训练调水的通道。放松只能家长手动。

## 7. 遗留风险

1. **下限缺医学锚点。** `AUTO_FLOOR_MM = 0.6` 按通用值（正常视力上限）定，不是按她的实测矫正视力。下次线下验光后应录入 `src/exams` 并复核此值。
2. **2000ms 阈值含设备与作答方式的延迟。** 反应时间是"视标出现 → 答对"，包含语音识别出词或触控的延迟。换作答方式（语音 ↔ 触控/键盘）会系统性平移这个值。她当前主要用什么方式作答未经确认；若日后发现阈值系统性偏移，调 `AUTO_MAX_REACTION_MS` 一处即可。
3. **判据只在一轮训练结束时评估。** 若她某天只练了左眼就退出（如 07-13），该日数据照常计入（口径 3），但当天不会触发判定——判定发生在下一次完整走完一轮时。这是可接受的：判定本来就基于 3 天窗口，延后一次不影响结论。
