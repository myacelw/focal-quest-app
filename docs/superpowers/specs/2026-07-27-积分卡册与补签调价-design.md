# 积分卡册 + 补签调价 · 设计文档

日期：2026-07-27
状态：已获用户批准（6 个关键决策经确认：卡片形态 / 多套随机 / 抽卡手感 / 补签定价 / 卡包定价与套规模 / 第二套主题；三节设计逐节通过）
来源：用户提出两个诉求——①「每月给 2 次补签机会，能不能改成用积分兑换」②「闺女喜欢小马宝莉卡片，能不能用积分换精美卡片，等于内置的兑换内容」。

## 1. 定位

给积分开一个**永久的、不花真钱的出口**：花积分开卡包，抽到的卡收进卡册。同时把补签从「几乎免费 + 次数硬限」改成「真有代价 + 次数兜底」。

**不是**新的训练玩法。卡册不产生任何训练数据、不影响任何医学参数、不进统计。

### 1.1 三个促成本设计的现状事实

1. **补签本来就在花积分。** `REPAIR_COST = 50`。用户以为「每月 2 次」是积分的替代品，实际是叠加在积分之上的额外上限。
2. **那 50 分几乎不构成代价。** `dailyPoints = (答对数×5 + 30) × 连续系数`，系数最高 2.0。按训练门槛每分钟 5 个、6 分钟算，一天保底答对 30 个 → **一天进账 180~360 分**。50 分不到一天的三分之一，真正拦住补签的是次数上限。
3. **积分缺出口。** 现在只有「家长自定义现实奖励」和「补签」两处花分，皮肤解锁走的是*累计*分门槛、不扣分。积分越攒越多而无处可花，激励会失效——用户的直觉是对的。

### 1.2 IP 口径（不可妥协）

仓库是公开的（PolyForm Noncommercial），**不放小马宝莉的官方角色形象或角色名**。卡图是**原创的彩虹小马风格**——独角、翅膀、彩虹鬃毛、糖果配色，是致敬风格而非复制角色。出图沿用 `docs/怪兽出图提示词.md` 那套 4×4 网格流程。

## 2. 关键决策（用户已确认）

| 决策 | 选择 | 理由 |
|---|---|---|
| 卡片形态 | **App 内虚拟卡册** | 「预设实物奖励」今天就能做到（家长在设置页手打一条「卡包 · 200 分」即可，零开发），真正的空缺是不花真钱、在 App 里就能收集的虚拟卡 |
| 套数与随机 | **多套，每套 32 张；兑换时选一套，随机出该套一张** | 加套 = 往数据加一条 + 两张图 + i18n，不动逻辑。首批 2 套（「选一套」这个交互 ≥2 套才成立） |
| 抽卡手感 | **不出重复 + 三档稀有度** | 「练一整天换来一张重复」的挫败会直接反噬训练动机。稀有度几乎免费——`pickCapture` 的权重抽取逻辑已存在且有确定性测试 |
| 补签定价 | **500 分 / 每月 3 次** | 主闸门从「次数」换成「价格」，正是用户最初想要的。500 ≈ 稳定期 1.4 天 / 新手 2.8 天所得 |
| 卡包定价 | **500 分/包，每套 32 张** | 一套 = 16000 分 ≈ 2 个月，出一次图顶两个月；跨越整个「4-6 周见效」疗程 |
| 首批内容 | **2 套：魔法小马 + 深海精灵** | 深海是 CLAUDE.md 里迭代 2 遗留的「深海动物（需先验 vosk）」内容点，做成卡片可绕开 vosk 直接消化掉 |

### 2.1 一处被撤回的论断

设计过程中我曾主张「卡包必须明显便宜于补签，否则积分永远优先流向补签」。**用户指出这不成立，我撤回**：补签是**条件性**支出——只有恰好漏 1 天、且在窗口内才可能发生，一个月最多 3 次；绝大多数日子里孩子根本没有「补签」这个选项可选。它是保险，卡包是日常消费，两者不在同一个消费竞争里。故两者同为 500 分。

### 2.2 「每周 1 次」方案的评估与放弃

用户曾提出「500 分 / 每周 1 次」，后自行改为「每月 3 次」。留档两点结论：

- **「每周 1 次」在频次上比现状更松，与直觉相反**：每月 2 次 = 一个月最多补 2 天；每周 1 次 = 一个月跨 4~5 个周 = 最多补 4~5 天。
- 若将来重提按周计，**必须用滚动 7 天而非自然周**：自然周有真漏洞——周六漏（周日补）＋周一漏（周二补）落在两个自然周，实际 3 天内补了 2 次。

现方案按自然月，直接复用既有的 `monthRepairCount`（按 `monthOf(createdDate)` 计数），无需新增周界逻辑。

## 3. 经济模型

| 项 | 值 |
|---|---|
| 一天进账 | 新手（streak 1-3）约 180~216；稳定期（streak≥11）约 360~460；平均取约 250 |
| 月进账（天天练） | 约 7500 分 |
| 补签 | 500 分，每月上限 3 次 → 上限支出 1500 分/月 |
| 卡包 | 500 分/包 |
| 集齐一套 | 32 × 500 = 16000 分 ≈ 2.1 个月 |

**分层是刻意的**：怪兽图鉴 = 每天的小确幸（免费、打卡必得一只），卡包 = 攒几天的大奖（花分买）。所以卡包单价高到「不能天天开」不是缺陷——即时反馈已经被图鉴占住了，两个系统不打架。

**依从率底线**：补签只能补「恰好漏 1 天」的孤立缺口（`findRepairTarget`），连漏 2 天救不回来。故「每月 3 次」的物理下限是一个月漏 3 天，**依从率锁死在 90% 以上**，不会滑坡。

## 4. 内容与数据模型

### 4.1 卡套定义（纯数据）

新建 `src/cards/card-defs.ts`，形状对齐既有 `src/dex/monster-defs.ts`：

```ts
CardSet { id, nameKey, cards: CardDef[] }
CardDef { id, setId, rarity, nameKey, sheet: 1 | 2, index: 0..15 }
```

`sheet` + `index` 唯一定位一个格子：图路径由 `setId` 与 `sheet` 派生为 `asset('/cards/<setId>/sheet<sheet>.webp')`，`index` 换算成 `background-position`（`col = index % 4`、`row = index / 4 | 0`）。**路径不写进数据**，避免 64 条重复字符串。

首批两套：`pony`（魔法小马）、`deep`（深海精灵）。卡 id 形如 `pony-01` … `pony-32`。

**加一套 = 往数组加一条 + 放两张图 + 加 i18n，不动任何逻辑代码。**

### 4.2 卡 id 硬约束：不能含冒号

同步 uuid 形如 `card:default:pony-07`，而 `naturalKeyFromUuid` 靠「自然键侧不含冒号」反解（取最后一个 `:` 之后）。卡 id 含冒号会让墓碑找不到本地行。由 `card-defs.test.ts` 锚死。

### 4.3 图沿用勋章的宫格方案，不切片

每套 32 张 = **两张 4×4 网格图**（`public/cards/<setId>/sheet1.webp`、`sheet2.webp`），用 `background-position` 定位到格子——正是 `BadgeCard` 现在的做法。

三个好处：①AI 出图产物就是 4×4 网格，**直接用，省掉 64 次切片** ②请求数从 64 降到 4 ③SW 预缓存只多 4 个文件。

**规格：1536×1536 / webp q85**，单卡 384×384。卡册格子（约 96²）与点开放大（约 300²）都够清晰。4 张合计约 2MB（现有勋章两张共 442KB）。这是体积与观感的平衡点；要更清晰就上 2048²/q88，代价是首次装机翻倍、且以后每加一套多 2MB。

图路径一律经 `data/asset.ts` 的 `asset()` 相对化（支持子路径部署）。

### 4.4 稀有度与权重

每套 **普通 18 / 稀有 10 / 闪卡 4**；抽卡权重 **common 65 / rare 28 / epic 7**。

**可验证的性质**（测试锚这个，不锚绝对话）：闪卡权重远低于普通，故**闪卡在抽取顺序上系统性偏后**，集齐路上后段的闪卡密度显著高于前段。这正好对冲「一套要练两个月、中途会腻」的风险。

⚠️ **不要写成「最后 4 张必然是闪卡」**——权重归一化只保证「普通与稀有都抽空后剩下的一定是闪卡」，闪卡本身也可能被早早抽到。若硬要保证，得把闪卡权重压到 0 直到前两档抽空，但那样后 4 张固定是闪卡，孩子会预期，惊喜反而没了。故不做。

### 4.5 新表 `cards`（Dexie v6 → v7）

```ts
CardRow { id: string, obtainedAt: number }   // setId / rarity 都从 defs 派生，不存
```

与 `MonsterRow` 对称（后者是 `id + capturedAt + source`；卡片只有一个来源，不需要 source）。

v6→v7 升级是**纯加空表**，没有存量数据要回填，不触碰 v6 那条「逐行兜底防白屏」的老伤。

## 5. 抽卡逻辑

### 5.1 把加权抽取抽成共用纯函数

`pickCapture` 现在把 `MONSTER_DEFS` 写死在函数体里，卡片要按「套」抽，无法直接调用。而它内部那套逻辑带着一条修过 bug 的注释——**不能复用 `rand` 本身决定池内位置，否则史诗只会抽到池尾**——照抄一份必然漂移（`key-map.ts` 就是因为这个理由从 `TrainingPage` 抽出来的）。

故：抽出通用函数到 `src/data/pick-weighted.ts`，**对档位类型泛型化**——不能让它 import `Rarity`，那个类型住在 `src/dex/monster-defs.ts`，让 `src/data/` 依赖 `src/dex/` 是反向依赖：

```ts
pickWeighted<T, K extends string>(
  remaining: T[],
  tierOf: (t: T) => K,
  weights: Record<K, number>,
  rand: number,
): T | null
```

`pickCapture` 改为调用它（传 `MONSTER_DEFS` 过滤后的池 + 自己的 `Rarity` 权重），`pickCard` 同样调用它。**dex 既有测试必须全绿**，作为这次重构未改变行为的证据。

### 5.2 `pickCard`

```ts
pickCard(ownedIdsInSet: string[], set: CardSet, rand: number): CardDef | null
```

只从**该套**未拥有的卡里抽（跨套互不影响）；该套集齐返回 `null`。

## 6. 账本与开包流程

### 6.1 定价常量各归其位

沿用项目惯例（`REPAIR_COST` / `SKIN_UNLOCK_COST` / `challenge-pace.ts` 都是「改一处即可调价」）：

| 常量 | 位置 | 值 |
|---|---|---|
| `PACK_COST` | `src/cards/pack.ts` | 500 |
| `REPAIR_COST` | `src/rewards/ledger.ts` | 50 → **500** |
| `REPAIR_MONTHLY_MAX` | `src/rewards/ledger.ts`（新增） | **3**，替掉 `canRepair` 里的裸 `2` |

### 6.2 `openPack` 流程

`src/cards/cards-service.ts`，形状对齐 `dex-service.ts`：

1. 读该套已拥有 id
2. 该套已集齐 → 返回「售罄」
3. 可用分 < `PACK_COST` → 返回「不够」
4. `pickCard(...)` 抽一张
5. **在一个 Dexie 事务里**写两张表：
   - `cards.put({ id, obtainedAt: now })`
   - `redemptions.add({ kind: 'pack', title: 'pack', cost: PACK_COST, createdAt: now, createdDate: toDateStr(new Date(now)), status: 'fulfilled', fulfilledAt: now })`
6. 事务提交后 `pushCards` / `pushRedemptions`

`title` 取稳定 slug `'pack'`（与 `repair` 同一约定：存 slug、渲染时才翻译，不存中文串）。**不在 redemption 上记是哪套/哪张**——卡片本身已落 `cards` 表，账本只需要知道扣了多少分。`createdDate` 必须写：它是按月计数的依据（虽然 pack 不占补签次数，但字段是必填的，且将来若要按月看开包量就靠它）。

### 6.3 为什么第 5 步必须是事务

开包同时给卡和扣分。不包事务，中间失败就会「扣了分没拿到卡」——孩子会哭，而且账本对不上没法自动修。push 放事务外，与项目现有「先落库再 push、失败靠 outbox 补扫 + `rescanOrphans` 兜底」的模式一致。

**顺带修 `doRepair`**（用户已同意）：它现在也是 `redemptions.add()` 后跟 `checkins.put()`，没包事务。补签从 50 涨到 500 后，「扣了 500 分却没补上签」从小毛病变成大事故。改动约三行。

### 6.4 `RedemptionRow.kind` 加 `'pack'` 的连锁

逐条核过，多数自动正确：

| 现有逻辑 | 影响 |
|---|---|
| `availablePoints`（只看 `status !== 'cancelled'`） | ✅ pack 自动扣分，不用改 |
| `overspend`（同上） | ✅ 家长端超支提示自动覆盖 pack |
| `monthRepairCount`（过滤 `kind === 'repair'`） | ✅ 开包不占补签次数 |
| `RewardsPage` 历史（过滤 `kind === 'reward'`） | ✅ pack 不进奖励历史——卡册本身就是历史，不新增家长端 UI |

### 6.5 不变量：pack 恒 `fulfilled`，永不可撤销

撤销会退分而不收回卡，等于白得一张。现有代码天然安全（撤销按钮只对 `status === 'pending'` 渲染），但**必须写成测试锚死**，不能靠巧合。

### 6.6 并发

孩子连点两次「开卡包」会并发读到同一个余额。防护只有一条：**按钮在 await 期间禁用**。不做服务层锁——多设备离线各兑换一次导致超支是 3b-2 已明示接受的既有缺口，家长端有「⚠️ 已超支 N 分」提示可人工取消。

## 7. 补签调价的完整改点

不止改常量：

1. `REPAIR_COST` 50 → 500；新增 `REPAIR_MONTHLY_MAX = 3` 并替掉 `canRepair` 里的 `>= 2`
2. `ledger.test.ts` 里 `monthRepairCount: 2` 的 `month-limit` 断言随之改
3. **i18n 参数化**：`repair.monthLimit` 中英两条现在把次数写死在字符串里（`'本月补签次数已用完（每月 2 次）'` / `'No repairs left this month (2/month)'`），改成接 `{max}`，否则改上限时文案会撒谎
4. **更新 `canRepair` 的注释**：它现在的论据是「50 分只相当于 1-2 天打卡分，比认真练一轮还便宜」，涨到 500 后这句不成立。`attempted` 闸门**本身保留**——它的正确理由是语义（补签是为「根本没机会练」设计的），不是价格

**已知的用户可见影响**（可接受）：涨价后头几天孩子余额可能不足 500，补不起签。

| `src/data/api.ts` | 新增 `pushCards`；`pushAllExisting` 的全量补推加一行 |
| `src/data/db.ts` | v7 加 `cards: 'id, uuid'` |

| `functions/lib/admin-stats.ts` | ✅ 无需改，`fillKindCounts` 用 `KINDS` 自动跟随 |

### 8.2 合并取最早，不用 LWW

`card` 走 `EARLIEST_FIELD`，理由与 `monster` 一字不差：「首次获得时刻」才是正确语义，LWW 会留下较晚的 `obtainedAt`。

### 8.3 部署顺序是安全的（但要知道为什么）

`validatePushRecords` 的 kind 白名单是**整批全或无**——一条 `card` 记录能让整批 400，而 400 被 `isPermanentStatus` 判为永久错误。

安全的原因有两条：①Cloudflare Pages 的前端与 Functions 同属一次部署，不会出现「新客户端撞旧服务端」②`engine.ts` 的 `applyPulled` 已防反向（旧客户端 pull 到不认识的 kind 直接忽略）。

⚠️ **本地开发要注意**：改完服务端必须 `npm run build` 才能让 `wrangler pages dev dist` 拿到新的 Functions，否则本地会撞 `bad_kind`。`scripts/test-api.mjs` 里「未知 kind 被拒 400」那条断言用的是 `'evil'`，不受影响。

### 8.4 补一条现在缺的闸门

新增一个测试，**同时 import 前端和服务端的两份 `KINDS` 并断言逐字相等**。现在这个一致性靠两个文件各自硬编码的断言维持，下次加 kind 照样会漏改一边。

## 9. 界面与入口

### 9.1 卡册页 `src/cards/CardAlbum.tsx`

- 两套分组显示；格子布局与稀有度边框沿用勋章墙既有风格
- 未拥有的卡显示剪影
- 每套顶部：进度（`12/32`）+ 一个「开卡包 · 500 分」按钮——**按钮本身就是「选一套」交互**，点哪套开哪套
- 余额不足 → 按钮禁用 + 「再练 N 分」（沿用皮肤锁态的既有表达）
- 该套集齐 → 按钮变「✨ 已集齐」
- 点**已拥有**的卡放大看大图（modal，不做独立路由）；未拥有的剪影点击无反应，不做「未获得」弹窗

### 9.2 入口不进底部导航

560px 手机断点是按「5 项英文导航单行所需 531px」算出来的（见 `src/layout/layout-budget.ts` 与 `css-contract.test.ts`），加第 6 项会让英文导航折行、破掉 3d 迭代刚修好的手机布局。

入口放在**首页与既有「图鉴」入口并排成一行**——图鉴和卡册是同级的两个收藏系统，并排最自然，也不让首页继续变长。`App.tsx` 加一个 View 分支。

**不用 `React.lazy`**：管理页那处 lazy 是因为它低频且要离线可开；卡册是孩子高频入口，省下的首屏解析远不值那点点击延迟。

### 9.3 开包表现

翻卡动画 + 音效分档。普通/稀有沿用现有庆祝音，**闪卡新增一个 `'shiny'` 音效**——理由与限时挑战「超时音不能沿用答错音」相同：界面刚分出的稀有度，若耳朵里是同一个声音等于没分。只加一个，不做三档三音。

### 9.4 i18n

2 个套名 + 64 个卡名 + 约 10 条界面文案，中英各一份，照勋章 30 枚的先例走。卡名 key 形如 `card.pony.07`。

## 11. 明确不做（YAGNI）

- 重复卡与碎片系统（挫败感反噬训练动机）
- 卡片交易 / 赠送
- 家长端开包历史 UI（卡册本身就是历史）
- 卡片详情独立路由（用 modal）
- 三档各自独立音效（只给闪卡加一个）
- 保证「最后 4 张必是闪卡」（见 §4.4）
- 按周计的补签窗口（见 §2.2）

## 12. 前置条件与风险

**前置条件：等「训练完成门槛」分支合并进 master 后，再从 master 起新分支。** 本迭代要改的 `src/rewards/ledger.ts` 和 `src/i18n.tsx` 正是门槛迭代此刻在改的文件（`canRepair` 的 `attempted` 闸门、补签文案），并行动必然冲突。

| 风险 | 缓解 |
|---|---|
| 一套 32 张要练两个月，中途失去兴趣 | 卡册显示进度；闪卡抽取位次偏后使后段密度更高（§4.4） |
| 出图工作量（4 张 4×4 网格 + 128 条 i18n 文案） | 一次出图顶两个月；宫格方案省掉 64 次切片 |
| 涨价是产品行为变更，闺女可能不适应 | 三个常量集中，各改一处即可回退（`PACK_COST` / `REPAIR_COST` / `REPAIR_MONTHLY_MAX`） |
| 首次装机多下约 2MB | 已选 1536²/q85 作为平衡点；不满意可降到 1024² |

## 13. 实施顺序

两块工作量差一个量级，**分两阶段做，补签在前**：

**阶段一 · 补签调价**（小，可独立上线）：三个常量 + `canRepair` 上限常量化 + `doRepair` 包事务 + i18n 参数化 + 注释更新 + 既有测试跟改。不碰 Dexie、不碰同步、不碰资源。做完就有价值——补签从「几乎白送」变成真代价。

**阶段二 · 卡册**：`pickWeighted` 重构 → `card-defs` 与出图 → Dexie v7 + 同步 8 处 → `cards-service` 与事务 → 卡册页与入口 → i18n 文案。

阶段一先落，可以让阶段二的 `RedemptionRow.kind` 扩展建立在一个已经稳定的账本上，两阶段的测试也不会互相干扰。
