## 1. 背景与现状漏洞

### 1.1 现状

一轮训练 = 左眼一节 + 右眼一节（默认各 3 分钟）。右眼节结束后点「完成并打卡 🎊」，`TrainingPage.nextEyeOrFinish()`（`src/training/TrainingPage.tsx:245-272`）依次做五件事：

1. `doCheckIn(today)` → 写 `checkins` 行、算连续天数、发当日积分
2. `syncBadges(now)` → 判定并落库勋章
3. `captureDailyOnCheckin(false, …)` → 当天首次打卡的保底怪兽
4. `newlyUnlockedSkins(prevPoints, totalPoints)` → 跨积分门槛的皮肤解锁庆祝
5. `playSfx('checkin' | 'badge')` → 完成音效

而 `doCheckIn` 的判据只有一条：**今天有没有打过卡**。

```ts
// src/data/checkin.ts:19-42（现状）
export async function doCheckIn(today: string): Promise<CheckinResult> {
  const existing = await db.checkins.get(today)
  if (existing) { return { alreadyCheckedIn: true, … } }
  const todaySessions = await db.sessions.where('date').equals(today).toArray()
  const correctToday = todaySessions.reduce((sum, r) => sum + r.correct, 0)
  …
  const dp = dailyPoints(correctToday, streak)   // ← correct=0 时仍有 30 分打卡奖励
  await db.checkins.put(row)
}
```

### 1.2 漏洞

**只要时间到就算完成。** 把 iPad 架在桌上、一个字不答，两节各 3 分钟走完，照样：

- 打卡成功、连续天数 +1
- 拿到 `dailyPoints(0, streak) = floor(30 × coef) ≥ 30` 分（`src/data/points.ts:7` 的 `+30` 是打卡奖励，与答对数无关）
- 拿到当天保底怪兽
- 解锁当天的限时挑战（`challengeUnlocked = checkedInToday`）
- 累计积分可换**现实奖励**与**补签卡**（`src/rewards/`）

也就是说，整套坚持引擎的货币可以靠挂机凭空印出来。这不只是"作弊"问题——**打卡数据是家长判断"孩子有没有在练"的唯一信号源**，被污染后连续天数与周报都失去意义。

### 1.3 为什么现在能修

`correct`（答对数）已经逐节落库在 `SessionRow.correct` 里，`doCheckIn` 本来就在算 `correctToday`。**判据的数据早就有了，只是没人用它做闸门。** 这也正是 CLAUDE.md 关键决策 #3 那句"靠『答对率=真调节看清』这一天然逻辑保障有效性"的落地——答对是软件唯一能验证的"她真的透过拍子看清了"。

## 3. 门槛数值与推导

### 3.1 数值

**判定用的只有一个数：一整轮（两眼合计）的门槛。**

```
整次（一轮）门槛 = round(单眼时长分钟数 × 5) × 2 只眼，单眼部分下限 5
```

| 单眼时长 | 一整轮时长 | **整次门槛（唯一判定用的数）** | 中间量·单眼折算 | 相当于 |
|---|---|---|---|---|
| 1 分钟 | 2 分钟 | **10** | 5 | 12 秒/个 |
| 2 分钟 | 4 分钟 | **20** | 10 | 12 秒/个 |
| 3 分钟（默认） | 6 分钟 | **30** | 15 | 12 秒/个 |
| 5 分钟 | 10 分钟 | **50** | 25 | 12 秒/个 |

> ⚠️ 「单眼折算」那一列**只是算式的中间量**（`goalPerEye`），**从不单独参与判定**——没有任何一处会拿它去比某一节的答对数。判定永远是「当天累计答对 ≥ 整次门槛」（§4）。文档、代码注释、文案里凡是提到"门槛"的地方，说的都是右边那个整轮数。

### 3.2 为什么是 5 个/分钟（= 12 秒一个）

门槛判定的是**「有没有真练」，不是「练得好不好」**。所以数值刻意压到"认真练的孩子闭着眼都超"的量级：

- 一个循环 = 看清视标（1-3 秒）+ 报答案 + 翻拍过渡（`fzp.flipMs` 默认 900ms，最慢档 1500ms）≈ **2-5 秒**。
- 交叉印证：限时挑战的节奏基准（`src/challenge/challenge-pace.ts`）把孩子的中位反应时间钳在 `[750, 3000]`ms，即最慢也就 3 秒。
- 所以 3 分钟档**一整轮（左右两节共 6 分钟）**的现实产出是 **80-160 个答对**，门槛 30 只要求其中的 **~20-35%**。

**12 秒/个 = 只有连"三分之二的时间在发呆"都做不到的人才会被拦。** 挂机（0 个）被拦得干干净净，而"今天状态差、一整轮慢吞吞答了 40 个"的孩子完全无感。

两眼合计判还额外买了一层保险：**某只眼状态差（比如弱眼那节只答对 8 个）时，另一只眼的产出可以把它带过去**，不会因为半轮失常就让整次白练。

### 3.3 为什么不惩罚慢的孩子（医学理由，不可动摇）

调节灵敏度差的孩子本来就慢——**而那正是最需要训练的那一个**。若门槛按速率（CPM / 每分钟答对率）设计，等于对最需要练的孩子施加最严的门槛，与训练目标完全相反。

所以：

- **门槛按时长等比缩放**（练得短要求就少），不是固定值；
- **数值定在现实产出的 20-35%**，留出巨大余量；
- **不看正确率、不看反应时间、不看 CPM**——那些是"练得好不好"，属于统计页与家长周报的职责，绝不进门槛。

> ⚠️ **实测校准口径**：若闺女真被误伤（认真练却不达标），改 `src/training/goal.ts` 的 `GOAL_CORRECT_PER_MIN`（5 → 3 或 2）一处即可，不要去改判定逻辑、也不要引入"正确率豁免"之类的分支。设为 0 即全放行（等价于回退本功能）。

### 3.4 脏 `durationSec` 的兜底（堵住"静默全放行"）

`fzp.durationSec` 是无校验的 localStorage：`Number('abc') = NaN`、`Number('0') = 0`。若门槛直接按它算，NaN 会让所有比较为 `false`（门槛静默失效、全放行），0 会让门槛变 0（同样失效）。

因此门槛模块提供**唯一的时长读取口** `readDurationSec()`，内部先钳制：

```
不是有限数 或 ≤ 0  → 取默认 180 秒
否则              → 钳到 [60, 300]（= 设置页四个档位的上下界）
```

`TrainingPage` 原来的私有 `readDurationSec()` 与 `DURATION_SEC = 180` **删除**，改为从门槛模块 import。这样"训练实际跑多久"和"门槛按多久算"**永远是同一个数**，不可能错位。

### 3.5 门槛按「当天真实练过的时长」算，不按事后改的档位 ⚠️ blocker

> 评审 blocker #1 拦下的洞。**必须原样实现**，否则整个门槛形同虚设。

`fzp.durationSec` 就是设置页「⏱️ 单眼时长」那四个按钮（`src/SettingsPage.tsx:110-119`），而「⚙️ 设置」在常驻导航里（`src/App.tsx:38` 的 `NAV`），**孩子随手就能点**。若门槛完全派生自"当前设置值"，两个方向都会错：

- **追溯降门槛（真漏洞）**：3 分钟档练完一轮只拿到 12 个（门槛 30）→ 点一下「1分」→ 门槛立刻变 10，而 `correctToday` 里那 12 个照样算 → 下一次 `doCheckIn` 直接打卡成功。等于 **2 分钟挂机 + 1 次点击买回打卡**。
- **追溯抬门槛（误伤家长）**：家长中途把 1 分改成 5 分 → 门槛从 10 跳到 50，当天已经练过的轮次全部作废。

当日门槛必须是一个**稳定的数**。所以时长取数硬定为：

```
当天有 session 行 → 取「当天全部 session 里最长的那一节 elapsedSec」
当天没有 session  → 取当前设置（经 sanitizeDurationSec）
```

为什么 `elapsedSec` 靠得住：`saveSession` 只在 `phase === 'finished'` 时落库，而 `tick()`（`src/training/session.ts:73-74`）到点时把 `elapsedSec` 钳成 `durationSec` —— 所以它**精确等于那一节当时的档位**，事后改设置改不动它。取 **max** 而非 min/平均：一天里既练过 3 分钟节又练过 1 分钟节时按最长的那节要求，避免"先长后短"稀释门槛。

同一算法必须**同时用在三处**（否则又是两把尺子）：`doCheckIn`、`getHomeStats`、以及补签闸门对过去某一天的判定（§5.6）。实现集中在 `goalForDay()` / `goalForPastDay()` 两个纯函数（§6.1）。

> **另一半：练之前就把档位钉在 1 分钟（本次已做降低可达性处理，见 §7.7）。** 孩子若一直用 1 分钟档，每天只需 10 个答对即可续连续天数、拿分、拿保底怪。这**不是本次改动引入的**——今天在完全没有门槛的情况下，把单眼时长从 3 分改成 1 分就已经直接把训练量砍到 1/3，属于"设置页对孩子开放"的既有问题。本设计分两半处理：**①「事后改档追溯降门槛」是真漏洞，用上面的 `goalForDay` 修死；②「练之前就调低档位」这条路用户拍板走"降低可达性"**——把「单眼时长」与「视标大小」挪进已有的 `<Collapsible>`（§7.7），孩子不会随手碰到、家长展开即可。**明确不做家长口令**（§10）：折叠是可达性，不是权限闸门，孩子展开一样能改——这是已知且接受的。

## 4. 判定口径：两眼合计（用户拍板）

### 4.1 结论

**两眼合计判**：一整轮训练（左眼一节 + 右眼一节）的**总答对数**达标即算完成。判据是

```
当天全部 sessions 的 correct 之和  ≥  整次门槛（= 单眼折算 × 2，按当天真实练过的最长一节算，见 §3.5）
```

**判定只发生在右眼节结束、点「完成这一轮 →」那一次**（§4.4）。左眼节结束不判、照常进右眼。

### 4.2 为什么不按单眼各判

| 角度 | 单眼各判 | **两眼合计判 ✅** |
|---|---|---|
| 挡挂机 | 能挡 | **同样能挡**（整轮挂机合计必为 0） |
| 弱眼 | 弱眼天生慢 → 对最该练的那只眼施加最严标准，**与医学目标相反** | 弱眼可被强眼"带过"，**某只眼状态差不该让整次白练** |
| 误伤代价 | 右眼最后 30 秒走神 → **整轮作废，要重练 6 分钟** | 只要总量够就通过 |
| 与发分口径 | 门槛按单节、发分按全天求和 → **两把尺子**（`checkin.ts:29-30`） | **同一把尺子** |
| 实现 | 要在每节末各查一次库、各判一次，还得决定"左眼不达标要不要拦着不让进右眼" | 与 `doCheckIn` 既有实现天然吻合，**一行取数都不用新加** |

后两行是决定性的：`doCheckIn` 本来就在用 `db.sessions.where('date').equals(today)` 求和算 `correctToday` 来发分。两眼合计判**直接复用这同一个数**——判定与结算从此是同一把尺子，"左眼达标右眼不达标 → 拦下打卡，但换个路径打上卡后不达标那节的分照拿"这类自相矛盾整类消失。

> 📌 **勘察风险 #1「门槛判本节、发分算全天 → 两把尺子」因改用两眼合计而自动消解**，不需要任何额外代码。它原本是"单眼各判"方案下才会出现的问题（§9 风险表 #1 已相应改写）。

### 4.3 为什么判据是"当天累计"而不是"本轮两节"

用当天累计（而非只看刚练完这两节）带来三个好处：

1. **一天练两轮的语义自然正确**：第一轮合计 18（差 12）→ 不达标；再练一轮拿到 20 → 当天 38 ≥ 30 → 打卡成功。孩子"再来一轮就能完成"的直觉与实现完全一致，这正是重来按钮成立的基础。

   ⚠️ 顺带修正一处既有口径的**前提**：`src/sync/reconcile.ts` 的注释写着"一天练两轮时 `doCheckIn()` 第二轮直接短路返回，当天分只按第一轮结算"。加门槛后这句仍然成立，但**短路的前提变成了"今天已有打卡行"**——第一轮不达标时压根没写行，第二轮当然要重算。

   **这带来一条本次改动新引入的发分不对称，必须显式记账**（评审 major #5；`dailyPoints = floor((答对×5 + 30) × coef)`，`src/data/points.ts`）：

   | 同样练两轮（streak=1 → coef=1.0） | 计入当日结算的答对数 | 当日积分 |
   |---|---|---|
   | 第一轮 40（**过**门槛 30）→ 第二轮 40 | 只有第一轮的 40 | `floor(40×5+30)` = **230** |
   | 第一轮 29（差 1 个）→ 第二轮 40 | 两轮合计 69 | `floor(69×5+30)` = **375**（**+63%**） |

   方向是"多练**只有先失败才**发分"，而积分能换现实奖励与补签卡（50 分/次）。所以这里**不再只写一句"这不是漏洞"**，而是明示为待用户拍板的产品取舍：

   - **支持保留现状**：每一个答对都是真答对；要吃到这个差价必须先坐满 6 分钟故意不答（29 个意味着三分之二时间在发呆），再认真练 6 分钟，总成本 12 分钟；而"练两轮、第二轮白练"本来就是既有行为，不是本次引入。
   - **若用户不接受**：`goal.ts` 提供 off-by-default 的封顶开关 `POINTS_CORRECT_CAP_FACTOR`（`0` = 不封顶 = 现状），`doCheckIn` 里用 `pointsCorrect(correctToday, goal)` 过一道即可。⚠️ **评审建议的 `factor = 2` 会严重误伤诚实训练**：按 §3.2，3 分钟档**一整轮**的现实产出是 80-160 个答对，而整次门槛只有 30 —— 封在 `2×30=60` 会把诚实一轮的当日积分从 430-830 砍到 330。真要封顶，factor 应取 **6** 左右（3 分钟档 → 180，高于一轮的现实上限），只削掉"叠加两轮"那部分。
   - **绝不能**改成"重算 dailyPoints"：那条"一律沿用行内原值"是 `reconcile.ts` 写死的硬口径，动它会让补签过的日子白涨可换现实奖励的货币。`reconcile.ts` / `reconcile.test.ts` 本次一个字不改。
2. **和 `dailyPoints` 同源**（§4.2）。
3. **门槛不随练的轮数上涨**——它是"今天最低要练到这个量"，不是"每轮都要达标"。

⚠️ 反过来要显式确认一个边界：**「今天已经打过卡」的短路必须排在门槛之前**。否则第一轮达标打了卡、第二轮又练（这次合计不够）时，会被门槛误判成"打卡失败"，把已经到手的连续天数吓没。判定顺序硬定为：

```
已有今日打卡行？ → 'already'（原样返回既有行，门槛不参与）
    ↓ 否
当天累计答对 < 门槛？ → 'below-goal'（不写库、不发分）
    ↓ 否
正常打卡 → 'checked-in'
```

### 4.4 判定时机：只在右眼节结束那一次

由「两眼合计」直接推出——门槛是**一整轮**的，所以一轮只判一次：

| 时刻 | 行为 |
|---|---|
| 左眼节计时走完 | 落库这一节的 session（照旧）→ 显示「本节完成 → 换右眼继续」。**完全不判门槛**，不查累计、不提差额 |
| 右眼节计时走完 → 点「完成这一轮 →」 | 落库 → 调 `doCheckIn`（**唯一的判定入口**）→ 按 `outcome` 分流到打卡页 / 不达标页 |

也就是说 `doCheckIn` 的调用点一个都没变（还是 `nextEyeOrFinish` 里 `session.eye !== 'left'` 那一支），本设计只是在它内部加了闸门。左眼那一节即使一个都没答对，也照常进右眼——**"半途拦截"是明确不做的**：它既挡不住挂机（挂机的人本来就不在乎），又会把"左眼状态差"直接变成惩罚。

## 5. 不达标时各条链路怎么处理

一条贯穿全篇的原则，先写在这里：

> **门槛只决定「今天算不算完成」（打卡 / 积分 / 连续天数 / 保底怪 / 挑战解锁），
> 不决定「训练事实是否被记录」（session 落库 / 统计 / 勋章累计）。**

### 5.1 session：照常落库、照常推云 ✅

**决定：不达标的 session 仍然 `saveSession()` 落库并 `pushSession()` 推云，一个字不改。**

四条理由：

1. **它是发生过的事实。** 孩子确实坐在那里练了 6 分钟，只是量不够。删掉它等于篡改记录。
2. **不落库会让"再练一轮就够"直接失效**——判据是当天累计，第一轮的答对数必须留在库里（§4.3）。
3. **落库时机改不动。** 落库发生在 `session.phase === 'finished'` 的 effect（`TrainingPage.tsx:122-137`），**早于孩子点任何按钮**。要"不达标不落库"就得引入"先缓存整轮、结算时才批量写"的状态机，复杂度陡增且极易漏写。
4. **家长周报要能看见"练了但没练够"**——那才是真实信号。

代价（明示接受）：

| 代价 | 处置 |
|---|---|
| 统计页日/周/月「次数」会 +1 | 不改。统计的语义是**训练量**，不是完成度。见 §5.8 |
| 管理后台 DAU/记录数把这天算活跃 | 不改。DAU 的语义是"有没有打开练"，用于看留存，比"有没有练够"更合适。见 §5.7 |
| 勋章可能在不打卡的日子解锁 | 有意为之。见 §5.4 |

### 5.2 打卡行：不写 ❌

`db.checkins` 当天不写行。因为 `pushCheckin()` 只在 `db.checkins.put()` 之后调用，**"不写行"天然等于"不推云"**，无需任何额外处理。

### 5.3 积分与连续天数：不发、会断 ❌

- **积分**：`dailyPoints` 返回 0，`totalPoints` 原样返回既有累计。
- **连续天数**：checkins 无今天行 → 明天 `nextStreak` 归 1。**这是门槛真正的牙齿**，不做任何缓冲。
- ⚠️ `reconcileCheckins`（`src/sync/reconcile.ts:39`）只重排**已存在的行**，**不会**为缺失日补行——所以断了就是断了，多设备同步也修不回来。这一点必须在结算页文案里讲清楚（§6）。
- 但**当天仍可挽回**：只要在今天结束前把累计答对练够，照样打卡、连续天数照样接上。文案要突出这一点，而不是让孩子以为"今天已经完了"。

**返回值的安全不变式**（有单测锚定）：不达标时必须满足

```
dailyPoints === 0  且  totalPoints === 既有累计（last?.totalPoints ?? 0）
```

这样即使调用方不小心走了皮肤解锁的推导路径，`prevPoints = totalPoints - dailyPoints === totalPoints`，`newlyUnlockedSkins(x, x)` 必然返回空数组，**不可能误弹「🎨 解锁新皮肤」**。

### 5.4 勋章：照常解锁落库，但不庆祝 ⚠️

**这一条最需要解释，因为它是全篇唯一"不达标却仍发生"的奖励。**

事实：30 枚勋章里只有 10 枚 streak 类读 `checkins`，另外 **20 枚**（sessions-1/5/10/25/50/100/200、time-30m/2h/10h、cpm-6/8/10/12/15、acc-90、acc-100、correct-100/500/1000）全部读 `sessions`（`src/badges/stats-derive.ts:13-22`）。

三个选项都试过一遍：

| 选项 | 问题 |
|---|---|
| (a) 不达标不调 `syncBadges` | 勋章判定被推迟到下次打卡 → `unlockedAt` 记成错误的日期。而 CLAUDE.md 白纸黑字："**勋章/怪兽取最早**——首次达成时刻才是正确语义"。为了 UI 观感去污染数据语义，不划算 |
| (b) 照常调、照常弹庆祝 | 「今天没完成」页面上弹「🎉 解锁新勋章！」+ 庆祝音效，信息直接打架 |
| (c) **照常调、落库，但只低调提示、不放完成庆祝** ✅ | 采纳 |

**采纳 (c)。** 理由：勋章衡量的是**跨天累计的训练成果**（练满 10 次、CPM 15、正确率 100%），它的判据本来就来自 `sessions` 而不是"今天完成了没"。不达标那节是**真练的**，它贡献的 `totalSessions` / `totalCorrect` 都是真实数据，凭什么不算？

落地：

- `syncBadges(Date.now())` **照常在整轮结束时调用**（不达标分支也调）→ 判定不延迟、`unlockedAt` 真实。
- 不达标页**不显示**「🎉 解锁新勋章！」大卡片，改为一行低调文案「🏅 顺便解锁了新勋章，去勋章墙看看～」+ 勋章名。
- 音效：不达标时**不放**任何完成音（`'checkin'` / `'finish'` 都不放）；仅当确有新勋章时放 `'badge'`（那是勋章音，不是打卡音）。

这样既不丢庆祝时刻，也不会让孩子误以为"今天完成了"。

### 5.5 保底怪兽 / 彩蛋怪兽 ❌ / ⚠️

- **保底怪**（`captureDailyOnCheckin`）：**不发**。它明确是"当天首次完成训练打卡"的奖励，不达标分支根本不调它。
- **彩蛋怪**（`captureMonster('egg', …)`）：**已经在答对 5 连的瞬间落库了**（`TrainingPage.tsx:175-187`），与打卡无关。所以不达标日**可能白捡一只彩蛋怪**。

  **明示接受。** 三个理由：①彩蛋是"连对 5 个"的即时奖励，那是实打实的答对，比打卡本身更能证明她在练；②`monsters` 的合并口径是"取最早 `capturedAt`"（`src/sync/merge.ts`），一旦落库无法用 LWW 撤回；③要撤回就得在答题瞬间预测整轮结果，不可能。

- 不达标页**仍会显示**本轮捕获的彩蛋怪开箱区（`capturedThisSession`）——它是真实收获，藏起来反而奇怪。

### 5.6 补签卡：堵死这条付费绕过通道 ❌❌

**这是本设计最重要的一处防漏。**

现状：`findRepairTarget(checkins, today)`（`src/rewards/ledger.ts:55`）**签名里根本没有 sessions**，判据纯粹是 `daysBetween(...) !== 2`（恰好漏 1 天）。`canRepair` 的三道闸门只有 `not-broken` / `month-limit` / `no-points`，**没有任何"那天是不是真的没练"的判据**。

加了门槛之后，"练了但没练够"的日子在 `checkins` 里就是一个纯粹的日期缺口，**和"压根没开 app"完全无法区分**。于是：

> 第二天首页自动弹补签横幅 → 花 **50 分**（`REPAIR_COST`，约 1-2 天打卡分）→ 连续天数原样接回。
> 等于**每天挂机 30 秒 + 50 分买回连续**，门槛完全失效。

**决定：缺口日若「练了但没练够」，则不可补签。**

```
canRepair 的判定顺序（新）：
  没缺口                → 'not-broken'
  缺口日练了但没练够      → 'attempted'      ← 新增，排在第二位
  本月次数用完           → 'month-limit'
  余额不足              → 'no-points'
```

为什么"练了却不能补、没练反而能补"不是反直觉：

1. **门槛失败是当天可挽回的**——重来按钮就在结算页上，再练一轮就完成了（§4.3）。过了当天才变成缺口，那说明她当天选择了不继续。
2. **补签卡的设计意图是"当天根本没机会练"**（生病、外出、忘了）。那是不可挽回的，才需要花分买。
3. 若两者都能补，门槛的成本就是 50 分——**比认真练一轮还便宜**。

⚠️ **判据必须是"那天确实没练够"，不能简化成"那天有没有 session 行"**（评审 major #2 拦下的错）。原先的写法认为「是缺口 + 有 session」⟺「练了但没练够」，**这个"恒等"是错的，而且方向反了**：`saveSession` 只在 `session.phase === 'finished'`（计时走满）时触发（`TrainingPage.tsx:122-137`），所以"那天有 session 行"真正等价的是"**至少完整走完过一节**"。两个反例：

1. 孩子练到 40 个答对（远超门槛 30）却没点右眼末的「完成」按钮就切走 / iPad 被收走 / 页面被 Safari 回收 —— 那天既没打卡行，又因为有 session 行而不可补签。**这恰恰是最该被补的一天。**
2. 中途退出（不满一节）**一行都不落** —— 于是"点开训练马上退出"的日子照样能花 50 分买回连续，而"老老实实练满 6 分钟只差几个"的日子不能。

净效果是把孩子教成「**要么练够，要么干脆别开**」，与坚持引擎的目标正相反，也没真堵住那条 50 分通道。

所以判据是**重算那天的门槛**（用那天 session 的 `elapsedSec` 算，不掺当前设置，见 §3.5）：

```
那天没有 session 行        → 不是 attempted（可补：确实没练）
那天答对之和 ≥ 那天的门槛   → 不是 attempted（可补：练够了、只是没点完成按钮）
那天答对之和 <  那天的门槛   → attempted（不可补：练了但没练够）
```

纯逻辑抽成 `dayFellShort(correctSum, sessionElapsedSecs)`（在 `goal.ts`，见 §6.1），服务层只负责查那天的 sessions 行。`rewards-service.ts → training/goal` **无循环依赖**（`goal.ts` 只 import `data/storage`）。

文案要说清楚（否则家长会当 bug 报）：「昨天练了但没练够——补签卡只能补完全没练的日子」。

### 5.7 云同步：session 照推、checkin 天然不推 ✅

| 路径 | 处理 |
|---|---|
| `pushSession` | 不改。不达标的 session 照常进 outbox 上云（§5.1） |
| `pushCheckin` | 不改。它只在 `db.checkins.put` 之后调用，不写行就不推 |
| 管理后台 DAU / 记录数 | 不改。`records.updated_at` + `kind='session'` 的口径把不达标日算作活跃——这是**对的**，DAU 要衡量的是"有多少家庭今天打开练了" |

**⚠️ 反向路径不受门槛约束（明示接受）：**

- `mergeRecord`（`src/sync/merge.ts`）对 `checkin` 走**纯 LWW**，从云端拉回的打卡行直接写库；
- `restoreBackup`（`src/backup/backup-service.ts:56`）直接 `db.checkins.bulkPut(...)`。

也就是说：**一台还没更新的旧版本设备按老逻辑打了卡、推上云，新版本设备拉回来照样有打卡行。** SW 的更新机制是"联网打开一次才接管"，所以新旧共存窗口真实存在。

止损：家里只有 1-2 台设备，孩子那台联网打开一次即更新。**不做**版本号校验、不做服务端门槛校验（服务端刻意不解析 payload，见 3b-1 设计）。

**定性：门槛是本地写入闸门，不是数据校验器。**

### 5.8 统计与家长周报：零改动 ✅

`aggregate`（`src/stats/aggregate.ts:21`）与 `weeklyReport`（`src/stats/weekly-report.ts:29`）的签名里**都只有 sessions、没有 checkins**。不达标的 session 会照常进日/周/月的「次数」「CPM」「正确率」和周报的「本周练了 N 次」。

**决定：统计与周报一个字不改。** 理由：

- 两者衡量的是**不同维度**：统计 = 训练量（事实），打卡 = 完成度（判定）。首页说"今天没练完"、统计说"今天练了 1 次"，**两句话都是对的**。
- 给统计加"未达标"标记会让图表口径复杂化（要么柱子分色、要么加筛选），而训练量本身没有任何虚假成分。

消除观感冲突的办法是**在第一现场把话说清**，而不是改统计：

1. **不达标结算页**明确写「这一轮的练习已经记下啦，答对数会累加」；
2. **首页加第三态**：既不是"今天练过啦 ✓"，也不是"今天还没练"，而是「今天练了 12/30，再练一轮就完成啦！」。这一条同时也是本次改动里给孩子最正向的驱动。

已知不修（既有问题，非本次引入）：`weeklyReport` 没有 `stats-derive.ts` 那样的 `answered >= 5` 护栏，一节只答 3 题全对会把周报正确率拉高。CLAUDE.md 已有口径"数据是趋势参考非诊断"，留作后续。

### 5.9 限时挑战：当天不解锁 ✅（这是想要的）

`challengeUnlocked(stats)` 就是 `stats.checkedInToday === true`（`src/challenge/challenge-unlock.ts:9`），首页入口卡整卡不渲染（`src/HomePage.tsx:145`）。

门槛拦下打卡 → **当天挑战玩不了**。这不是 bug，是设计：**挑战是训练的奖赏**（30 秒冲分小游戏，本来就锁在"当天练完"之后）。零代码改动。

不在不达标页提挑战（避免信息过载），孩子练够了自然会在首页看到入口卡出现。

| 链路 | 不达标时 | 代码改动 |
|---|---|---|

| session 推云 | ✅ 照常 | 无 |
| checkin 行 | ❌ 不写 | `doCheckIn` 加闸门 |
| checkin 推云 | ❌ 天然不推 | 无 |

| 限时挑战 | ❌ 当天不解锁 | 无 |

## 6. 接口与数据结构变更

### 6.1 新模块 `src/training/goal.ts`

**所有可调数字的唯一出处。** 纯函数 + 一个薄读取包装（与 `src/challenge/challenge-storage.ts` 同构：纯函数负责逻辑、薄包装负责碰 localStorage）。

```ts
/** 单眼时长默认值（秒）——原 TrainingPage 私有的 DURATION_SEC 搬到这里 */
export const DEFAULT_DURATION_SEC = 180
/** 门槛速率：每分钟需答对几个。改这一处即可调松紧；设为 0 等于全放行（回退本功能） */
export const GOAL_CORRECT_PER_MIN = 5
/** 单眼折算的下限（防极短时长算出 0）；整次门槛的实际下限因此是 10 */
export const GOAL_MIN_PER_EYE = 5
/** 时长钳制区间 = 设置页四档 [60,120,180,300] 的上下界 */
export const DURATION_MIN_SEC = 60
export const DURATION_MAX_SEC = 300
/** 一轮训练的眼数（左 + 右） */
export const EYES_PER_ROUND = 2
/** 当日结算的答对数封顶倍数；0 = 不封顶（现状）。见 §4.3 的发分不对称 */
export const POINTS_CORRECT_CAP_FACTOR = 0

/** 把脏 localStorage 值钳成可用秒数：非有限数/≤0 → 默认值；否则钳到 [60,300] */
export function sanitizeDurationSec(sec: number): number
/**
 * **中间量**：单眼折算 = round(分钟 × GOAL_CORRECT_PER_MIN)，不低于 GOAL_MIN_PER_EYE。
 * ⚠️ 它**从不单独参与判定**——没有任何一处拿它去比某一节的答对数（判定口径是两眼合计，§4）。
 * 导出它只是为了让 goalPerRound 的算式可读、可单测。
 */
export function goalPerEye(durationSec: number): number
/** **整次（一轮两眼合计）门槛 = goalPerEye × EYES_PER_ROUND —— 这是唯一判定用的那个数** */
export function goalPerRound(durationSec: number): number

/**
 * 某一天的门槛（§3.5）：当天练过就按「最长那一节的 elapsedSec」，没练过才用当前设置。
 * 唯一出处——doCheckIn / getHomeStats / 补签闸门三处必须都走它。
 */
export function goalForDay(durationSec: number, sessionElapsedSecs: number[]): number
/** 过去某一天的门槛：只看那天真实练过的时长，绝不掺入"现在"的设置 */
export function goalForPastDay(sessionElapsedSecs: number[]): number
/** 那天是不是"练了但没练够"（补签闸门的判据，§5.6）。没练过 → false */
export function dayFellShort(correctSum: number, sessionElapsedSecs: number[]): boolean

/** 还差几个（不为负） */
export function shortfall(correctToday: number, goal: number): number
/** 是否达标 */
export function meetsGoal(correctToday: number, goal: number): boolean
/** 进当日结算的答对数（factor ≤ 0 时原样返回，即现状不封顶） */
export function pointsCorrect(correctToday: number, goal: number, factor?: number): number

/** 薄包装：读 fzp.durationSec 并 sanitize。TrainingPage / HomePage / SettingsPage 共用 */
export function readDurationSec(): number
```

`GOAL_CORRECT_PER_MIN = 0` 时 `goalPerEye` 会被 `GOAL_MIN_PER_EYE` 顶到 5 —— 所以"全放行"的正确做法是把 `GOAL_CORRECT_PER_MIN` **和** `GOAL_MIN_PER_EYE` 都设 0。这一点写进模块注释。

### 6.2 `src/data/checkin.ts`

```ts
/** 打卡结果三态：正常打卡 / 今天已打过 / 答对太少没达门槛 */
export type CheckinOutcome = 'checked-in' | 'already' | 'below-goal'

export interface CheckinResult {
  outcome: CheckinOutcome
  /** 当天累计答对（全部 sessions 求和，与 dailyPoints 同源；**两眼合计**） */
  correctToday: number
  /** 当天门槛（**整次 = 两眼合计**，如 3 分钟档是 30 而不是 15） */
  goal: number
  streak: number
  dailyPoints: number
  totalPoints: number
}

/**
 * durationSec = 刚练完那一节的实际时长，用于按比例算门槛。
 * ⚠️ 它只是**兜底基准**：真正的门槛走 `goalForDay(durationSec, 当天各节 elapsedSec)`，
 * 当天练过就按最长那节算，防"练完再把档位调小"追溯降门槛（§3.5）。
 */
export async function doCheckIn(today: string, durationSec: number): Promise<CheckinResult>
```

**`alreadyCheckedIn: boolean` 字段删除**，由 `outcome === 'already'` 取代——三态用一个布尔表达不了，留着两个字段迟早会不同步。调用点只有 `TrainingPage`（4 处），一并改。
`src/dex/dex-service.ts` 的 `captureDailyOnCheckin(alreadyCheckedIn, …)` **签名不动**（那是它自己的参数，我们照旧传 `false`，只是外层条件从 `!result.alreadyCheckedIn` 变成 `result.outcome === 'checked-in'`）。

不达标分支的返回值：

```ts

  outcome: 'below-goal',
  correctToday, goal,
  streak: currentStreak(lastCk, today),   // 展示用：今天不练完就会归零的那个数

  totalPoints: last ? last.totalPoints : 0,

```

`streak` 用 `currentStreak`（而非 `nextStreak`）是刻意的：它表达的是"**还没保住**的连续天数"，正好驱动结算页那句「🔥 连续 N 天还没保住，今天再练一轮就能接上」。

### 7.4 设置页时长档位加门槛提示

时长卡片（`src/SettingsPage.tsx` 的 `[60,120,180,300]` 那张）底部加一行灰色小字，随档位实时变：

> 「每天需答对 30 个才算完成（每分钟 5 个 × 3 分钟 × 两只眼）」

这是家长唯一能看到门槛数值的地方，**必须有**——否则孩子说"我练了但没打上卡"时家长完全无从判断。文案里的「× 两只眼」不是修辞，它就是判定口径本身（§4.1）：家长看到的这个 30 与不达标页显示的「需要 30」是同一个数。

⚠️ 这行提示会随时长卡一起被收进 §7.7 的折叠区（它本来就是给家长看的）。家长排查"练了没打上卡"时需要先展开「📐 视标与时长」——这是有意的取舍，见 §7.7。

两个实现细节：

- 提示里的分钟数必须走 `sanitizeDurationSec(durationSec) / 60`，不能直接用 `durationSec / 60`。`goalPerRound` 内部会 sanitize 而除法不会，于是脏 `fzp.durationSec`（`'abc'` → NaN、`'0'` → 0）会让这行显示成「每分钟 5 个 × **NaN** 分钟 × 两只眼」。顺带把 `SettingsPage` 的 `durationSec` state 初值也统一成 `sanitizeDurationSec(Number(lsGet('fzp.durationSec')))`——否则脏值下四个档位按钮还会全都不高亮（`Number(null)` 是 0，被 sanitize 兜成 180，与现状行为一致）。
- 这行说的是**「按当前档位，一天要答对几个」**，不是"今天实际的门槛"。孩子今天若已练过更长的一节，当天真实门槛按那节算（§3.5），会高于这里的数——首页第三态「今天练了 12/50」显示的才是当天真实门槛。两处不矛盾：家长看这行是为了知道"档位对应多少"。

### 7.5 右眼节末的按钮改中性文案

### 7.7 设置页把「影响训练量」的两项折叠起来（用户拍板新增）

**决定：把「⏱️ 单眼时长」与「👁️ 视标大小」两张卡挪进已有的 `<Collapsible>`（`src/settings/Collapsible.tsx`，签名 `{title, defaultOpen, danger, children}`），标题「📐 视标与时长（家长设置）」，默认收起。**

**为什么要做**：门槛按时长**等比缩放**（§3.3 那条医学口径不可动摇——固定门槛会惩罚调节慢的孩子）。等比缩放的代价就是"把单眼时长调到 1 分钟 → 训练量砍到 1/3 → 门槛也跟着从 30 降到 10"。§3.5 的 `goalForDay` 只堵住了**事后**改档追溯降门槛这一半；**练之前就调档**那一半门槛堵不住，也不该靠门槛去堵——那是设置项可达性的问题：「⚙️ 设置」在常驻导航里，孩子随手就能点进去改。视标大小同理（调小 = 变难、调大 = 变简单，且它直接决定训练的医学有效性）。

**为什么是折叠而不是口令**：

| 方案 | 结论 |
|---|---|
| 家长口令 | **不做**（§10）。给家庭自用的 app 加密码是过度设计，家长自己也会忘；真要绕过，清一下 localStorage 就完了 |
| 折叠（采纳） | **成本几乎为零**（组件现成、已有 6 张卡在用），效果是"不会随手碰到"。孩子要改得先想到去展开——那已经是有意为之而不是顺手了 |
| 移出设置页 / 改只读 | 不做。家长要能改，医学参数本来就该随孩子情况调 |

**明确定性：折叠是可达性，不是权限闸门。** 孩子展开一样能改，这是已知且接受的。门槛的真正防线是 §3.5（事后改档不追溯），不是这里。

**落地**（`src/SettingsPage.tsx`，「训练设置」分组内，顺序不变）：

```
📏 屏幕标定             （不折叠——首次必做，藏起来会让新用户卡住）
📐 视标与时长（家长设置） ← 新折叠卡，默认收起
   ├─ 👁️ 视标大小（滑块 + 实时预览 E + 等效视力级别）
   └─ ⏱️ 单眼时长（四档 + §7.4 的门槛提示行）
🔄 翻拍速度             （不折叠——只影响观感不影响训练量，孩子调着玩无所谓）
🥽 拍子度数             （不折叠——软件只记录不参与计算，改了不影响训练量）
🎨 皮肤                 （不折叠——这是给孩子的奖励，本来就该显眼）
```

只挪这两项、其余一张不动，**判据是"改了会不会改变训练量或难度"**：翻拍速度只改节奏观感、拍子度数只是记录（真调节刺激来自物理拍子），孩子随便调都不影响门槛与训练强度。

两处实现注意：

1. **两张内层卡去掉 `className="fq-card"`**，只保留布局样式 + 一条分隔线。`<Collapsible>` 自身就渲染一张 `fq-card`，套娃会出现"卡中卡"的双层圆角与双层内边距。
2. **`defaultOpen` 用默认的 `false`**。给它传 `true` 等于什么都没做。

代价（接受）：家长排查"练了却没打上卡"时要先展开才能看到 §7.4 那行门槛数值。可接受——那本来就是家长动作，而孩子看到的差额在不达标页和首页第三态上都有。

## 8. 「再练一轮」的状态复位

### 8.1 为什么不用 `key` 重挂载

最省事的写法是在 `App.tsx` 给 `<TrainingPage>` 加一个 `key` 让 React 整体重挂载，state/ref 自动归零。**不能这么做**：

`TrainingPage` 卸载时会跑 `useEffect(() => () => { voskRef.current?.stop() }, [])`，而 `vosk-single.ts` 的 `stop()` 会把单例 `current` 清空。重挂载后 `beginSession()` 会重新 `startVosk` → 重新拉 3 个模型分片、拼 60MB Blob、让 worker 重新解压模型。

**这正是 commit `89743b6`「iPad 换眼时白屏退出——vosk 模型并发加载把内存打爆」修过的那条路径。** 为了一个重来按钮去踩它，不值得。

组件不卸载还有个额外好处：语音一直在线，点「再练一轮」立刻能开始，不用再等模型。

### 8.2 复位清单（一个都不能漏）

`restartRound()` 必须逐个复位，漏一个的后果都很隐蔽：

```ts
function restartRound() {
  savedRef.current = false            // 漏 → 新一轮的 session 根本不落库（finished effect 直接 return）
  seqRef.current = 0
  targetShownAtRef.current = 0
  sumReactionRef.current = 0          // 漏 → 上一轮的反应样本混进 avgReactionMs，污染周报趋势
  reactionCountRef.current = 0
  setCheckin(null)                    // 漏 → 一进 finished 就被结算页抢先渲染成旧结果
  setNewBadges([])
  setNewSkins([])
  setCapturedThisSession([])          // 漏 → 上一轮的怪兽会在新一轮结算页再开箱一次
  setLastAnswer(null)
  setComboFx(null)
  setEggCaptureFx(null)
  setPaused(false)
  roundDateRef.current = toDateStr(new Date())   // 漏 → 上一轮若是零点前开始的，新一轮还记在昨天
  setSession(createSession('left', readDurationSec()))   // 从左眼重新开始一整轮
}
```

**刻意不复位**（都是跨轮次仍然有效的东西）：

| 不复位的 | 理由 |
|---|---|
| `capturedByWorld` | 「已拥有的储备怪」，用于扩展皮肤轮换池，与轮次无关 |
| `randomSkinId` | 本次进页已挑定的皮肤，重来沿用更连贯；重掷还会和 `totalPoints` 的加载竞态 |
| `totalPoints` | 只读缓存（皮肤解锁判定用） |
| `muted` / `voskStatus` / `voskRef` | 语音与静音状态跨轮保持 |

这份清单由**源文本契约测试**（`?raw`，仿 `src/challenge/challenge-shell.test.ts`）逐条锚定——本仓 vitest 是 `environment: 'node'`、没有 jsdom，组件渲染测不了，源文本是唯一能自动化的闸门。

### 8.3 为什么重来是"一整轮"而不是"一节"

- **医学上两眼要均衡**：只补练一只眼会让另一只少练。
- **实现最简**：`createSession('left', …)` 与初始状态完全一致，不需要额外的"从右眼开始"分支。
- **对挂机者是正确的成本**（要重新坐 6 分钟），对认真练的孩子根本不会触发（§3.2）。

判据是当天累计（§4.3），所以重来那一轮**不必**自己达标——上一轮的答对数照样算数。

### 8.4 新增 prop

`TrainingPage` 加 `onHome: () => void`，`App.tsx` 传 `() => setView('home')`。这是「回首页」次按钮所需，也是 `TrainingPage` 第一次有 props。

### 8.5 一轮训练用同一个日期（跨零点）

现状 `saveSession` 用**落库时刻**的 `toDateStr(new Date())`（`TrainingPage.tsx:126-127`），`doCheckIn` 也各算一次。一轮训练跨零点时左眼节落到昨天、右眼节落到今天，`correctToday` 只剩右眼那一节（3 分钟档大概率 20-40 个，而门槛是整次的 30，命中率一半一半）。

改动前这只是"当天分少一点"，**改动后可能整轮判 below-goal，而昨天同样没写打卡行**（`doCheckIn` 从未在零点前被调用）→ 两天都没打卡、连续天数直接断，而孩子实际练满了 6 分钟。

**决定：一轮训练锁定一个日期。** 加 `roundDateRef`，在**左眼节开始时**（`beginSession()` 里判 `eye === 'left'`，以及 `restartRound()`）算一次 `toDateStr(new Date())`，`saveSession` / `doCheckIn` / `captureDailyOnCheckin` 三处都用它。这样左右两节必然同日、判定与发分都完整。

代价（可接受）：23:50 开始的一轮整体记到前一天，今天的首页会显示"还没练"。这比"断连续天数"轻得多，而且语义上"一轮训练属于它开始的那天"本身讲得通。

## 10. 明确不做

- **不做速率型门槛**（CPM / 每分钟答对率 / 正确率下限）——会惩罚调节慢的孩子，与医学目标相反（§3.3）。
- **不做单眼各判**（用户已拍板）——某只眼状态差就整轮作废、重罚 6 分钟，会直接毁掉坚持引擎；且判定与发分会变成两把尺子（§4.2）。
- **不做左眼节末的中途判定/拦截**——门槛是一整轮的，一轮只判一次（§4.4）。
- **不做积分补发/重算**——撞 `reconcile.ts` 写死的"dailyPoints 一律沿用行内原值"硬口径；积分是能换现实奖励与补签卡的货币，任何重算通道都会通胀（勘察 risk 17）。
- **不做"不达标不落库"**——事实要记，且当天累计判据依赖它（§5.1）。
- **不给统计图表加"未达标"标记**——统计的是训练量，训练量没有虚假成分（§5.8）。
- **不改管理后台 DAU 口径**——DAU 要衡量"有多少家庭今天打开练了"，比"练够了没"更适合看留存（§5.7）。
- **不做服务端门槛校验**——服务端刻意不解析 payload（3b-1 设计），且家庭规模下没有对抗性作弊者。
- **不做跨会话的"勋章庆祝补偿"**——不达标日解锁的勋章不会在下次打卡时补弹庆祝，静静进勋章墙（§5.4）。
- **不做门槛的家长可调 UI**——改常量重新部署即可，多一个设置项等于多一条被孩子发现的绕过路径。（⚠️ 注意门槛的**时长**基准仍来自已有的「单眼时长」设置项，这是没法避免的——门槛必须随时长等比缩放。防绕过靠 §3.5 的"按真实练过的时长算"，不是靠藏设置。）
- **不加家长口令、不把设置项改成只读**——折叠（§7.7）已经把"随手改"变成"有意去改"，加密码对家庭自用 app 属过度设计，且清一下 localStorage 就能绕过。（「单眼时长」与「视标大小」挪进折叠区**本次要做**，见 §7.7；其余四张卡不动。）
- **不做"离目标还差多少"的实时 HUD**（训练中显示进度条）——会把训练变成刷数量，与"看清了再答"的医学目标冲突。差额只在结算页出现。
- **不改 `weeklyReport` 的短节护栏**（`answered >= 5`）——既有问题，非本次引入，留作后续。
