# 邀请码配额与管理员换码 设计文档

**日期**：2026-07-29
**状态**：已与用户逐节确认

## 1. 背景

用户提出两条需求：**每个邀请码限制最多邀请人数（如 5 人）**、**管理员可以更换自己的邀请码，其他人不行**。

勘察现状后，两条的处境完全不同。

### 1.1 「限 5 人」已经实现了，缺的是可见性

- `migrations/0001_init.sql` 的 `users.invite_quota INTEGER NOT NULL DEFAULT 5`，注释已写明「改为 0 即封停其码」；
- `functions/api/auth/register.ts` 用子查询现算 `used = COUNT(*) FROM users c WHERE c.invited_by = u.id`，`used >= quota` 返回 403 `invite_quota_exhausted`；
- 客户端 `src/sync/account.ts` 的 `authErrorKey` 已映射到 `sync.err.inviteUsedUp`（「这个邀请码的名额用完了」），中英双语齐备；
- 管理后台的邀请排行已经在显示每个账号的 `invited / quota`。

所以本迭代**不新增配额机制**，只补它的可见性：设置页现在只显示一串码和复制按钮，文案含糊地写「额度有限」，**一个数字都没有**。后果是名额用完之前没人知道快用完了，用完之后是亲友那边收到报错，家长一脸茫然。

### 1.2 「换码」完全没有

全仓唯一写 `users.invite_code` 的路径是注册时 `genInviteCode()` 生成一次，此后再无任何写入。客户端那份 `inviteCode` 与 `isAdmin` 一样，是登录响应的快照存在 Dexie 的 `syncMeta` 里。

## 2. 换码要解决的两个问题

用户给出的动机是两条：**作废泄露的旧码**、**换个码来多邀几个人**。

第二条在当前实现下换码解决不了——已用数是按 `invited_by = 我的 id` 数出来的，与码这个字符串无关，换新码后仍然是「已邀 3、还剩 2」。所以必须显式选择名额语义。

### 2.1 选定：换码即重置已用名额

比较过的三种方案：

| 方案 | 语义 | 代价 |
|---|---|---|
| A · 管理员不限量 | `is_admin` 跳过配额检查 | 一行改动、零 UI；但**码一旦泄露 = 无限注册** |
| **C · 换码重置名额（选定）** | 码 = 一张有 5 次使用次数的券，换券即重新计次 | 加一列 + 改一处 SQL；后台排行口径要一并修正 |
| 提额 UI | 后台可改任意账号 `invite_quota` | 管理页首次出现写接口，鉴权与测试成本更高 |

C 优于 A 的地方在**安全**，而不只是心智模型：即使管理员的码泄露，最多被薅 5 个注册就自动锁死，不是无限。A 把「泄露 = 无限注册」当作必须接受的代价，C 直接消掉了这个代价。

C 的心智模型也更直观——「码是一张有次数的券」比「账号有名额、码只是个标识」更接近家长的直觉。

### 2.2 换码范围：只能换自己的

管理员只能换**自己**的码，不能重置别人的、也不能改别人的配额。入口因此放在设置页的云同步卡（只对 `isAdmin` 渲染按钮），**管理页完全不动**，不需要用户列表、不需要管理页首次出现写接口。

普通用户名额用完没有自助路径，只能联系管理员。这是设计意图（防滥用），文案要说清楚。

## 3. 数据模型

`migrations/0002_invite_rotate.sql`：

```sql
ALTER TABLE users ADD COLUMN invite_reset_at INTEGER NOT NULL DEFAULT 0;
```

**零回填**：存量行全部是 0，而 `created_at >= 0` 永真，所以存量账号的计数行为与今天逐字节一致。普通用户永远不换码，这列对他们恒为 0。

`invited_by` 一列**不动**——换码不影响归属追溯，已注册的人仍然挂在邀请人名下，后台「最近注册」里的邀请人 email 照常正确。重置的只是「本世代已用几个」。

## 4. 配额判据（全仓唯一一处）

`functions/api/auth/register.ts` 的子查询加一个条件：

```sql
(SELECT COUNT(*) FROM users c
  WHERE c.invited_by = u.id AND c.created_at >= u.invite_reset_at) AS used
```

边界用 `>=` 且比较的是毫秒时间戳，无歧义：换码那一刻之后注册的才计入当前世代。

## 5. 服务端：两个新端点

### 5.1 `GET /api/account/invite`

所有登录用户可调，返回 `{ inviteCode, used, quota, isAdmin }`。

`used` 用 §4 的同一条口径算——**两处必须同源**，否则界面显示「还剩 1 个」而注册那边判满，是最难排查的一类不一致。

### 5.2 `POST /api/account/invite`

仅 `is_admin`。生成新码，在同一条 `UPDATE` 里写 `invite_code` 与 `invite_reset_at = now`，返回与 5.1 相同的形状（`used` 必为 0）。

**与 5.1 同路径、用方法区分**（同一个 `functions/api/account/invite.ts` 里导出 `onRequestGet` 与 `onRequestPost`），而不是 `.../invite/rotate`：两者的响应形状必须逐字一致，同文件才能共用同一个 `readState()` 去算 `used`——而 §4 已经说明这个口径分叉是最难排查的一类不一致。

- **鉴权：复用现有的 `adminGate`，不新写一个。** 它的语义（`null → unauthorized` / 非管理员 → `forbidden` / 否则 `ok`）与本端点所需的逐字相同，另写一个 `rotateGate` 就是本仓反复吃过亏的「两处各写一份必然漂移」。**401 与 403 保持分开**，理由见 `adminGate` 自己的注释——合成一个码，排障时分不清「该重新登录」还是「该去 D1 里设 is_admin」；而抽成纯函数是因为 `deploy-cf.yml` 的质量门不跑 `test:api`，鉴权回归只有单测拦得住。
- **顺带把 `adminGate` 从 `functions/lib/admin-stats.ts` 移到 `functions/lib/auth.ts`**（其单测一并移走，`stats.ts` 改一处 import）。它是纯粹的鉴权谓词，与统计整形无关；出现第二个消费者之后，原来的位置就是错的。
- **撞车重试**：`invite_code` 有 UNIQUE 约束，新码撞车重试 3 次，仍失败回 `retry` 503（沿用 register 里既有的口径与客户端文案）。
- **限速**：每日 5 次，走现成的 `hitRateLimit` / `readRateLimit`。无限换码等于无限名额，而这个端点的唯一凭证是一个 **365 天不过期**的 token。

## 6. 客户端（设置页云同步卡）

打开卡片时拉一次 `GET /api/account/invite`，显示「我的邀请码 XXXX · 已邀 2/5」；`isAdmin` 才多渲染一个「换一个码」按钮，点击先二次确认（不可逆、旧码立刻失效）。

三条必须写死的行为：

1. **GET 失败（离线）回落到 `syncMeta` 里的快照码，且不显示 used/quota。** app 是离线可用的 PWA，显示 `0/5` 是撒谎，转圈或空白是退步。
2. **只有成功响应才覆盖** `syncMeta` 的 `inviteCode` 与 `isAdmin`，失败绝不清空——否则离线打开一次设置页，管理页入口就消失了。
3. 换码成功后立刻把新码写回 `syncMeta`。

### 6.1 顺带修掉的既有缺口

- **多设备旧码不同步**：客户端的码是登录快照，在 iPad 上换了码，笔记本的设置页会一直显示旧码，复制发给人必然失败。加了这个 GET 就消掉了。
- **`isAdmin` 不再只是登录快照**：CLAUDE.md 记过「改完 `is_admin` 要重新登录一次」，因为客户端那份是登录响应的快照。GET 顺带回这个字段后，打开设置页就生效。

## 7. 管理后台排行口径修正

这是 C 方案的必付成本。`functions/api/admin/stats.ts` 的邀请排行现在是 `COUNT(c.id)` 数历史全部，而配额判据只数本世代。换过两次码之后，界面会并排显示「已邀 7 / 配额 5」这种自相矛盾的数字。

改法：SQL 加一个条件聚合出 `currentUsed`，前端显示「累计 7 · 当前码 2/5」。两个口径都保留——累计反映真实拉新贡献，当前码反映还能邀几个，都有用，但不能混成一个数。

## 8. 测试

### 8.1 一个必须正视的覆盖缺口

本迭代的核心判据（§4 那个 `AND c.created_at >= u.invite_reset_at`）**写在 SQL 里，抽不成纯函数**，而 `deploy-cf.yml` 的质量门只跑 `npm test` 与两份 typecheck、**不跑 `test:api`**。也就是说：谁哪天顺手把这个条件删掉，CI 全绿，线上静默恢复成旧行为（换码不再重置名额），而且不报错、没人会发现。

对策是按本仓 `nav.test.ts` / `settings-fold.test.ts` / `challenge-shell.test.ts` 既有的路子，**加一条源文本契约测试**：用 `?raw` 读 `register.ts`，断言计数 SQL 里含 `invite_reset_at`。它拦不住语义错误，但能拦住「被删掉」，而后者才是这条口径最可能的死法。

### 8.2 分层

| 层 | 覆盖 |
|---|---|
| 纯函数单测 | `adminGate` 既有的三条用例随文件迁移到 `auth` 侧，断言不变（未登录 → `unauthorized`/401、非管理员 → `forbidden`/403、管理员 → `ok`） |
| 源文本契约 | `register.ts` 的计数 SQL 含 `invite_reset_at`（§8.1） |
| 集成断言 `test:api` | 换码后旧码失效（400 `bad_invite_code`）；新码可用满 5 次；第 6 次 403 `invite_quota_exhausted`；换码后 `used` 归 0；非管理员 rotate 得 403；未登录 rotate 得 401；`GET /api/account/invite` 返回的 `used` 与注册端判据一致 |

`test:api` 跑之前须 `npm run db:seed:admin`（否则 admin 那批连锁 401）；撞 429 先停 wrangler 再 `npm run db:reset:limits`（运行期间它持着 D1 文件锁）。

## 9. i18n

全部新增文案按本仓规矩出中英双语（`src/i18n.tsx` 的 zh/en 两份字典），含：已用/额度行、换码按钮、二次确认文案、换码成功/失败提示、离线回落时的说明、普通用户「名额用完请联系管理员」的说明。

## 10. 明示接受的边界

1. **配额检查有竞态**：`COUNT` 与 `INSERT` 不在一个事务里，两个人同时用同一个码注册，理论上能超出一个名额。家庭规模不处理。
2. **换码后旧码立即失效**，已发出去还没注册的亲友会失败，需要重发新码。不做宽限期——立即失效正是「作废泄露码」的全部意义。
3. **其他设备的旧码要到下次打开设置页（GET 成功）或重新登录才更新**。已由 §6.1 大幅缓解，但离线设备仍会显示旧码。
4. **普通用户无自助换码/提额路径**，名额用完只能联系管理员。这是设计意图。

## 11. 明确不做

- **管理员改别人的配额 / 重置别人的码**：需求是「只能换自己的」，做了就得在管理页加用户列表与写接口，且亲友那边的码会在他不知情时变掉。
- **自定义邀请码**（指定成好记的字符串）：需要额外的重名校验与字符集限制，当前动机里没有这一条。
- **普通用户靠训练表现提额**：邀请额度会变成可刷的游戏化奖励，与「防滥用」的初衷相反。
- **换码时保留旧码一段宽限期**：见 §10.2。
- **服务端事务化配额检查**：见 §10.1。

## 12. 一条顺带的运维建议（不写代码）

管理员能自助换码之后，`BOOTSTRAP_INVITE_CODE` 这个环境变量就彻底没有存在理由了——它**无限量**（`invitedBy` 记 `NULL`，整个配额分支被绕过）、**且不可追溯**（后台看不出是谁邀的），是系统里唯一绕过配额的路径，与本迭代收紧的方向正相反。CLAUDE.md 与 `register.ts` 的注释都已写着「用完应删除该 secret」。

建议本迭代上线后在 Cloudflare 控制台删掉该 secret。这不是代码改动，作为部署清单的一条记在这里。
