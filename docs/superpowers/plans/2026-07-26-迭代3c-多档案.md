# 迭代 3c 多档案 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 一个家长账号下支持多个孩子档案——训练/打卡/积分/勋章/图鉴/兑换/验光/医学参数按档案独立，奖励清单与设备偏好共享，档案清单跨设备同步；单档案家庭界面零变化。

**Architecture:** 归属判定与档案规则全部抽成 `src/profiles/*.ts` 纯函数（`profile-rules` / `profile-settings`），碰 Dexie 的读取集中到 `src/profiles/profile-data.ts` 一层薄封装（`profileSessions()` 等），各业务服务只改成"从这层读、写时盖当前 profileId"。当前档案存 localStorage 但以模块级变量为准（仿 `i18n.tsx` 的 `useSyncExternalStore` 模式），故 node 环境无 localStorage 也能单测切档案。Dexie 升到 **v9**：新增 `profiles` 表，并把 `checkins`/`badges`/`monsters` 三张"自然键主键"表改成复合主键 `[profileId+自然键]`（IndexedDB 主键不可原地修改，走 v7 快照 → v8 删表 → v9 重建的官方三步走）。

**Tech Stack:** TypeScript + React 18 + Vite 6、Dexie 4（IndexedDB，复合主键）、vitest 2 + fake-indexeddb、Cloudflare Pages Functions + D1（仅改 kind 白名单一处）。

## Global Constraints

- 交流与注释、提交信息一律**简体中文**；技术术语与代码标识符保留英文。
- **归属原则（spec §11.5，逐条落实，不得自行更改）**：属于孩子的独立，属于家长或设备的共享。
  - **每档案独立**：训练记录 / 打卡 / 连续天数 / 统计 / 积分（累计与可用）/ 勋章 / 怪兽图鉴 / 皮肤解锁（由积分派生自动跟随）/ 兑换记录 / 补签卡 / 验光记录 / **视标大小 · 单眼时长 · 拍子度数**。
  - **设备共享**：屏幕标定 `fzp.cssPxPerMm`、翻拍速度 `fzp.flipMs`、语言 `fzp.lang`、皮肤选择 `fzp.skinId`、引导 `fzp.onboarded`、提醒时间 `fzp.reminderTime`。
  - **账号共享**：奖励清单（`rewards` 表）——家长配一次，哪个孩子都能兑换；**兑换记录（`redemptions`）仍按档案独立**。
- **视标大小 / 单眼时长 / 拍子度数每档案独立是医学正确性问题**，不是偏好：两个孩子视力不同，共享会让训练强度对其中一个是错的。
- **单档案时不出现任何切换 UI**（渐进披露）。只有 `active=true` 的档案数 **≥2** 才在首页显示切换器。
- 档案 = **昵称 + 可选年龄段**，不收真名与生日（数据最小化，spec §7）。
- 删除档案是**软删**（`active=false`），其训练记录**不删**（家长还想看历史），只是不再出现在切换器里。
- **本地 IndexedDB 始终是唯一可靠源**：后端不可用 / 没登录 / 断网时训练照常，同步纯属尽力而为、失败一律静默。
- 存量数据全部归入迁移时自动建的 `default` 档案，家长可改名。7 张业务表的行 `profileId` 已经是 `'default'`（3b-2 交付），**不再改动其值**。
- `deterministicUuid(kind, profileId, naturalKey)` 已把 profileId 编进 uuid（`kind:profileId:自然键`），换档案天然不撞 uuid。**不得改动 uuid 形状**——uuid 一旦上云极难改。
- 奖励清单与档案清单这两类"非孩子"记录的 uuid 中段一律用常量 `ACCOUNT_SCOPE`，其值**必须**是字符串 `'default'`：云端已有的 `reward:default:<createdAt>` 行全靠它，改值会让那些行变成永不更新的孤儿。
- `src/data/api.ts` 的 7 个 `pushXxx` 签名（`pushSession/pushCheckin/pushBadges/pushMonsters/pushRewards/pushRedemptions/pushExams`）与 `pushAll` **一字不动**，只加一个 `pushProfile`。
- 服务端契约（3b-1 已交付）：单条 payload ≤ **16KB**、单批 ≤ **500 条**、`updatedAt` 不得超前当前时间 **24 小时**；本迭代对服务端**只做一处改动**——`functions/lib/sync-validate.ts` 的 `KINDS` 白名单加 `profile`（从 7 变 8）。改完必须跑 `npm run test:api` 确认既有 **31 项断言**全绿。
- 所有测试文件显式 `import { describe, it, expect } from 'vitest'`（`globals` 未开）；测试与源码同目录。
- 新增 localStorage 键沿用 `fzp.` 前缀并走 `lsGet/lsSet`；当前档案键 `fzp.activeProfileId` 是**设备级、不同步**；每档案医学参数键形状 `fzp.p.<profileId>.<base>`。新增的 `syncMeta` 键 `resyncedFor3c` 是**一次性迁移标记**，不进 localStorage、不参与备份、退出登录也不清。
- **混版是本迭代最大的数据风险**：3b 客户端既不认识 `kind='profile'`（跳过但游标照旧前进），也不认识复合主键（拿 `date` 当 checkins 主键，会把一个孩子的打卡整行覆盖到另一个孩子头上再推上云）。代码侧有 `ensureFullResyncFor3c` 兜底，但它只能捞回"被跳过"的记录、**补不回被覆盖的数值**——所以「人工前置」里"先把每一台设备升到 3c，再建第二个档案"是**硬关卡**，不是建议。
- **档案归属的权威是 uuid 中段**（`kind:profileId:自然键`），不是服务端 `records.profile_id` 列——那一列会被旧客户端的 push 覆写（`push.ts` 的 ON CONFLICT 里有 `profile_id = excluded.profile_id`）。凡是"这条记录属于哪个孩子"的判断都从 uuid 起算。
- 家长既有的 `fzp.optotypeSizeMm` / `fzp.durationSec` / `fzp.flipperD` **必须迁移**到 default 档案，且**不删旧键**（回滚与旧构建仍能读）。
- 新文案必须 **ZH / EN 双份**（`src/i18n.tsx` 扁平字典，两份都要加，缺一份会静默回退成中文）。
- 开发环境 IO 慢：`vitest` 首次启动 40-70 秒属正常，勿因慢而中断重试。
- Windows + Node 24 下脚本一律用 `process.exitCode`，不用 `process.exit()`。
- 测试基线：本计划开始前 `npm test` 为 **400 passed / 44 files**。每个任务末尾给出该任务后的预期总数。

### 混版硬关卡：**先把每一台设备都升到 3c，再创建第二个档案**

- [ ] 让**每一台已装机设备**（iPad + 家长手机）都联网打开一次新版本，在「设置 → 关于」里确认版本号都已是 3c。
- [ ] 全部确认之后，才在设置页创建第二个档案。

为什么这是硬关卡（不是"最好这样"）：3b 客户端**不认识** `kind='profile'`，也**不认识**复合主键。混版窗口里在 iPad 上建了「妹妹」并练了一节，手机那台还是 3b，会发生三连损坏且全程静默：

1. `applyPulled` 对未知 kind 直接 `return`（engine.ts:117），但 `pullPages` 照旧 `setLastPulledSeq` → 那条 `profile` 行**此后永不重发**；
2. 3b 的 `checkins` 主键是 `date`，`findLocal` 用自然键 `get('2026-07-20')` 命中的是**姐姐**那一行 → `mergeRecord` 判 LWW put → 姐姐当天的 `streak`/`dailyPoints`/`totalPoints` 被妹妹的数值整行替换（连 uuid 一起换成 `checkin:kid2:…`）；
3. 紧随其后的 `reconcileAndWriteBack` 把混在一起的两个孩子当**一条链**重算并 `enqueuePut`（`updatedAt=now`，必赢 LWW）→ 推回 D1 → 再同步给已升级的 iPad。

积分是能换现实奖励和补签卡的货币，这种损坏不可逆。代码侧的配套防线（Task 4 的一次性全量重拉）只能把"窗口期被跳过的 `profile` 行"和"被跳过的业务行"补回来，**补不回被覆盖掉的数值**——所以关卡必须由人来把。

### 回滚步骤（可执行版，替换"退回旧构建"这句空话）

⚠️ **不能只是退回旧构建**：v9 落盘后旧构建（最高只声明 `version(6)`）打开同一个库会 `VersionError` → Dexie 兜底不带版本号重开 → `verifyInstalledSchema` 因 `checkins` 主键不符而失败 → Dexie 抬高原生版本并进 schemaPatchMode，试图把主键改回 `date` → 抛 `Not yet support for changing primary key` → `db.open()` 失败（白屏），而且原生版本已被抬高，**再切回新构建也会走同一条兜底路径**。

真正可执行的三步：

1. **先删本站数据**：iPad「设置 → Safari → 高级 → 网站数据」里删掉本站条目（或改用无痕窗口验证）。
2. 再装 / 回退到旧构建，确认能正常打开（此时是空库）。
3. 用第一步导出的 **JSON 备份**在旧构建里「恢复」。

`legacyKeyed`（Task 2 建的升级前整表快照）**不是回滚依据**——新旧构建都没有读它的入口。它只作**排障取证**（想看升级前的原始行长什么样时用 Safari 开发者工具直接翻 IndexedDB）。**恢复请一律走 JSON 备份。**

> 开发机上可以随便试；上面这些只针对"把新版本推给孩子那台设备"这一刻。

### Task 1: 档案归属纯函数（profile-rules）

**为什么先做：** 后面 9 个任务都要问同一个问题——"这一行属于哪个档案"。存量行可能**没有** `profileId`（v6 迁移是逐行 `try/catch` 的，允许漏），所以判定必须是 `(row.profileId || 'default')` 而不是索引查询：用 `where('profileId')` 查会让这些行从统计里**静默消失**。

**Files:**
- Create: `src/profiles/profile-rules.ts`
- Test: `src/profiles/profile-rules.test.ts`

**Interfaces:**
- Consumes: 无（纯函数，零依赖）。
- Produces:
  - `DEFAULT_PROFILE_ID = 'default'`、`ACCOUNT_SCOPE = 'default'`、`MAX_PROFILES = 6`、`MAX_NAME_LEN = 12`
  - `interface ProfileLike { id: string; name: string; active: boolean; createdAt: number }`
  - `profileIdOf(row: { profileId?: string }): string`
  - `belongsTo(row: { profileId?: string }, profileId: string): boolean`
  - `filterByProfile<T extends { profileId?: string }>(rows: readonly T[], profileId: string): T[]`
  - `resolveActiveProfileId(saved: string | null, profiles: readonly ProfileLike[]): string`

```ts
import { describe, it, expect } from 'vitest'
import {
  DEFAULT_PROFILE_ID, ACCOUNT_SCOPE, MAX_PROFILES, MAX_NAME_LEN,
  profileIdOf, belongsTo, filterByProfile, resolveActiveProfileId,
  sanitizeProfileName, newProfileId, canAddProfile, missingProfileIds,
  type ProfileLike,
} from './profile-rules'

function p(id: string, over: Partial<ProfileLike> = {}): ProfileLike {
  return { id, name: id, active: true, createdAt: 1000, ...over }
}

describe('ACCOUNT_SCOPE', () => {
  it('必须恰好是 "default" —— 云端既有 reward:default:<createdAt> 行全靠它', () => {
    // 奖励清单是账号共享的，uuid 中段用这个常量。改成别的值（如 "account"）会让
    // 云端所有既有 reward 行变成永不再被更新的孤儿，家长的奖励列表在别的设备上会重复出现。
    expect(ACCOUNT_SCOPE).toBe('default')
    expect(DEFAULT_PROFILE_ID).toBe('default')
  })
})

describe('profileIdOf / belongsTo', () => {
  it('缺 profileId 的存量行一律视为 default', () => {
    // v6 迁移是逐行 try/catch 的，确实会留下没有 profileId 的行。
    // 若改用 where('profileId') 索引查询，这些行会从统计里静默消失——孩子几个月的记录凭空不见。
    expect(profileIdOf({})).toBe('default')
    expect(profileIdOf({ profileId: '' })).toBe('default')
    expect(belongsTo({}, 'default')).toBe(true)
    expect(belongsTo({}, 'kid2')).toBe(false)
  })

  it('显式 profileId 精确匹配', () => {
    expect(belongsTo({ profileId: 'kid2' }, 'kid2')).toBe(true)
    expect(belongsTo({ profileId: 'kid2' }, 'default')).toBe(false)
  })
})

describe('filterByProfile', () => {
  it('只留本档案的行（含缺省行归 default）', () => {
    const rows = [
      { n: 1 },
      { n: 2, profileId: 'default' },
      { n: 3, profileId: 'kid2' },
    ]
    expect(filterByProfile(rows, 'default').map((r) => r.n)).toEqual([1, 2])
    expect(filterByProfile(rows, 'kid2').map((r) => r.n)).toEqual([3])
  })

  it('空输入返回空数组', () => {
    expect(filterByProfile([], 'default')).toEqual([])
  })
})

describe('resolveActiveProfileId', () => {
  it('保存值仍是可用档案 → 原样沿用', () => {
    expect(resolveActiveProfileId('kid2', [p('default'), p('kid2')])).toBe('kid2')
  })

  it('保存值被软删 → 回退到最早创建的可用档案', () => {
    expect(resolveActiveProfileId('kid2', [
      p('kid2', { active: false, createdAt: 100 }),
      p('kid3', { createdAt: 300 }),
      p('default', { createdAt: 200 }),
    ])).toBe('default')
  })

  it('保存值根本不存在（换设备拉到别的档案清单）→ 同样回退', () => {
    expect(resolveActiveProfileId('ghost', [p('kid3', { createdAt: 300 })])).toBe('kid3')
  })

  it('saved 为 null → 取最早创建的可用档案', () => {
    expect(resolveActiveProfileId(null, [p('b', { createdAt: 200 }), p('a', { createdAt: 100 })])).toBe('a')
  })

  it('一个可用档案都没有 → 退回 default（永远有个能练的档案，不能让 app 卡住）', () => {
    expect(resolveActiveProfileId('kid2', [])).toBe('default')
    expect(resolveActiveProfileId('kid2', [p('kid2', { active: false })])).toBe('default')
  })
})

describe('sanitizeProfileName', () => {
  it('去首尾空白', () => {
    expect(sanitizeProfileName('  妹妹  ')).toBe('妹妹')
  })

  it('超长截断到 MAX_NAME_LEN', () => {
    expect(sanitizeProfileName('一'.repeat(30))).toBe('一'.repeat(MAX_NAME_LEN))
  })

  it('空白/空串返回 null（调用方据此拒绝创建）', () => {
    expect(sanitizeProfileName('   ')).toBeNull()
    expect(sanitizeProfileName('')).toBeNull()
  })
})

describe('newProfileId', () => {
  it('形状是 p + 时间的 36 进制，且绝不等于 default', () => {
    const id = newProfileId([], 1_700_000_000_000)
    expect(id).toBe('p' + (1_700_000_000_000).toString(36))
    expect(id).not.toBe(DEFAULT_PROFILE_ID)
  })

  it('与既有 id 撞车时换一个（同一秒内连建两个档案是可达的）', () => {
    const first = newProfileId([], 1_700_000_000_000)
    const second = newProfileId([first], 1_700_000_000_000)
    expect(second).not.toBe(first)
  })
})

describe('canAddProfile', () => {
  it('未达上限可加；软删的不占额度', () => {
    expect(canAddProfile([p('a')])).toBe(true)
    const many = Array.from({ length: MAX_PROFILES }, (_, i) => p('k' + i))
    expect(canAddProfile(many)).toBe(false)
    expect(canAddProfile([...many.slice(1), p('dead', { active: false })])).toBe(true)
  })
})

describe('missingProfileIds', () => {
  it('报出数据里出现过、但档案表里没有的 id（去重、忽略 undefined）', () => {
    // 恢复老备份后会出现这种情况：7 表里有 kid2 的记录，但 profiles 表没有 kid2，
    // 不补出来这些数据在界面上就永远看不到。
    expect(missingProfileIds(['default', 'kid2', 'kid2', undefined, 'kid3'], ['default', 'kid3']))
      .toEqual(['kid2'])
  })

  it('全都有 → 空数组', () => {
    expect(missingProfileIds(['default'], ['default'])).toEqual([])
  })
})
```

```ts
/**
 * 多档案的归属判定与档案规则（spec §11.5）。全部纯函数、零依赖，便于单测锚定。
 *
 * 一句话原则：**属于孩子的独立，属于家长或设备的共享。**
 */

/** 迁移时自动创建的档案 id。存量 7 表的行 profileId 都是它 */
export const DEFAULT_PROFILE_ID = 'default'

/**
 * "不属于任何孩子"的记录（奖励清单、档案清单本身）在 uuid 中段用的作用域。
 *
 * ⚠️ 它的值**必须**是 'default'：云端已经存在一堆 `reward:default:<createdAt>` 行，
 * 换成 'account' 之类会让那些行全部变成永不更新的孤儿，家长的奖励清单在别的设备上重复出现。
 * 单独起个名字只是为了让"这里的 default 表示账号级、不是第一个孩子"读得出来。
 */
export const ACCOUNT_SCOPE = 'default'

/** 档案数上限。家用场景够了，且防止误触建出一堆空档案 */
export const MAX_PROFILES = 6

/** 昵称长度上限：切换器是一排小药丸，太长会挤爆首页 */
export const MAX_NAME_LEN = 12

/** 档案的最小形状。纯函数只需要这四个字段，不必依赖 Dexie 的 ProfileRow */
export interface ProfileLike {
  id: string
  name: string
  active: boolean
  createdAt: number
}

/**
 * 一行数据属于哪个档案。
 *
 * ⚠️ 必须容忍 profileId 缺失并归入 default：v6 的迁移是**逐行 try/catch** 的
 * （单行失败不整体回滚，否则 db.open() 永久失败 = 白屏），所以"没有 profileId 的存量行"
 * 是可达状态。这也是本迭代一律在内存里过滤、而不用 `where('profileId')` 索引查询的原因——
 * IndexedDB 的索引会跳过该字段为 undefined 的记录，那些行会从统计里**静默消失**。
 * 数据量很小（几百行），内存过滤的代价可以忽略。
 */
export function profileIdOf(row: { profileId?: string }): string {
  return row.profileId && row.profileId.length > 0 ? row.profileId : DEFAULT_PROFILE_ID
}

export function belongsTo(row: { profileId?: string }, profileId: string): boolean {
  return profileIdOf(row) === profileId
}

export function filterByProfile<T extends { profileId?: string }>(
  rows: readonly T[],
  profileId: string,
): T[] {
  return rows.filter((r) => belongsTo(r, profileId))
}

/**
 * 当前档案 id 的兜底解析：保存的那个若已被软删 / 根本不存在（换设备后拉到的是别的清单），
 * 回退到**最早创建的可用档案**；一个都没有就回 DEFAULT_PROFILE_ID。
 * 永远返回一个非空 id——app 任何时候都得有个能练的档案。
 */
export function resolveActiveProfileId(saved: string | null, profiles: readonly ProfileLike[]): string {
  const usable = profiles.filter((p) => p.active)
  if (saved && usable.some((p) => p.id === saved)) return saved
  if (usable.length === 0) return DEFAULT_PROFILE_ID
  return [...usable].sort((a, b) => a.createdAt - b.createdAt)[0].id
}

/** 昵称清洗：去空白 + 截断。空则返回 null（调用方据此拒绝创建/改名） */
export function sanitizeProfileName(raw: string): string | null {
  const s = raw.trim()
  if (s.length === 0) return null
  return s.slice(0, MAX_NAME_LEN)
}

/**
 * 生成新档案 id。用时间的 36 进制而非 crypto.randomUUID——
 * 后者要求安全上下文（iPad 走局域网 IP 时为 undefined），而这里不需要不可预测性。
 * 撞车时追加后缀：同一毫秒建两个档案虽罕见，但 id 一旦重复会让两个孩子共用一份数据。
 */
export function newProfileId(existingIds: readonly string[], nowMs: number): string {
  const base = 'p' + nowMs.toString(36)
  let id = base
  let n = 1
  while (existingIds.includes(id) || id === DEFAULT_PROFILE_ID) {
    id = `${base}-${n}`
    n += 1
  }
  return id
}

/** 软删的档案不占额度（它已经不在切换器里了） */
export function canAddProfile(profiles: readonly ProfileLike[]): boolean {
  return profiles.filter((p) => p.active).length < MAX_PROFILES
}

/**
 * 数据里出现过、但档案表里没有的 profileId。
 * 恢复老备份后就是这种情况（备份文件里可能没有 profiles 表），不补出来那些数据在界面上
 * 永远看不到——数据还在，但没有任何入口能切到它。
 */
export function missingProfileIds(
  dataProfileIds: readonly (string | undefined)[],
  existingIds: readonly string[],
): string[] {
  const have = new Set(existingIds)
  const out: string[] = []
  for (const raw of dataProfileIds) {
    const id = raw && raw.length > 0 ? raw : DEFAULT_PROFILE_ID
    if (!have.has(id)) {
      have.add(id)
      out.push(id)
    }
  }
  return out
}
```

### Task 2: Dexie v9——新增 profiles 表 + 三张 KEYED 表改复合主键

**这是本迭代唯一动用户既有数据的任务，也是唯一的高风险任务。**

`checkins` 主键是 `date`、`badges`/`monsters` 主键是 `id`。两个孩子同一天打卡、或各自解锁同一枚勋章，在旧 schema 下**就是同一行**、互相覆盖——多档案在这三张表上根本不成立。而 IndexedDB 的 keyPath 建表后不可修改（Dexie 会直接报 `Not yet support for changing primary key`），唯一办法是**删表重建**，故走 Dexie 官方文档的三步走：v7 把三张表整表快照进 `legacyKeyed` → v8 删表 → v9 以 `[profileId+自然键]` 重建并写回。三步在**同一个 versionchange 事务**里跑完（Dexie 按序应用各版本），中途失败整体回滚到 v6，不会留下半迁移状态。`legacyKeyed` **刻意保留不删**（三张表合计通常几百行、几十 KB），但它**只是排障取证用的原始行副本，不是回滚依据**——新旧构建都没有读它的入口，回滚请走「人工前置」里那三步（删本站数据 → 装旧构建 → JSON 备份恢复）。

> ⚠️ **上真机之前必须先在桌面 Safari 上预演一次**（见「人工前置」）。同一个 versionchange 事务里 `deleteObjectStore` 紧接着 `createObjectStore(`**同名**`)` 在 WebKit 上历来是脆弱路径，而本任务的单测跑在 node 的 fake-indexeddb 上，**一定不会复现平台特有行为**；失败后果不是"少个功能"而是 `db.open()` 永久失败 = app 完全打不开。预演失败就改走本任务末尾的 **Plan B（新表名，完全不删表）**。

```ts
    // checkins 主键是 date、badges/monsters 主键是 id：两个孩子同一天打卡、或各自解锁同一枚

    this.version(7)
      .stores({
        // 三张 KEYED 表这一版**保持原样**（本版只负责快照），自增表顺手加 profileId 索引
        sessions: '++id, date, uuid, profileId',

        badges: 'id, uuid',
        monsters: 'id, uuid',
        rewards: '++id, uuid',
        redemptions: '++id, kind, status, uuid, profileId',
        exams: '++id, date, uuid, profileId',
        outbox: '++id, uuid, kind',
        syncMeta: 'key',
        profiles: 'id, uuid',
        legacyKeyed: '++id, kind',
      })
      .upgrade(async (tx) => {
        const jobs: [LegacyKeyedRow['kind'], string][] = [
          ['checkin', 'checkins'],
          ['badge', 'badges'],
          ['monster', 'monsters'],
        ]
        for (const [kind, table] of jobs) {
          const rows = (await tx.table(table).toArray()) as Record<string, unknown>[]
          for (const row of rows) {
            try {
              await tx.table('legacyKeyed').add({ kind, row })
            } catch {
              // 逐行兜底：单行失败**绝不能**让整个 versionchange 事务回滚——
              // 一回滚 db.open() 每次都失败，app 直接白屏（3b-2 已踩过这个坑）。
            }
          }
        }
      })

    // 只为"删这三张表"而存在的一版：Dexie 要求删与建分处两个版本
    this.version(8).stores({
      checkins: null,
      badges: null,
      monsters: null,
    })

    this.version(9)
      .stores({
        // 复合主键：两个孩子的同一天 / 同一枚勋章从此是两行。
        // 额外保留 date / id / uuid 单字段索引，供 orderBy 与按 uuid 反查
        checkins: '[profileId+date], date, uuid',
        badges: '[profileId+id], id, uuid',
        monsters: '[profileId+id], id, uuid',
      })
      .upgrade(async (tx) => {
        const TARGET: Record<LegacyKeyedRow['kind'], string> = {
          checkin: 'checkins',
          badge: 'badges',
          monster: 'monsters',
        }
        /** 各类的自然键字段——复合主键的另一半 */
        const KEY_FIELD: Record<LegacyKeyedRow['kind'], string> = {
          checkin: 'date',
          badge: 'id',
          monster: 'id',
        }
        const snaps = (await tx.table('legacyKeyed').toArray()) as LegacyKeyedRow[]
        for (const snap of snaps) {
          try {
            const row = { ...snap.row }
            // 复合主键的两半都必须有值，否则 IndexedDB 直接 DataError。
            // v6 的迁移是逐行 try/catch 的，确实可能留下没有 profileId 的行 → 一律归 default。
            //
            // ⚠️ 这里刻意写字面量 'default' 而不 import Task 1 的 DEFAULT_PROFILE_ID：
            // db.ts 是最底层模块（profiles/ 反过来依赖它），import 会造成反向依赖。
            // 值**必须**与 DEFAULT_PROFILE_ID 一致——profile-rules.test.ts 的第一条用例
            // （`expect(DEFAULT_PROFILE_ID).toBe('default')`）就是锚定这个约定的。
            if (typeof row.profileId !== 'string' || row.profileId.length === 0) {
              row.profileId = 'default'
            }
            const nk = row[KEY_FIELD[snap.kind]]
            if (typeof nk !== 'string' || nk.length === 0) continue // 键坏了的脏行跳过，不炸事务
            await tx.table(TARGET[snap.kind]).put(row)
          } catch {
            // 同上：逐行兜底，宁可少一行也不让 db.open() 永久失败
          }
        }
      })
```

#### Plan B（真 Safari 预演失败时才走：**新表名，完全不删表**）

如果「人工前置」的桌面 Safari 预演在 v7→v8→v9 上失败（`db.open()` 报错 / 白屏 / 表打不开），**不要**在同名 delete+create 上调试，直接改走这条路径——它完全绕开"同一个 versionchange 事务里删掉又建同名 store"这个 WebKit 脆弱点：

1. **只留一个新版本 v7**，不再有 v8/v9，也不再需要 `legacyKeyed`：

```ts
    this.version(7).stores({
      sessions: '++id, date, uuid, profileId',
      // 旧的三张表**原样保留、不再写入**（天然就是升级前快照，兼作排障取证）
      checkins: 'date, uuid',
      badges: 'id, uuid',
      monsters: 'id, uuid',
      // 新表名 + 复合主键。IndexedDB 不能改主键、也不能改表名，
      // 但**新建一张表**是最平凡的路径，任何浏览器都不会出意外。
      checkins2: '[profileId+date], date, uuid',
      badges2: '[profileId+id], id, uuid',
      monsters2: '[profileId+id], id, uuid',
      rewards: '++id, uuid',
      redemptions: '++id, kind, status, uuid, profileId',
      exams: '++id, date, uuid, profileId',
      outbox: '++id, uuid, kind',
      syncMeta: 'key',
      profiles: 'id, uuid',
    }).upgrade(async (tx) => {
      const jobs: [string, string, string][] = [
        ['checkins', 'checkins2', 'date'],
        ['badges', 'badges2', 'id'],
        ['monsters', 'monsters2', 'id'],
      ]
      for (const [from, to, keyField] of jobs) {
        const rows = (await tx.table(from).toArray()) as Record<string, unknown>[]
        for (const row of rows) {
          try {
            const next = { ...row }
            if (typeof next.profileId !== 'string' || next.profileId.length === 0) next.profileId = 'default'
            const nk = next[keyField]
            if (typeof nk !== 'string' || nk.length === 0) continue
            await tx.table(to).put(next)
          } catch { /* 逐行兜底，绝不让事务回滚（回滚 = db.open() 永久失败 = 白屏） */ }
        }
      }
    })
```

2. 类里的表声明改成 `checkins2! / badges2! / monsters2!`（类型同 Plan A：`Table<CheckinRow, [string, string]>` 等），并把三张旧表声明为 `Table<..., string>` 保留只读。
3. 全仓把 `db.checkins` / `db.badges` / `db.monsters` 逐处换成 `db.checkins2` / `db.badges2` / `db.monsters2`，另加两处映射表：`src/data/api.ts` 与 `src/sync/engine.ts` 的 `TABLE_OF`（值改成 `'checkins2'` / `'badges2'` / `'monsters2'`）。`src/backup/backup-service.ts` 的 `readTables()`/`restoreBackup()`、`src/reset/reset.ts` 同理。
   > 用 `rg -n "db\.(checkins|badges|monsters)\b" src` 列全部引用点；改完 `npm run typecheck` 会把漏的都指出来（旧表类型的主键是 `string`，传复合键即报错）。
4. 备份格式**不变**：`BackupTables` 的字段名仍是 `checkins`/`badges`/`monsters`（那是文件格式，与库里的表名无关），只是读写换到新表。
5. 代价与收益：代价是代码里三个表名带个 `2` 后缀（可读性小损失）；收益是迁移只有一个版本、只做"建新表 + 逐行拷"，旧表原样留在库里**天然就是回滚快照**（可省掉 `legacyKeyed`，也让上面「回滚步骤」的第 1 步不再是唯一出路）。

```ts
import { lsGet, lsSet } from '../data/storage'
import { DEFAULT_PROFILE_ID } from './profile-rules'
import { useSyncExternalStore } from 'react'

/**
 * 当前档案 id。**设备级、不同步**（spec §5.1：设备记住 activeProfileId，是本地设置）：
 * iPad 上老大在练、手机上家长看老二的统计，互不干扰。
 *
 * 以模块级变量为准、localStorage 只作持久化——照抄 i18n.tsx 的做法。这一点很重要：
 * 单测跑在 node 环境（无 localStorage，lsGet/lsSet 会静默降级），若直接读 localStorage
 * 就永远只能测到 default 档案，"按档案过滤"这条主线全都测不了。
 */
export const ACTIVE_PROFILE_KEY = 'fzp.activeProfileId'

let current: string = lsGet(ACTIVE_PROFILE_KEY) || DEFAULT_PROFILE_ID
const listeners = new Set<() => void>()

export function getActiveProfileId(): string {
  return current
}

export function setActiveProfileId(id: string): void {
  if (!id) return
  current = id
  lsSet(ACTIVE_PROFILE_KEY, id)
  listeners.forEach((f) => f())
}

function subscribe(f: () => void): () => void {
  listeners.add(f)
  return () => { listeners.delete(f) }
}

/** 订阅当前档案：切档案时各页面自动重取数据 */
export function useActiveProfileId(): string {
  return useSyncExternalStore(subscribe, () => current, () => current)
}
```

```ts
import { db, type ProfileRow } from '../data/db'
import { translate, getLang } from '../i18n'
import { pushProfile } from '../data/api'
import { getActiveProfileId, setActiveProfileId } from './active-profile'
import {
  DEFAULT_PROFILE_ID, canAddProfile, missingProfileIds, newProfileId,
  resolveActiveProfileId, sanitizeProfileName,
} from './profile-rules'

/**
 * 档案 CRUD。编排层保持极薄——判定全在 profile-rules 的纯函数里。
 *
 * 写入一律"先落本地库、再 pushProfile"（与既有 7 张表同一套路）：pushProfile 是
 * fire-and-forget 且受构建期开关约束（VITE_BACKEND=off 时直接不动作），不能拿它当持久化手段。
 */
async function put(row: ProfileRow): Promise<void> {
  await db.profiles.put(row)
  pushProfile(row)
}

export async function listProfiles(): Promise<ProfileRow[]> {
  const rows = await db.profiles.toArray()
  return rows.sort((a, b) => a.createdAt - b.createdAt)
}

export async function listActiveProfiles(): Promise<ProfileRow[]> {
  return (await listProfiles()).filter((p) => p.active)
}

/**
 * 保证 default 档案存在。**必须在应用层做而不是 Dexie upgrade 里**：
 * 全新安装根本不跑 upgrade 函数（Dexie 直接建最新 schema），那样新用户会一个档案都没有。
 * 幂等，且绝不覆盖家长改过的名字。
 */
export async function ensureDefaultProfile(): Promise<void> {
  if ((await db.profiles.get(DEFAULT_PROFILE_ID)) !== undefined) return
  await put({
    id: DEFAULT_PROFILE_ID,
    name: translate(getLang(), 'profile.defaultName'),
    active: true,
    createdAt: Date.now(),
  })
}

/**
 * 给"数据里出现过、档案表里却没有"的 profileId 补出档案。
 * 恢复老备份后就是这种情况（备份文件里可能没有 profiles 表）——不补出来，那些训练记录
 * 数据还在但界面上永远切不到，等于凭空消失。
 */
export async function ensureProfilesForData(): Promise<void> {
  const [profiles, sessions, checkins, badges, monsters, redemptions, exams] = await Promise.all([
    db.profiles.toArray(), db.sessions.toArray(), db.checkins.toArray(), db.badges.toArray(),
    db.monsters.toArray(), db.redemptions.toArray(), db.exams.toArray(),
  ])
  // rewards 刻意不看：奖励清单是账号共享的，它的 profileId 恒为 ACCOUNT_SCOPE，不代表某个孩子
  const seen = [...sessions, ...checkins, ...badges, ...monsters, ...redemptions, ...exams]
    .map((r) => r.profileId)
  const now = Date.now()
  let i = 0
  for (const id of missingProfileIds(seen, profiles.map((p) => p.id))) {
    i += 1
    await put({
      id,
      name: id === DEFAULT_PROFILE_ID
        ? translate(getLang(), 'profile.defaultName')
        : `${translate(getLang(), 'profile.defaultName')} ${i + 1}`,
      active: true,
      createdAt: now + i,
    })
  }
}

export async function createProfile(name: string, ageBand?: string): Promise<ProfileRow | null> {
  const clean = sanitizeProfileName(name)
  if (clean === null) return null
  const all = await listProfiles()
  if (!canAddProfile(all)) return null
  const now = Date.now()
  const row: ProfileRow = {
    id: newProfileId(all.map((p) => p.id), now),
    name: clean,
    active: true,
    createdAt: now,
  }
  if (ageBand) row.ageBand = ageBand
  await put(row)
  return row
}

export async function renameProfile(id: string, name: string): Promise<boolean> {
  const clean = sanitizeProfileName(name)
  if (clean === null) return false
  const row = await db.profiles.get(id)
  if (!row) return false
  await put({ ...row, name: clean, updatedAt: Date.now() })
  return true
}

/**
 * 设置年龄段。**空串与 'none' 一律当"未填"处理并删掉字段**（不是存进字符串 'none'）：
 * `ProfileRow.ageBand` 的约定是"空表示未填"，存 'none' 会让所有
 * `ageBand ? … : …` 的判断把它当成填了——语义分叉一旦上云就得长期兼容。
 */
export async function setProfileAgeBand(id: string, ageBand: string): Promise<void> {
  const row = await db.profiles.get(id)
  if (!row) return
  const next: ProfileRow = { ...row, updatedAt: Date.now() }
  if (ageBand === '' || ageBand === 'none') delete next.ageBand
  else next.ageBand = ageBand
  await put(next)
}

/**
 * 软删（spec §11.5）：只置 active=false，**训练记录一条不删**——家长可能还想看历史，
 * 而且真删会让云端那些记录在下一次拉取时又回来。硬删留到有明确需求时再做。
 */
export async function deactivateProfile(id: string): Promise<void> {
  const row = await db.profiles.get(id)
  if (!row) return
  await put({ ...row, active: false, updatedAt: Date.now() })
  await syncActiveProfile()
}

/** 校正当前档案：被软删 / 换设备后不存在时回退，返回校正后的 id */
export async function syncActiveProfile(): Promise<string> {
  const next = resolveActiveProfileId(getActiveProfileId(), await listProfiles())
  if (next !== getActiveProfileId()) setActiveProfileId(next)
  return next
}

/**
 * 启动引导：保证有 default 档案 → **把数据里出现过的陌生档案补出来** → 校正当前档案。
 *
 * ⚠️ 中间那步不能省。凡是"数据里有某个 profileId，但 profiles 表里没有那一行"的状态，
 * 界面上就**永远切不到**那个孩子——数据在库里，统计和勋章都读不到、切换器也不列出它。
 * 可达路径不止"恢复老备份"，至少还有三条：
 *  ① 混版窗口里旧客户端对未知 kind='profile' 直接 return，但游标照旧前进 → 那条永不重发；
 *  ② 那条 profile 记录被 pushIsolating 判为永久 4xx 隔离掉，而业务行正常上云；
 *  ③ 另一台设备先拉到业务行、profile 行还在下一页（页大小 500，可跨页）。
 * 三个函数都幂等，只读几百行，启动时的成本可以忽略。
 */
export async function bootstrapProfiles(): Promise<void> {
  await ensureDefaultProfile()
  await ensureProfilesForData()
  await syncActiveProfile()
}
```

```ts
/**
 * 各 kind 的本地主键形状：
 *  - `auto`     ++id 自增（sessions/rewards/redemptions/exams）→ 只能按 uuid 索引反查；
 *  - `compound` v9 起的 `[profileId+自然键]`（checkins/badges/monsters）；
 *  - `id`       单字段字符串主键（profiles）。
 * ⚠️ 不能再用 `isKeyedKind` 一刀切：v9 之后拿单个自然键去 `get()` 复合主键表**永远取不到行**，
 * 结果是拉取到的打卡/勋章被当成"本地没有"重复插入、或者删不掉。
 */
const KEY_SHAPE: Record<SyncKind, 'auto' | 'compound' | 'id'> = {
  session: 'auto',
  reward: 'auto',
  redemption: 'auto',
  exam: 'auto',
  checkin: 'compound',
  badge: 'compound',
  monster: 'compound',
  profile: 'id',
}

/** 本地主键值（供 delete 用） */
function localKeyOf(kind: SyncKind, row: AnyRow): string | number | [string, string] {
  if (KEY_SHAPE[kind] === 'auto') return row.id as number
  if (KEY_SHAPE[kind] === 'id') return row.id as string
  return [profileIdOf(row), String(kind === 'checkin' ? row.date : row.id)]
}

/**
 * 拉取记录的**档案归属**。三级取值，顺序不可颠倒：
 *  ① `uuid` 中段（`kind:profileId:自然键`）——**不可变权威**，一旦生成就不再变；
 *  ② `payload.profileId`——行内业务字段（KEYED 类的 payload 保留全部字段，见 toPayload）；
 *  ③ `rec.profileId`（= 服务端 `records.profile_id` 列）——最后兜底。
 *
 * ⚠️ 为什么**不能**直接用 ③：那一列是**可被覆写的不可靠值**。3b 客户端的 `toDto` 硬编码
 * `profileId:'default'`，而 `functions/api/sync/push.ts` 的 ON CONFLICT 里有
 * `profile_id = excluded.profile_id`——任何一台旧设备把 kid2 的行回推一次，云端那行的列就
 * 变成 'default'（payload 里仍是 kid2）。拿它去定位复合主键 `[pid, nk]`，会命中**姐姐**那一行，
 * `mergeRecord` 判 put 后把妹妹的数值写进姐姐的打卡里——而且是在**已升级**的设备上发生。
 * badges / monsters 的复合键同理会被污染。
 */
function profileIdOfPulled(rec: PulledRecordDto): string {
  const fromUuid = profileIdFromUuid(rec.uuid)
  if (fromUuid !== 'default') return fromUuid
  const payload = (rec.payload ?? {}) as AnyRow
  if (typeof payload.profileId === 'string' && payload.profileId.length > 0) return payload.profileId
  return rec.profileId && rec.profileId.length > 0 ? rec.profileId : 'default'
}

/** 找本地对应行：自增表按 uuid 索引，其余按主键直查。`pid` 由 profileIdOfPulled 规范化后传入 */
async function findLocal(kind: SyncKind, rec: PulledRecordDto, pid: string): Promise<AnyRow | null> {
  const table = db.table<AnyRow>(TABLE_OF[kind])
  if (KEY_SHAPE[kind] === 'auto') {
    return (await table.where('uuid').equals(rec.uuid).first()) ?? null
  }
  // 墓碑 payload 里没有自然键，从 uuid 的 'kind:profileId:key' 形状反解（见 sync-keys）
  const nk = naturalKeyOf(kind, (rec.payload ?? {}) as AnyRow) ?? naturalKeyFromUuid(rec.uuid)
  if (nk.length === 0) return null // 键坏了：不去构造非法 key（会抛 DataError）
  const key = KEY_SHAPE[kind] === 'compound' ? ([pid, nk] as [string, string]) : nk
  return (await table.get(key)) ?? null
}
```

```ts
async function applyPulled(rec: PulledRecordDto): Promise<void> {
  // 服务端将来扩了 kind 而客户端还是老版本：忽略，不炸（孩子那台可能几周没更新）
  if (!(KINDS as readonly string[]).includes(rec.kind)) return

  const table = db.table<AnyRow>(TABLE_OF[rec.kind])
  const payload = (rec.payload ?? {}) as AnyRow
  // 档案归属只认这一处规范化的结果（uuid 中段优先），下面 findLocal 与写回都用它
  const pid = profileIdOfPulled(rec)
  // 复合主键表的两半都必须是合法 key：自然键取不到就直接跳过这一条，
  // **绝不**去构造 [pid, undefined] / [pid, ''] —— IndexedDB 会抛 DataError
  if (KEY_SHAPE[rec.kind] !== 'auto') {
    const nk = naturalKeyOf(rec.kind, payload) ?? naturalKeyFromUuid(rec.uuid)
    if (nk.length === 0 || pid.length === 0) return
  }
  const local = await findLocal(rec.kind, rec, pid)
  const outcome = mergeRecord(rec.kind, local, { payload, updatedAt: rec.updatedAt })

  if (outcome.op === 'skip') return
  if (outcome.op === 'delete') {
    if (local !== null) await table.delete(localKeyOf(rec.kind, local))
    return
  }
  const row: AnyRow = { ...payload, uuid: rec.uuid, updatedAt: rec.updatedAt, profileId: pid }
  // 自增表沿用本地 id（payload 刻意不带 id），否则同一条记录会被插成第二行
  if (KEY_SHAPE[rec.kind] === 'auto' && local !== null) row.id = local.id
  await table.put(row)
}
```

```ts
async function pullPages(transport: Transport, token: string): Promise<PushResult> {
  let since = await getLastPulledSeq()
  for (let page = 0; page < MAX_PAGES; page++) {
    const res = await transport.pull(since, PULL_LIMIT, token)
    if (!res.ok) return { ok: false, status: res.status }
    for (const rec of res.records) {
      try {
        await applyPulled(rec)
      } catch {
        // 单条隔离：任何一条记录的字段漂移（缺 profileId / 自然键坏了 / 将来新增字段）

        await setMeta(META.lastError, 'rejected').catch(() => {})
      }
    }
    since = res.nextSince
    await setLastPulledSeq(since)
    if (!res.hasMore) break
  }
  return { ok: true, status: 200 }
}
```

```ts
import {
  db, type SessionRow, type CheckinRow, type BadgeRow, type MonsterRow,
  type RedemptionRow, type ExamRow,
} from '../data/db'
import { filterByProfile } from './profile-rules'
import { getActiveProfileId } from './active-profile'

/**
 * 按档案读数据的唯一入口。业务服务与页面**只从这里读**，不再直接 `db.xxx.toArray()`——
 * 漏掉一处过滤就意味着姐姐的训练记录算进妹妹的统计里。
 *
 * 为什么一律在内存里过滤而不用 `where('profileId')`：v6 的迁移是逐行 try/catch 的，
 * 存量里可能有**没有 profileId 的行**，而 IndexedDB 的索引会跳过该字段为 undefined 的记录
 * ——那些行会从统计里静默消失（孩子几个月的记录凭空不见）。数据量只有几百行，代价可忽略。
 *
 * ⚠️ 奖励清单（rewards）刻意**没有**对应的读取函数：它是账号共享的（家长配一次、哪个孩子都能
 * 兑换，spec §11.5），照旧走 `db.rewards.toArray()`。兑换记录（redemptions）才按档案分。
 */
export async function profileSessions(profileId: string = getActiveProfileId()): Promise<SessionRow[]> {
  return filterByProfile(await db.sessions.toArray(), profileId)
}

/**
 * 本档案打卡，**按 date 升序**。
 * v9 之后 `db.checkins.toArray()` 是按复合主键 `[profileId+date]` 排的，不能直接当"按日期升序"
 * 用；而 streak 链、前缀和、补签缺口检测全都依赖日期顺序，故这里显式排序。
 */
export async function profileCheckins(profileId: string = getActiveProfileId()): Promise<CheckinRow[]> {
  const rows = filterByProfile(await db.checkins.toArray(), profileId)
  return rows.sort((a, b) => (a.date < b.date ? -1 : 1))
}

/** 本档案最后一天的打卡行（累计积分与连续天数的口径）。没有则 null——不能借用别人的链 */
export async function latestCheckin(profileId: string = getActiveProfileId()): Promise<CheckinRow | null> {
  const rows = await profileCheckins(profileId)
  return rows.length > 0 ? rows[rows.length - 1] : null
}

export async function profileBadges(profileId: string = getActiveProfileId()): Promise<BadgeRow[]> {
  return filterByProfile(await db.badges.toArray(), profileId)
}

export async function profileMonsters(profileId: string = getActiveProfileId()): Promise<MonsterRow[]> {
  return filterByProfile(await db.monsters.toArray(), profileId)
}

export async function profileRedemptions(profileId: string = getActiveProfileId()): Promise<RedemptionRow[]> {
  return filterByProfile(await db.redemptions.toArray(), profileId)
}

export async function profileExams(profileId: string = getActiveProfileId()): Promise<ExamRow[]> {
  return filterByProfile(await db.exams.toArray(), profileId)
}
```

```ts
import { db, type SessionRow, type CheckinRow } from './db'
import { nextStreak, currentStreak, type LastCheckin } from './streak'
import { dailyPoints } from './points'
import { pushSession, pushCheckin } from './api'
import { getActiveProfileId } from '../profiles/active-profile'
import { filterByProfile } from '../profiles/profile-rules'
import { latestCheckin } from '../profiles/profile-data'

/**
 * 三个函数的签名刻意**一字不动**：档案从"当前档案"取，调用方（TrainingPage / HomePage /
 * SettingsPage）零改动。
 */
export async function saveSession(row: Omit<SessionRow, 'id'>): Promise<void> {
  // 写入必须盖上当前档案，否则新数据全落进 default——妹妹练的算进姐姐的统计里
  const stamped = { ...row, profileId: row.profileId ?? getActiveProfileId() }
  const id = await db.sessions.add(stamped)
  pushSession({ ...stamped, id })
}

export interface CheckinResult {
  alreadyCheckedIn: boolean
  streak: number
  dailyPoints: number
  totalPoints: number
}

/** 完成一轮训练后打卡；今日答对数从**本档案**的 sessions 汇总。today = 本地 YYYY-MM-DD */
export async function doCheckIn(today: string): Promise<CheckinResult> {
  const profileId = getActiveProfileId()
  const existing = await db.checkins.get([profileId, today])
  if (existing) {
    return {
      alreadyCheckedIn: true,
      streak: existing.streak,
      dailyPoints: existing.dailyPoints,
      totalPoints: existing.totalPoints,
    }
  }
  // 按日期索引取当天所有档案的行，再按档案筛——不能让姐姐的答对数抬高妹妹的当日积分
  const todaySessions = filterByProfile(await db.sessions.where('date').equals(today).toArray(), profileId)
  const correctToday = todaySessions.reduce((sum, r) => sum + r.correct, 0)

  const last = await latestCheckin(profileId)
  const lastCk: LastCheckin | null = last ? { date: last.date, streak: last.streak } : null
  const streak = nextStreak(lastCk, today)
  const dp = dailyPoints(correctToday, streak)
  const totalPoints = (last ? last.totalPoints : 0) + dp

  const row: CheckinRow = { profileId, date: today, streak, dailyPoints: dp, totalPoints }
  await db.checkins.put(row)
  pushCheckin(row)
  return { alreadyCheckedIn: false, streak, dailyPoints: dp, totalPoints }
}

export interface HomeStats {
  checkedInToday: boolean
  streak: number
  totalPoints: number
}

export async function getHomeStats(today: string): Promise<HomeStats> {
  try {
    const last = await latestCheckin()
    const lastCk: LastCheckin | null = last ? { date: last.date, streak: last.streak } : null
    return {
      checkedInToday: last?.date === today,
      streak: currentStreak(lastCk, today),
      totalPoints: last ? last.totalPoints : 0,
    }
  } catch {
    // IndexedDB 不可用（隐私模式/storage 受限）时降级，不崩
    return { checkedInToday: false, streak: 0, totalPoints: 0 }
  }
}
```

```ts
import { db } from '../data/db'
import { deriveStats } from './stats-derive'
import { evaluate } from './evaluate'
import { BADGES, type BadgeDef } from './badge-defs'
import { pushBadges } from '../data/api'
import { getActiveProfileId } from '../profiles/active-profile'
import { profileSessions, profileCheckins, profileBadges } from '../profiles/profile-data'

/**
 * 检测并写入新解锁的勋章，返回新解锁的定义列表。
 *
 * spec §11.5：勋章**每档案独立**——成就属于个人，共享会抹掉"自己挣来的"这层意义。
 * 姐姐已解锁 20 枚，妹妹第一次打开勋章墙就该是空的。
 */
export async function syncBadges(now: number): Promise<BadgeDef[]> {
  const profileId = getActiveProfileId()
  const [sessions, checkins, existing] = await Promise.all([
    profileSessions(profileId),
    profileCheckins(profileId),
    profileBadges(profileId),
  ])
  const achieved = new Set(evaluate(deriveStats(sessions, checkins)))
  const have = new Set(existing.map((b) => b.id))
  const newIds = [...achieved].filter((id) => !have.has(id))
  if (newIds.length > 0) {
    // profileId 是复合主键 [profileId+id] 的一半，缺了 bulkPut 直接 DataError
    const rows = newIds.map((id) => ({ profileId, id, unlockedAt: now }))
    await db.badges.bulkPut(rows)
    pushBadges(rows)
  }
  const byId = new Map(BADGES.map((b) => [b.id, b]))
  return newIds.map((id) => byId.get(id)).filter((b): b is BadgeDef => b !== undefined)
}

export async function getUnlockedIds(): Promise<Set<string>> {
  return new Set((await profileBadges()).map((b) => b.id))
}
```

```ts
import { lsGet, lsSet } from '../data/storage'
import { getActiveProfileId } from './active-profile'

/**
 * 每档案独立的**医学参数**（spec §11.5）。
 *
 * ⚠️ 这三个键单独拎出来是**医学正确性**问题，不是偏好：两个孩子视力不同，视标大小共享会让
 * 训练强度对其中一个是错的（视标 = 等效视力级别，直接决定调节刺激量）。
 * 与之相对，这些**继续设备共享**、不要顺手改成按档案：
 *  - `fzp.cssPxPerMm`（屏幕标定）：屏幕物理属性，与孩子无关；
 *  - `fzp.flipMs`（翻拍速度）/ `fzp.lang` / `fzp.skinId`：设备偏好，换档案不该重设。
 */
export const MEDICAL_BASES = ['optotypeSizeMm', 'durationSec', 'flipperD'] as const
export type MedicalBase = (typeof MEDICAL_BASES)[number]

/** 硬默认，与 3c 之前各处的兜底值逐字一致（1.0mm / 180s / ±2.00D） */
export const MEDICAL_DEFAULTS: Record<MedicalBase, number> = {
  optotypeSizeMm: 1,
  durationSec: 180,
  flipperD: 2,
}

/** 每档案键名。仍用 `fzp.` 前缀——备份的 collectSettings() 靠它自动收集，不必改备份逻辑 */
export function profileSettingKey(profileId: string, base: string): string {
  return `fzp.p.${profileId}.${base}`
}

/** 旧的设备级键名（迁移的来源，且**刻意不删**：回滚到旧构建时它还得能读） */
function legacyKey(base: string): string {
  return `fzp.${base}`
}

/** 数值解析：null / 空 / 非数字 / ≤0 一律退回默认（0mm 视标、0 秒训练都是坏值） */
export function numOr(raw: string | null, fallback: number): number {
  if (raw === null || raw === '') return fallback
  const n = Number(raw)
  return Number.isFinite(n) && n > 0 ? n : fallback
}

/**
 * 一次性迁移：把家长既有的三个设备级医学参数拷到 default 档案。纯函数（读取器注入），便于单测。
 *
 * 为什么必须迁：家长已经实测把视标调到约 0.7mm；升级后若读不到就退回默认 1.0mm，
 * 等于**悄悄把训练难度改了**——而这属于医学参数，不是"少个偏好"。
 * 只在目标键还不存在时写，故幂等：重复启动不会把家长后来的改动回退。
 */
export function legacyMigrationWrites(
  read: (key: string) => string | null,
  profileId: string,
): { key: string; value: string }[] {
  const out: { key: string; value: string }[] = []
  for (const base of MEDICAL_BASES) {
    const target = profileSettingKey(profileId, base)
    if (read(target) !== null) continue
    const old = read(legacyKey(base))
    if (old === null || old === '') continue
    out.push({ key: target, value: old })
  }
  return out
}

/**
 * **恢复备份**时的医学参数搬运（纯函数，与上面的启动迁移刻意口径不同）。
 *
 * 差别在"要不要覆盖"：`legacyMigrationWrites` 是幂等的启动迁移，见到目标键已存在就跳过；
 * 而恢复备份表达的是"我要这份文件里的值"，**必须强制覆盖**当前档案键。
 * 不这么做的后果：家长恢复 3c 之前导出的老备份后，文件里的 `fzp.optotypeSizeMm=0.7` 被写回
 * 旧键，但训练页与设置页读的是 `fzp.p.default.optotypeSizeMm`，而唯一的搬运者
 * `migrateLegacyMedicalKeys()` ①只在 main.tsx 启动时跑、②目标键已存在就跳过
 * → 视标仍是当前档案的现值，**恰好在最需要正确的场景里悄悄改了训练强度**。
 *
 * 备份文件里若已有 `fzp.p.<profileId>.<base>`（3c 之后导出的），以它为准、不回写旧键。
 */
export function restoredMedicalWrites(
  settings: Record<string, string>,
  profileId: string,
): { key: string; value: string }[] {
  const out: { key: string; value: string }[] = []
  for (const base of MEDICAL_BASES) {
    const target = profileSettingKey(profileId, base)
    // 新备份自带每档案键：restoreBackup 写回 settings 时已经把它写进去了，这里别再拿旧键覆盖
    if (typeof settings[target] === 'string' && settings[target] !== '') continue
    const old = settings[legacyKey(base)]
    if (typeof old !== 'string' || old === '') continue
    out.push({ key: target, value: old })
  }
  return out
}

/**
 * 内存镜像：storage 不可用时（隐私模式 / storage 分区 / **node 单测**）仍能在本次会话内
 * 读到刚写的值。`lsGet`/`lsSet` 是静默降级的，没有这层镜像"改了设置立刻读回"就会失败。
 */
const mirror = new Map<string, string>()

function readKey(key: string): string | null {
  const v = lsGet(key)
  if (v !== null) return v
  return mirror.get(key) ?? null
}

function writeKey(key: string, value: string): void {
  mirror.set(key, value)
  lsSet(key, value)
}

export function readMedical(base: MedicalBase, profileId: string = getActiveProfileId()): number {
  // 只读**本档案**的键：新档案没有值就用硬默认，绝不继承别的孩子的视标大小
  return numOr(readKey(profileSettingKey(profileId, base)), MEDICAL_DEFAULTS[base])
}

export function writeMedical(base: MedicalBase, value: number, profileId: string = getActiveProfileId()): void {
  writeKey(profileSettingKey(profileId, base), String(value))
}

/** 启动时跑一次（幂等）。刻意只拷不删旧键 */
export function migrateLegacyMedicalKeys(): void {
  for (const w of legacyMigrationWrites(readKey, 'default')) writeKey(w.key, w.value)
}

/**
 * 恢复备份后调用（Task 9 的 `restoreBackup` 在写回 settings 之后调它）。
 * 与 `migrateLegacyMedicalKeys` 的区别见 `restoredMedicalWrites` 的注释：这里**强制覆盖**。
 */
export function applyRestoredMedicalKeys(
  settings: Record<string, string>,
  profileId: string = DEFAULT_PROFILE_ID,
): void {
  for (const w of restoredMedicalWrites(settings, profileId)) writeKey(w.key, w.value)
}
```

```ts
/**
 * 拉取落库后必须重算打卡链（spec §6.5）。变化的行重新入队 —— 让所有设备收敛到同一结果。
 * 不会来回打乒乓：重算只依赖 (date, dailyPoints, repairDates) 且严格幂等。
 * 返回是否有变化，供 syncNow 决定要不要在**本轮**再排空一次 outbox。
 *
 * ⚠️ 必须**按档案分组**再重算。streak 与 totalPoints 是链式累积的，把两个孩子的行混在一条链上
 * 算，结果是姐姐连练 10 天会把妹妹的连续天数抬上去、累计积分（能换现实奖励的货币）跟着虚高。
 * 补签日期同理要按档案取：姐姐买的补签卡不该把妹妹当天的分清零。
 */
async function reconcileAndWriteBack(): Promise<boolean> {
  const [checkins, reds] = await Promise.all([db.checkins.toArray(), db.redemptions.toArray()])
  if (checkins.length === 0) return false

  const before = new Map(checkins.map((c) => [`${profileIdOf(c)}:${c.date}`, c]))
  const byProfile = new Map<string, CheckinRow[]>()
  for (const c of checkins) {
    const pid = profileIdOf(c)
    const arr = byProfile.get(pid)
    if (arr) arr.push(c)
    else byProfile.set(pid, [c])
  }

  const changed: CheckinRow[] = []
  for (const [pid, rows] of byProfile) {
    const repairDates = repairDatesFrom(reds.filter((r) => profileIdOf(r) === pid))
    for (const row of reconcileCheckins(rows, repairDates)) {
      const old = before.get(`${pid}:${row.date}`)
      if (
        !old || old.streak !== row.streak ||
        old.dailyPoints !== row.dailyPoints || old.totalPoints !== row.totalPoints
      ) {
        changed.push(row)
      }
    }
  }
  // enqueuePut 同时写本地行并入 outbox（updatedAt = 现在），故本设备的重算结果会赢下 LWW
  if (changed.length === 0) return false
  await enqueuePut('checkin', changed)
  return true
}
```

```ts
function stampProfile<T extends { profileId?: string }>(rows: readonly T[]): T[] {

    ...r,
```

```ts
      if (incomingProfiles !== undefined) {

  // ①只在 main.tsx 启动时跑、②目标键已存在就跳过（幂等设计）——于是家长"用备份恢复"之后
  // 视标仍是恢复前的值，恰好在最需要正确的场景里悄悄改了训练强度。这里**强制**搬一次。
  applyRestoredMedicalKeys(file.settings)
  // 先保证 default 档案存在，再把数据里出现过、档案表里没有的 id 补出档案：
  // 不补出来那些记录数据还在，但界面上切不到（老备份里通常根本没有 profiles 表）
  await ensureDefaultProfile()
  await ensureProfilesForData()

  await pushAll()
```

```tsx
import { useEffect, useState } from 'react'
import type { ProfileRow } from '../data/db'
import { listActiveProfiles, ensureProfilesForData } from './profiles-service'
import { setActiveProfileId, useActiveProfileId } from './active-profile'
import { useT } from '../i18n'

/**
 * 首页档案切换器（孩子自己点）。样式与皮肤选择那排小药丸一致，孩子已经会用了。
 *
 * ⚠️ **只在可用档案 ≥2 时渲染**（spec §11.5 的渐进披露）：独生子女家庭不该为多档案付
 * 任何认知成本——单档案时这里必须什么都不出现，连标题都不要。
 */
export function ProfileSwitcher() {
  const t = useT()
  const active = useActiveProfileId()
  const [rows, setRows] = useState<ProfileRow[] | null>(null)

  // 挂载时先补一次陌生档案再列（首页在切视图时会重新挂载，故同步刚拉来的孩子很快就能出现）。
  // 幂等且便宜：没有缺失时不写任何行、不入 outbox。**刻意不放在同步引擎里**——那样会让
  // syncNow 结束时 outbox 非空，打破 engine.test.ts 里几处 `outbox.count()===0` 的既有断言。
  useEffect(() => {
    void ensureProfilesForData()
      .catch(() => {})
      .then(() => listActiveProfiles())
      .then(setRows)
      .catch(() => setRows([]))
  }, [])

  if (rows === null || rows.length < 2) return null

  return (
    <div
      className="fq-rise"
      style={{ display: 'flex', gap: 6, justifyContent: 'center', flexWrap: 'wrap', alignItems: 'center' }}
    >
      <span style={{ fontSize: 12, color: 'var(--muted)', fontWeight: 600 }}>{t('home.profilePick')}</span>
      {rows.map((p) => {
        const on = p.id === active
        return (
          <button
            key={p.id}
            className="fq-chip"
            onClick={() => setActiveProfileId(p.id)}
            style={{
              cursor: 'pointer', fontWeight: 700, border: '1.5px solid transparent',
              background: on ? 'var(--violet)' : 'var(--chip-bg)', color: on ? '#fff' : 'var(--violet)',
            }}
          >
            {p.name}
          </button>
        )
      })}
    </div>
  )
}
```
