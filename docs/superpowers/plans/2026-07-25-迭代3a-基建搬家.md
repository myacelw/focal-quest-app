# 迭代 3a 基建搬家（Cloudflare Pages + 自定义域名）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 app 从 GitHub Pages 子路径迁到 Cloudflare Pages 自有域名根路径，并让跨域隔离（vosk 所需的 COOP/COEP）由平台响应头下发而非仅靠 Service Worker 补头。

**Architecture:** 前端构建产物不变，只改三处外围：①新增 `public/_headers` 让 Cloudflare Pages 原生下发 COOP/COEP/CORP；②新增 `wrangler.toml` 声明 Pages 项目（3b 将在同文件加 D1 binding）；③新增 CI workflow 用 wrangler 部署。`VITE_BASE` 已 env 化且默认 `/`，故根路径部署无需改代码。**SW 的补头逻辑保留不动**——它是幂等的 `set`，与平台头共存，且是离线场景与配置失误的双保险。

**Tech Stack:** Vite 6 + vite-plugin-pwa（injectManifest）、wrangler（新增 devDependency）、GitHub Actions。

### Task 2: 本地用 wrangler 验证跨域隔离真的生效

**Files:**
- Create: `scripts/check-coi.mjs`

**Interfaces:**
- Consumes: Task 1 的 `dist/_headers`、`npm run cf:dev`。
- Produces: `scripts/check-coi.mjs`（`node scripts/check-coi.mjs <baseUrl>`，退出码 0=全部头就位，1=缺头并打印缺哪个）。3a 收尾与将来回归都用它。

**为什么需要这一步：** `scripts/serve-dist.mjs` 是**故意不发头**的裸静态服务器（模拟 GitHub Pages）。它读不到 `_headers`，用它测等于没测。`wrangler pages dev` 会真正解析 `_headers`，是本地唯一能验证 Pages 行为的方式。

**本任务的 red-green 从何而来：** 项目里正好有两个服务器——`serve-dist.mjs` **故意不发头**（模拟 GitHub Pages），`wrangler pages dev` **会读 `_headers`**。先拿脚本对准前者，它必须报"缺头"（red，证明脚本真在检查而非空转）；再对准后者，它必须通过（green）。这比人为制造 bug 更真实。

- [ ] **Step 1: 写检查脚本**

创建 `scripts/check-coi.mjs`：

```js
/**
 * 检查一个部署（本地 wrangler pages dev 或线上）是否下发跨域隔离三件套。
 * 用法：node scripts/check-coi.mjs http://127.0.0.1:8788
 * 退出码 0 = 首页与子资源都带全 COOP/COEP/CORP；1 = 有缺失（打印明细）。
 */
const base = process.argv[2] || 'http://127.0.0.1:8788'

const WANT = {
  'cross-origin-opener-policy': 'same-origin',
  'cross-origin-embedder-policy': 'require-corp',
  'cross-origin-resource-policy': 'cross-origin',
}

async function checkOne(url) {
  const res = await fetch(url)
  const missing = []
  for (const [k, v] of Object.entries(WANT)) {
    const got = res.headers.get(k)
    if (got !== v) missing.push(`${k}: 期望 ${v}，实际 ${got ?? '(无)'}`)
  }
  return { url, status: res.status, missing }
}

// 从首页 HTML 里挑一个真实子资源（构建产物带 hash，不能写死文件名）
async function findAsset() {
  const html = await (await fetch(base + '/')).text()
  const m = html.match(/(?:src|href)="([^"]*\/assets\/[^"]+\.(?:js|css))"/)
  return m ? new URL(m[1], base).href : null
}

const targets = [base + '/']
const asset = await findAsset()
if (asset) targets.push(asset)
else console.warn('警告：首页里没找到 /assets/ 子资源，只检查首页')

let bad = 0
for (const t of targets) {
  const r = await checkOne(t)
  if (r.missing.length) {
    bad++
    console.error(`✗ ${r.url} (HTTP ${r.status})`)
    for (const m of r.missing) console.error('   ' + m)
  } else {
    console.log(`✓ ${r.url} (HTTP ${r.status}) 三头齐全`)
  }
}
console.log(bad === 0 ? '全部通过' : `${bad} 个目标缺头`)
process.exit(bad === 0 ? 0 : 1)
```

### Task 3: Service Worker 放行 `/api/`（为 3b 铺路，必须先上线）

**Files:**
- Modify: `src/sw.ts`（fetch 事件处理器顶部，约 82-88 行）
- Create: `src/sw-route.test.ts`

**Interfaces:**
- Produces: 纯函数 `shouldBypass(pathname: string): boolean` 从 `src/sw.ts` 导出，供测试；SW 内部在 fetch handler 顶部调用它。
- Consumes: 无。

**为什么这个改动必须在 3a 而不是 3b：** 现有 SW 的 fetch handler 对**所有同源 GET** 做 cache-first 并回填缓存（`sw.ts:82-142`，只放过非 GET 和跨域）。3b 的 `GET /api/sync/pull` 若被它接管，客户端将反复读到**过期的缓存响应**，同步表现为"拉不到新数据"且极难排查。而 iPad 上**已装机的旧 SW 要等新版本部署后才会换**——所以放行逻辑必须比账号功能**先**上线，否则 3b 首发那几天正好踩坑。

- [ ] **Step 1: 写失败的测试**

创建 `src/sw-route.test.ts`：

```ts
import { describe, it, expect } from 'vitest'
import { shouldBypass } from './sw'

describe('shouldBypass', () => {
  it('放行 /api/ 下的请求（云同步必须直连网络，不能吃 SW 缓存）', () => {
    expect(shouldBypass('/api/sync/pull')).toBe(true)
    expect(shouldBypass('/api/auth/login')).toBe(true)
  })

  it('不放行普通静态资源（它们要走 cache-first 才能离线）', () => {
    expect(shouldBypass('/index.html')).toBe(false)
    expect(shouldBypass('/assets/index-abc123.js')).toBe(false)
    expect(shouldBypass('/badges/sheet1.webp')).toBe(false)
    expect(shouldBypass('/models/vosk-model.tar.gz.part00')).toBe(false)
  })

  it('不把名字里含 api 的静态资源误判为接口', () => {
    expect(shouldBypass('/assets/api-helper-abc.js')).toBe(false)
    expect(shouldBypass('/rapid.png')).toBe(false)
  })
})
```

- [ ] **Step 3: 实现最小改动**

在 `src/sw.ts` 中，`isModelOrHeavy` 函数**之后**、`sw.addEventListener('fetch', ...)` **之前**插入：

```ts
/**
 * 是否绕过 SW 直连网络。云同步接口（/api/*）必须每次真发请求：
 * 本 SW 对同源 GET 一律 cache-first，若接管了 pull 请求，客户端会反复读到过期响应。
 * 用路径段匹配而非 includes('api')，避免把 /assets/api-helper.js 之类静态资源误判。
 */
export function shouldBypass(pathname: string): boolean {
  return pathname === '/api' || pathname.startsWith('/api/')
}
```

然后在 fetch 处理器里，`if (url.origin !== sw.location.origin) return` 这一行**之后**插入一行：

```ts
  if (shouldBypass(url.pathname)) return // /api/* 交给浏览器直连，不缓存不代理
```

改完后该段应为：

```ts
sw.addEventListener('fetch', (event) => {
  const req = event.request
  if (req.method !== 'GET') return
  const url = new URL(req.url)
  if (url.origin !== sw.location.origin) return // 跨域资源不经手（本项目本无跨域）
  if (shouldBypass(url.pathname)) return // /api/* 交给浏览器直连，不缓存不代理
```

### Task 4: CI 自动部署到 Cloudflare Pages

**Files:**
- Create: `.github/workflows/deploy-cf.yml`

**Interfaces:**
- Consumes: 人工前置 P5 配好的 secrets `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`；Task 1 的 `wrangler.toml`；Task 3 已放行 `/api/` 的 SW。
- Produces: push 到 master 即部署到 Cloudflare Pages 的流水线。与既有 `deploy.yml`（GitHub Pages 热备）并存。

- [ ] **Step 1: 写 workflow**

创建 `.github/workflows/deploy-cf.yml`：

```yaml
name: Deploy PWA to Cloudflare Pages

# 推送 master 自动构建并部署到 Cloudflare Pages（自有域名、根路径）。
# 与 deploy.yml（GitHub Pages 热备）并存：两者构建同一份源码，
# 区别只在 VITE_BASE（此处为根路径，故不设）与发布目标。
on:
  push:
    branches: [master]
  workflow_dispatch:

concurrency:
  group: cf-pages
  cancel-in-progress: true

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm

      - run: npm ci

      # vosk 模型已切片入库（public/models/*.part* + parts.json），无需下载。
      # 不设 VITE_BASE → 默认 '/'，自有域名根路径部署。
      - name: 构建
        run: npm run build
        env:
          VITE_BACKEND: 'off'

      - name: 部署到 Cloudflare Pages
        uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: pages deploy dist --project-name=focal-quest
```

- [ ] **Step 4: 写部署文档**

创建 `docs/部署到-Cloudflare-Pages.md`：

```markdown
# 部署到 Cloudflare Pages（当前线上方案）

线上地址：https://<你的域名>

## 为什么从 GitHub Pages 迁过来

- **自有域名 + 根路径**：不再是 `github.io/focal-quest-app/` 子路径。
- **跨域隔离由平台下发**：vosk 依赖 SharedArrayBuffer → 需要 COOP/COEP。
  GitHub Pages 设不了响应头，只能靠 `src/sw.ts` 给每个响应补头 + "未隔离则刷新一次"兜底；
  Cloudflare Pages 支持 `public/_headers`，**首屏加载时就已隔离**，SW 补头退为双保险。
- **同域后端**：3b 的 `/api/*` 走 Pages Functions，与前端同域，零 CORS。
- **国内可达性**：`*.pages.dev` 默认子域在大陆被 DNS 污染，**必须绑自定义域名**才能访问。

## 组成部分

| 文件 | 作用 |
|---|---|
| `public/_headers` | Pages 原生下发 COOP/COEP/CORP |
| `wrangler.toml` | Pages 项目名与产物目录（3b 起还含 D1 binding） |
| `.github/workflows/deploy-cf.yml` | push master 自动构建+部署 |
| `scripts/check-coi.mjs` | 验证部署是否真的下发三头 |
| `src/sw.ts` 的 `shouldBypass()` | 放行 `/api/*` 直连网络（否则云同步会读到 SW 缓存的旧响应） |

## 日常操作

推送 master 即自动部署。手动部署：

```bash
npm run build && npm run cf:deploy
```

本地模拟 Pages（**唯一能验证 `_headers` 的本地方式**，`npm run serve:static` 故意不发头以模拟 GitHub Pages）：

```bash
npm run cf:dev
```

然后另开终端跑 `node scripts/check-coi.mjs http://127.0.0.1:8788`。

## 更新机制

与 GitHub Pages 时期一致：`registerType: 'autoUpdate'`，孩子联网打开一次即静默更新；
vosk 模型在 SW 的跨版本 `fq-runtime` 缓存里，不会重下 42MB。

## 排查

| 现象 | 原因与处理 |
|---|---|
| `crossOriginIsolated` 为 false | `dist/_headers` 未生成或缩进不对（须两空格）；跑 check-coi.mjs 看缺哪个头 |
| 语音识别不可用 | 同上；跨域隔离失败时 vosk 无法加载 |
| CI 报 Authentication error | `CLOUDFLARE_API_TOKEN` 未配或权限不足 |
| CI 报 project not found | Pages 项目名与 `--project-name` 不一致 |
| `*.pages.dev` 打不开 | 预期行为（大陆 DNS 污染），用自定义域名访问 |
